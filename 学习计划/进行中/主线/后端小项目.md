# Spring Boot 学生选课与成绩管理系统｜完整项目实战计划书（升级版）

> **定位**：面向 Java 后端实习的完整单体项目；以真实教务业务为主线，兼顾技术深度、工程质量与可展示亮点。
>
> **主线**：业务建模 → Spring Boot API → 选课事务与并发 → 成绩业务 → 权限与安全 → 测试及性能 → Docker 交付。
>
> **进度管理**：按任务与验收推进，不设固定天数。只有提交代码、测试通过并有证据，才勾选完成。
>
> **当前状态**：规划完成，尚未开始实施。MyBatis / MyBatis-Plus 基础理论与核心实操已完成；本项目重点从“会用 API”过渡到“能设计、实现、验证和交付真实业务”。

## 一、项目目标和亮点

### 1.1 项目目标

开发一个支持**学生、教师、管理员**使用的选课与成绩管理后端。系统不仅提供 CRUD，还要处理学期、开课班级、选课时间窗口、容量限制、时间冲突、退课、成绩录入与发布等实际业务，并保证并发情况下的数据正确性。

最终交付应达到：

- 能用 API 完整演示从“创建课程 → 发布开课计划 → 学生选课 → 教师录入成绩 → 成绩发布 → 学生查询”的业务闭环。
- 能独立解释表设计、事务边界、关键 SQL、冲突处理和权限设计。
- 有可重复执行的自动化测试、并发测试、部署配置及接口文档。
- 有可展示的 Git 历史、架构图、核心流程图、测试结果与 README。

### 1.2 项目核心亮点（必须真正实现，不只写在 README）

| 亮点 | 要解决的业务问题 | 技术实现 | 展示证据 |
|---|---|---|---|
| **高并发防超选** | 最后一个名额被多人抢占 | 条件 UPDATE + InnoDB 行锁 + 事务 + 唯一约束 | 并发请求测试、容量不超限断言 |
| **选课冲突检测** | 同一学生选择上课时间重叠的课程 | 学期、星期、节次/时间区间建模，冲突 SQL 与事务内再校验 | 冲突/不冲突/临界边界用例 |
| **完整成绩工作流** | 未发布成绩不能被学生看到 | 录入、修改、发布状态与角色权限 | 教师录入→发布→学生可见的端到端测试 |
| **权限与数据隔离** | 学生不能替别人选课，教师不能修改非本人开课班级成绩 | Spring Security + 登录鉴权 + 角色和资源归属校验 | 401/403/越权测试 |
| **可靠性与工程交付** | 重复请求、异常回滚、部署难复现 | 唯一约束、幂等策略、集成测试、Docker Compose | 回滚测试、重复请求测试、一键启动说明 |

**原则**：以高并发选课和业务规则为技术主亮点；安全、自动化测试和部署构成工程亮点。拒绝为了技术名词堆叠而引入微服务、MQ 或 Kubernetes。

### 1.3 项目完成的两个里程碑

- **里程碑 A｜可用核心系统**：学生/教师/课程/学期/开课管理、选退课、冲突检测、成绩管理、关键事务与测试通过；接口可演示。
- **里程碑 B｜简历级交付**：基础认证与资源权限、完整异常处理、集成和并发测试、关键 SQL 优化、Docker Compose、README/API 文档、可展示证据。

## 三、业务范围及边界

### 3.1 必须完成的业务

1. **学生管理**：学号唯一、增改查、状态管理、条件分页。
2. **教师管理**：工号唯一、基本信息、负责的开课班级查询。
3. **课程管理**：课程编号、学分、基础容量规则及课程信息管理。
4. **学期与开课管理**：课程按学期创建开课班级（Section），明确授课教师、容量、上课时段、选课时间窗口。
5. **选课/退课**：校验学生和开课状态、名额、重复选择、时间冲突；退课遵守截止时间和成绩规则。
6. **成绩管理**：教师为本班学生录入/修改成绩，发布后学生可查；成绩范围与发布约束。
7. **查询与统计**：我的课表、课程名单、课程成绩分布、学生学期平均分/排名，含分页和复杂 SQL。
8. **认证与权限**：学生、教师、管理员基础登录；学生仅操作本人，教师仅操作所授课班级，管理员管理基础数据。

### 3.2 明确不做（第一版）

- 复杂自动排课算法、跨校区资源调度、完整教务审批系统。
- 完整前端应用（使用 Swagger UI/Apifox 演示 API 即可）。
- Redis、消息队列、分布式事务、微服务、Kubernetes。
- 支付、短信、邮件、生产级 SSO。

**可选扩展**：课程候补队列、操作审计、Redis 热点查询缓存、CI 自动测试；仅在核心验收完成后增加。

## 四、数据库设计（先设计，后编码）

### 4.1 核心表（推荐 8 张）

| 表 | 核心字段（示例） | 关键作用 |
|---|---|---|
| `student` | `id, student_no, name, status` | 学生身份与状态 |
| `teacher` | `id, teacher_no, name, status` | 教师身份 |
| `course` | `id, course_code, name, credit` | 课程目录（不代表某学期的开课） |
| `semester` | `id, code, name, start_date, end_date, status` | 学期 |
| `course_section` | `id, course_id, semester_id, teacher_id, capacity, enrolled_count, status, enrollment_start, enrollment_end, version` | 某门课程在某学期的具体开课班级 |
| `section_schedule` | `id, section_id, day_of_week, start_slot, end_slot` | 开课班级的上课时间片段 |
| `enrollment` | `id, student_id, section_id, score, grade_status, created_at` | 当前有效的选课关系及成绩 |
| `app_user` | `id, username, password_hash, role, student_id, teacher_id, status` | 身份验证及角色映射 |

> `app_user` 属于后期安全阶段；早期可以用测试身份模拟调用，不应为完成登录而延迟核心业务。时间冲突检测以“同一学期的节次区间”作为第一版模型；若采用真实时钟，需明确时区与日期/周次规则。

### 4.2 核心约束

- `student.student_no`、`teacher.teacher_no`、`course.course_code`、`semester.code` 唯一。
- `enrollment` 建立 `UNIQUE(student_id, section_id)`，从数据库层面防重复选课。
- **第一版退课采用物理删除 `enrollment`**（仅允许未产生正式成绩、未过退课截止时间的记录退课）；如要保留退课历史，可额外建立事件/审计表，**不要直接给 `enrollment` 加固定 0/1 逻辑删除同时保留上述唯一约束**。
- `course_section.capacity > 0`，`0 <= enrolled_count <= capacity`；必要时增加数据库 CHECK，服务层仍需校验。
- `score` 为 `NULL` 表示未录入，非空时须介于 0～100；学生查询仅返回已发布成绩。
- `course_section` 必须属于有效学期、教师和课程；选课关系使用外键或明确的应用层参照完整性策略。
- 课程满员、学期状态、选课时间、时间冲突等属于业务规则，数据库约束无法全部替代。

### 4.3 数据一致性设计

**选课**的以下步骤在同一个 Spring 事务中执行。

1. 验证身份、学期、选课窗口、开课状态和学生状态。
2. 验证同学期课表无冲突（注意并发时必须重校验或用恰当锁保证）。
3. 先使用条件 UPDATE 占用名额：

   ```sql
   UPDATE course_section
   SET enrolled_count = enrolled_count + 1
   WHERE id = :sectionId
     AND status = 'OPEN'
     AND enrolled_count < capacity;
   ```

4. 检查影响行数必须为 1；插入 `enrollment`，依靠唯一索引挡住重复请求。
5. 任何一步失败，**整体回滚**；不能吞掉异常后错误提交。

**特别注意：**容量控制与课表时间冲突属于两类并发问题。上述条件 UPDATE 能防容量超额，却**不能独立保证同一个学生同时提交两门时间冲突课程时一定被阻止**。第一版可以在同一事务中锁定该学生记录（如 `SELECT ... FOR UPDATE`）以串行化该学生的选课/退课修改，然后再执行冲突检查、占名额和插入；所有选退课写入路径遵循同一锁顺序，避免死锁。对同一学期的重复请求仍由唯一约束兜底。

**退课**也使用同一个事务。先锁定学生及相关记录，再校验退课条件、删除选课记录，确认恰好删除 1 行后执行带 `enrolled_count > 0` 条件的人数扣减。若扣减未更新 1 行，则整体回滚。重复退课不会重复扣减人数。

**成绩**发布独立于选课状态。学生接口只返回已发布的成绩。教师只能修改本人授课班级中尚未锁定且尚未发布的成绩。发布规则由 Service 层执行，并测试越权与非法状态转换。

### 4.4 索引与 SQL

- 为 `enrollment(section_id)`、`course_section(semester_id, teacher_id)`、课表查询相关连接列建立必要索引，避免仅凭猜测建索引。
- 选课列表、学生课表、成绩统计至少各有一条自定义 MyBatis XML SQL。
- 使用 `EXPLAIN` 检查主要 JOIN/过滤条件，并记录优化前后结果；性能结论需基于可复现测试数据。

## 五、项目架构与工程规范

### 5.1 基础架构

```text
HTTP/API
  ↓
Controller（请求、校验、响应）
  ↓
Service（业务规则、权限、事务）
  ↓
Mapper（MP CRUD / XML SQL）
  ↓
MySQL
```

目录参考：`controller/`, `service/`, `service/impl/`, `mapper/`, `entity/`, `dto/`, `vo/`, `config/`, `security/`, `exception/`, `common/`。**按实际需要创建包，不提前建空目录。**

### 5.2 工程约定

- Controller 不直接操作 Mapper；业务规则放 Service；跨表事务放在清晰的 Service 入口。
- 请求用 DTO、输出用 VO，不直接把含密码等敏感字段的 Entity 返回给客户端。
- 参数校验与业务校验分开；统一处理校验失败、资源不存在、业务冲突、权限不足、系统异常。
- API 使用恰当的 HTTP 状态码；重点区分 400、401、403、404、409、500。
- 日志要能定位接口请求、业务错误和数据库异常；脱敏，不回显底层堆栈给客户端。
- `@Transactional` 的代理调用、自调用失效、异常吞掉后不回滚等问题必须在项目中验证。

## 七、持续执行的 Git、测试与开发规则

### 7.1 一次开发任务的标准流程

**明确需求 → 明确验收条件 → 先设计 → 独立编码 → 测试 → Code Review → 修复 → Git 提交 → 记录结果。**

- 每次只推进一个有边界的任务；不因建议执行就标记完成。
- 优先独立编写核心代码，AI 用于原理解释、方案比较、代码审查、排障。
- 简单 CRUD 练一次完整链路即可；后续复用，不做机械重复训练。
- 失败场景必须有测试；涉及数据修改的测试注意清理与隔离。
- 每个模块完成后更新进度、未解决问题与决策记录，不在项目末尾补写所有文档。

### 7.2 Git 必须实际掌握的操作

- [ ] `status / add / commit / log / diff`
- [ ] `.gitignore` 与敏感配置排除
- [ ] `branch / switch / merge`，处理一次实际冲突
- [ ] `fetch / pull / push`，理解 non-fast-forward
- [ ] `restore / revert / stash` 的适用区别
- [ ] 为稳定交付版本创建 Tag

### 7.3 测试级别

- **单元测试**：校验业务条件、错误分支、部分 Service 逻辑。
- **数据库集成测试**：约束、Mapper XML、事务和真实 SQL 行为。
- **API 集成测试**：入参校验、HTTP 状态码、权限与响应结构。
- **并发测试**：竞争最后名额、同一学生并发选冲突课、重复退课。
- **交付烟雾测试**：从干净数据库启动后演示关键 API。

**测试证据不等于只贴一张成功截图**：至少记录场景、输入、期望、实际结果与运行方式。
