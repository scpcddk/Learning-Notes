## 一、项目定位、范围与完成标准

### 1.1 定位

本项目是一个面向 Java 后端实习和长期工程能力积累的**单体教务系统**。以高校的学生选课、教师管理和成绩认定流程为业务背景，重点训练：

1. 需求分析和领域建模；把“课程、学期、教学班、报名、录取、成绩”区分清楚。
2. Spring MVC、Spring Boot、MyBatis-Plus、MyBatis XML 和 MySQL 的完整开发链路。
3. **带权重的分轮竞争选课**：即时扣除可用权重、轮末排序与随机平局、班级容量、最低开班人数、补选、退课及返还。
4. 事务与并发：重复请求、跨表一致性、相同学生并发报名、人数与余额不超限、轮次结算幂等。
5. 成绩工作流：首次录齐自动开启 72 小时审核、自动整体发布、录入截止、补录授权与已发布成绩更正。
6. 特殊考试：普通补考、获批缓考/缺考、统一批次、冻结名单、最终成绩认定。
7. 复杂 SQL：学分加权 GPA、同入学年级 `RANK()` 排名、只统计正式成绩的班级平均分。
8. 身份认证、资源归属校验、自动化测试、日志排障、Git 和 Docker 交付。

项目首先完成**可演示且可验证的 Java 后端**，而不是为了堆技术而强行加入 Redis、MQ、微服务、Kubernetes 或 AI。

### 1.2 两个交付里程碑

| 里程碑 | 达成条件 | 不等于 |
|---|---|---|
| **A：核心业务可用** | 学籍、课程、学期、教学班、选课/补选/退课、成绩与特殊考试、GPA/排名的核心流程可运行且关键测试通过 | 只把 CRUD 接口跑通 |
| **B：简历级工程交付** | 真实身份权限、自动化与并发测试、必要 SQL 优化、Docker/Compose、README、API 文档、Git 历史、可重复演示 | 只有几张截图或未经验证的性能宣传 |

**首版完成定义**：正常流程、错误流程、边界和重复/并发流程都经验证；另一个开发者可以依文档构建、启动、使用样例数据并运行关键测试。

### 1.3 第一版必须做的功能

| 模块 | 第一版交付范围 |
|---|---|
| 人员与学籍 | 学生、教师、管理员账号；正常在读/休学/退学/已毕业；基础信息和权限 |
| 学期 | 管理员设定第 1 周星期一；连续 20 周；状态按日期自动计算 |
| 课程目录 | 课程学分、专业和年级选课范围、课程停用及历史保留 |
| 开课与排课 | 某课程在某学期多个教学班；教师、教学周、星期、节次、容量和开班门槛 |
| 选课与补选 | 正常选课 3 天、第一轮补选 2 天、第二轮 1 天；权重竞争和随机同分处理 |
| 权重余额 | 初始 100 点、首轮补选统一 +50、报名即时扣除、按规定返还和最终清零；学生可查看余额 |

| GPA 与排名 | 正式最终成绩计算累计学分加权 GPA；同入学年级正常在读学生的个人排名 |
| 质量与交付 | 认证授权、MySQL 集成/并发测试、README/API 文档、Git 和 Docker Compose |

### 1.4 明确不做或不提前做

- 第一版**不实现跨学期重修的专用业务**；设计时不能使用“学生＋课程终身唯一”堵死未来扩展。
- 第一版**不实现课程先修条件校验**；保留课程标识和历史成绩以供后续扩展。
- 不开发复杂的自动排课、教室/监考管理、多个独立教学班共用同一教学活动、完整培养方案、财务或学费模块。
- 不开发复杂的特殊考试批次作废重建、多次补救考试和冻结名单的任意例外补录。
- 不要求完整商业级前端；但**学生可用权重、报名状态、正式成绩和本人排名必须存在可验证的查看方式**。
- Redis、MQ、微服务、Kubernetes、云原生深化、RAG/Agent 是里程碑 B 后的可选扩展，不参与第一版验收。
- 需求未确认的异常审批、保底分配与扩展流程，不能擅自变成第一版功能。

## 二、技术栈、工程范围及学习方式

### 2.1 技术栈

| 领域 | 建议技术 | 作用和约束 |
|---|---|---|
| 语言 | Java 21 | 基础语法、集合、异常、时间、并发与服务层逻辑 |
| 服务端 | Spring Boot + Spring MVC | REST 接口、依赖注入、配置、自动任务 |
| 持久层 | MyBatis-Plus + MyBatis XML | 普通 CRUD 用 MP；关键业务和复杂统计 SQL 用自定义 Mapper/XML |
| 数据库 | MySQL 8.x / InnoDB | 事务、约束、索引、锁、窗口函数、事务隔离 |
| 校验 | Jakarta Bean Validation | 参数校验，但不能取代服务层业务校验 |
| 权限 | Spring Security | 身份、角色与具体资源归属校验 |
| 测试 | JUnit 5、Spring Boot Test、Mockito、真实 MySQL 集成测试 | 交易、选课结算、发布和复杂 SQL 必须有真实数据库证据 |
| 构建 | Maven / Maven Wrapper | 统一构建命令与依赖版本 |
| 接口文档 | OpenAPI/Swagger UI、Apifox 或 Postman | 接口演示、错误案例复现 |
| 版本管理 | Git / GitHub | 每个可验证任务形成清晰提交 |
| 部署 | Docker / Docker Compose | 应用+MySQL 可重复启动与持久化 |

**版本选择**：旧详尽计划书以 **JDK 21 + Spring Boot 4.1.1 + MyBatis-Plus 3.5.17 对应 Starter** 为优先候选；正式建立新项目时，应先独立验证 Spring Boot、MP、Security、Validation、测试和 API 文档 Starter 是否兼容，再锁定版本。若不适合，可统一采用已验证的 Spring Boot 3.x 兼容组合；**不得混用不兼容代际的 Starter**。这里是项目选型任务，不是声称代码环境已经完成验收。

### 2.2 核心工程约定

1. 使用独立开发库和测试库（例如 `course_dev` / `course_test`）；不得在已有练习数据库上直接做集成测试。
2. 使用 profile、环境变量和 `.env.example` 区分环境；不提交真实密码、Cookie、Token、`.env`。
3. Controller 负责协议层，Service 负责业务规则与事务边界，Mapper 负责 SQL；不能把业务校验完全堆在 Controller。
4. API 的 DTO 与 VO 分开，不直接暴露存储 Entity；统一输入校验、业务异常和错误响应。
5. 重要时间边界按统一学校时区；时间判断可测试，避免直接依赖手工调整电脑系统时间。
6. 不因模板或者计划列出就一次性安装所有中间件；用到时再加。
7. 必须留真实测试证据；没有跑通的功能不能勾选完成。

### 2.3 学习与 Agent 使用原则

- 执行方式坚持：**讲解 → 示例 → 小任务 → 我自己操作 → 检查纠错 → 下一步**；每次集中一个知识点或一个小功能。
- 需求整合、重复格式整理、测试报告排版等可交给 AI 协助。
- **数据库关系建模、选课权重/录取结算、Spring 事务、复杂 SQL 和并发排障由我主导实践**，AI 负责分析方案、代码审查、提出测试、定位问题，不默认整块代写。
- 单表 CRUD 不机械重复训练；教师等模块复用已掌握的公共模式。
- 每次任务先明确“这一步由谁写、如何验证、保留什么证据”，而不是将可学习的全部实践自动外包。
- 如果对某个功能的掌握尚不够，可以暂停增加功能，先做一次最小可复现练习。

### 2.4 本地开发环境的逐项验收

| 检查点 | 实际操作 | 验收证据 |
|---|---|---|
| JDK | 检查 `java -version` 和 IDEA 项目 SDK | 两者使用兼容的 Java 版本 |
| Maven | 检查 `mvn -version` 或 `./mvnw -v` | 使用明确的 JDK 和 Maven 版本 |
| MySQL | 检查版本、服务状态和开发/测试库 | 能在测试库创建表并执行事务 |
| Spring Boot | 启动最小服务，检查端口与启动日志 | 服务正常启动，不依赖本机硬编码路径 |
| 数据访问 | 用独立测试库跑一次 Mapper 查询 | 能排除驱动、URL、账户和映射错误 |
| Git | `git status`、一次真实提交、`git log` | 有可检查的版本历史 |
| Docker | 完成基本版本检查，不强制立即容器化 | 阶段 7 前明确本机环境状况 |
| 配置安全 | 检查 `.gitignore`、profile 与环境变量 | 没有提交密码和个人隐私数据 |

**先建立最小可运行环境，再引入复杂业务。** 项目依赖应通过 Maven 统一管理，不能直接复制历史练习项目的全部依赖而不验证版本兼容。

### 2.5 时间与测试时钟规范

本系统有许多必须严格区分的时间：学期第 1 周星期一、选课三轮起止、课程首次实际上课日、普通成绩截止、72 小时审核、授权到期。

- 先选定一个**学校统一时区**；全部业务判断都显式使用它，不能在某个接口使用操作系统本地时间、另一个接口使用数据库默认时区。
- 统一约定时间窗口的边界处理，例如采用开始包含、结束不包含的区间；具体小时与精度需要在设计文档中写清。
- 自动发布和授权过期测试必须使用可控时钟或可控调度入口；**不应为了测试真实等待 72 小时**。
- 轮次关闭与结算是不同动作：截止时间到了，可能还需要执行一次可重试的结算任务。
- 业务日志应能定位同一学期、轮次、教学班、申请与操作人；不记录学生密码、令牌或未授权的成绩明细。

## 三、最终生效业务基线摘要（不代替正式需求文档）

> 本节帮助开发阶段快速定位核心约束。任何未展开的例外、详细定义和最终解释应回查 `docs/需求与业务规则.md`。

### 3.1 人员、课程、学期

1. 学生学籍有**正常在读、休学、退学、已毕业**四类；非正常在读者仍可看本人历史正式成绩，但不能正常选课/补选/退课。
2. 账号由管理员创建；学号、工号、课程编号等身份标识需要保证唯一。
3. 学期从管理员配置的第 1 周**星期一**开始，连续 **20 周**：1～18 周教学，19～20 周考试；学期状态按学校时区的日期自动计算。
4. 第一个教学班被创建后，学期起始日不可再普通修改；不能通过删除记录绕开限制。
5. 课程具备学分、专业/入学年级选课范围；不设限制的课程可面向所有符合资格学生。课程被用于创建班级后，学分冻结。
6. 课程**停用**表示以后不再新开该课，不删除当前班级、历史成绩与累计 GPA 贡献。
7. 授课教师不能承担实际上课时间重叠的独立班级；学生也不能报名或录取时间冲突的课程。
8. 每个上课片段可指定不连续教学周集合，冲突必须同时满足**教学周相交、星期相同、节次区间相交**。
9. 教学班最大容量为**正偶数**，最低开班人数固定为最大容量的 **1/2**；更改容量必须保持正偶数且不得低于当前有效人数。
10. 选课开放后课表冻结；管理员可在重新校验教师冲突并记录审计后更换授课教师。

### 3.2 分轮选课与可见权重

1. 正常选课：学期开始日前 **14 天开启**，持续 **3 天**；随后第一轮补选 **2 天**、第二轮补选 **1 天**，不额外开常规第三轮。
2. 每位符合资格学生起始 **100 点权重**；**第一轮补选开始时全体符合资格学生统一增加 50 点**，每学期只发一次。
3. 学生选择课程的具体教学班并分配投入点数；**报名提交成功立即扣除当前可用余额**，学生可以看到实时剩余点数。
4. 本轮结束前可撤回未结算的报名并释放该笔权重。业务校验未通过不扣；不允许余额负数或重复扣返。
5. 同一学期同一课程只允许一个有效选课/报名目标；已有课程和未撤销报名都参与学生上课时间冲突校验，不能同时报名冲突课程。
6. 本轮截止时按**剩余容量**结算：报名量未超过名额则符合资格者取得名额；超额时按**投入权重从高到低**录取，同权重竞争剩余名额时由服务端随机决定。
7. 前一轮已确认的名额不被后一轮高权重报名者替换；本轮竞争落选的投入权重返还。
8. 实际有效录取人数达到最低门槛的班级可确认开班；不足则保持待开班并等待后续补选。**已确认开班后合法退课降到最低人数以下，也不再自动取消**。
9. 第二轮补选最终结算后仍不足人数的待开班班级取消，取消相应选课名额并按约定返还权重；系统不保证每人都能选上。
10. 全部轮次结算及必要返还完成后**清零可用权重**；此后不能再用本学期权重常规选课。
11. 普通退课按该班级**首次实际上课日起 7 天内**的统一规则处理；任何有效成绩一开始录入，整班普通退课立即锁定。
12. 在权重仍有效的阶段合法退课，返还该笔已扣权重并释放容量；**最终清零后**仍可合法退课，但不再恢复可用权重。始终保留退课审计。

### 3.3 普通成绩、截止、迟交与已发布更正

1. 成绩区分**合法数值 0～100、缺考、缓考、未录入**；0 分和“未录入”不得混淆。
2. 已记录的合法缺考、缓考可计为“已录入”以触发审核，不要求所有人先得到数值成绩。
3. 同一教学班**首次全部录齐**后自动开启 **72 小时审核**；审核期间教师可合法修改已录结果，但不得清空以解除完整性或重置计时。
4. 72 小时结束系统自动按教学班**整体正式发布**；未正式发布的结果学生不可见；自动任务必须可安全重试。
5. 学期普通录分截止默认是**第 20 周星期日结束后 14 天**，管理员可在合法区间内配置，最早第 20 周星期日、最晚其后 30 天，截止日含完整当天。
6. 管理员只能在原普通截止尚未过期时修改；到期之后按**具体教学班的迟交录入授权**处理，须注明期限、原因并审计，授权不可重叠。
7. 72 小时审核一旦合法开启，普通录分截止到达不会撤销该审核或阻止到期发布。
8. 正式成绩发布后不得普通改分。教师须申请、管理员批准**指定学生、指定目标成绩、有限期限**，教师在授权内执行时新成绩**立即生效**，不再二次审核。
9. 申请待审或已批准但未执行，学生仍看旧正式结果。同一学生×教学班不能并行存在两条活动更正申请。
10. 教师可撤回自己待审核申请；批准授权到期未执行自动失效，均保存历史并允许符合规则的后续申请。

### 3.4 缺考、缓考和课程特殊考试

1. 全部课程统一 **60 分及格**。
2. 正式不及格学生自动具有普通补考资格；**未获批准原缺考**按原成绩 **0 分**，同样自动取得普通补考资格。
3. 获批缺考、缓考学生取得特殊考试资格；在正式数值结果生效前，该课程不进入 GPA。
4. 每**学期×课程**最多一个特殊考试批次；跨教学班集中处理，结果归回原选课关系。
5. 学生名单按资格自动汇总；管理员在考试前**确认冻结名单**，冻结前新资格应纳入，冻结后不得按普通流程添加/删除；冻结前不可录特殊考试分数。
6. 管理员可指定**一名或多名特殊考试负责教师**，在批次正式生效前有理由、有审计地更换负责人；该权限不等同于其他普通班级的改分权限。
7. 冻结批次全部考试结果录齐（包括再次缺考记数值 0）后自动开启 72 小时审核，届满批次整体正式生效；原教学班不再重复审核。
8. **普通补考**：考试原始分 ≥60，课程最终**统一 60 分、绩点 1.0**；原始分 <60 或再次缺考则最终 0 分、绩点 0。
9. **获批缺考/缓考考试**：原始分 ≥60，最终课程成绩为原始分；原始分 <60 或再次缺考则最终 0 分。
10. 历史考试原始分、资格来源和最终认定分数均保留。学生普通成绩界面只展示**当前正式最终认定结果**，不会提前展示审核中成绩或内部审计。

### 3.5 累计 GPA、排名与统计

1. 对具有正式数值成绩的课程：成绩 ≥60 的单科绩点为 `(最终认定成绩 - 50) / 10`；成绩 <60 绩点为 **0**，但该课程学分仍计入 GPA 分母。
2. 累计 GPA：`Σ(参与课程学分 × 单科绩点) / Σ(参与课程学分)`，采用**历学期累计**；无正式数值成绩的批准缓考/缺考课程暂不纳入分子和分母。
3. 课程没有任何有效正式数值成绩时 GPA 显示“暂无数据”，不作 0。
4. 个人名次只在**同一入学年级**内部比较。仅**正常在读且至少有一门正式数值成绩课程**者参排；不设最低学分门槛。
5. 排序先 GPA **降序**；若 GPA 相同，**当前没有未通过课程的学生优先**；两个条件均相同则并列，采用**竞赛排名 `RANK()`（1、1、3、4）**。
6. 历史挂科已经补考通过后不算“当前挂科”，但普通补考通过仍按最终 60、绩点 1.0 计算。
7. 学生**只能查看本人的同年级名次**，不能查看完整榜单或其他学生的成绩、GPA、排名。
8. 教学班平均分只统计该班当前**正式有效的数值最终认定成绩**：0 分参与；批准缓考等无数值结果暂不参与；没有数值结果显示“暂无数据”。
9. 教师可看**本人授课教学班统计**，管理员可看全部合法统计范围；更正或特殊考试正式生效后更新相关指标。

### 3.6 四条最容易搞混的完整业务链

**链路 A：成功报名但暂未开班**

```text
学生可用权重 100
  → 报名某教学班，投入 35，余额立即变 65
  → 本轮结束，报名量未超剩余容量，取得暂定名额
  → 班级实际录取人数尚未达到最低开班人数
  → 维持待开班，后续补选继续接纳新报名
  → 满足最低人数后确认开班
```

**关键**：报名、取得名额、确认班级开班是不同业务节点。正式数据状态可以由设计阶段选择实现方式，但查询必须让学生分得清当前属于哪一节点。

**链路 B：超额竞争落选**

```text
容量 40；本轮剩余名额 3
  → 5 人有效报名，分配权重分别为 50、40、30、30、10
  → 截止后按本轮剩余容量竞争
  → 50、40 优先获得名额，两个 30 对最后 1 个名额随机竞争
  → 另外两人落选，返还各自原投入
  → 重复执行结算不得重新抽取
```

**关键**：随机只是同权重且名额不足时的决胜规则，不可以随机忽略较高权重。示例仅说明规则，不指定数据库算法。

**链路 C：退课与权重清零**

```text
学生本学期已获得一门课程名额，原投入 40
  → 第二轮补选完成全部结算之前合法退课
  → 名额释放 + 返还可用权重 40 + 保留退课审计

另一次合法退课发生在全部补选结算且权重已清零之后
  → 名额释放 + 保留退课审计
  → 不重新增加该学期可用权重
```

**关键**：退课合法性仍取决于首次实际上课日起 7 天内及班级成绩录入状态；权重清零只是决定退课是否返还**可用余额**，不能变成禁止合法退课的理由。

**链路 D：正式成绩与特殊考试**

```text
教师录入普通考试成绩/合法缺考或缓考结果
  → 教学班首次所有结果录齐 → 自动开始 72 小时审核
  → 审核到期后该班统一正式生效
  → 不及格/合法特殊状态进入相应考试资格处理
  → 同学期同课程统一特殊考试批次
  → 考前冻结名单 → 批次结果录齐 → 再审核 72 小时
  → 批次统一正式生效，更新原课程最终成绩
  → 班级平均分、学生 GPA 与个人名次反映当前生效结果
```

**关键**：学生查看的是**当前正式最终认定结果**，而不是老师刚保存的草稿分，也不是审核中的特殊考试原始分。

### 3.7 权重录取与最低开班人数的典型边界

| 情境 | 正确的业务解释 | 开发时不能犯的错误 |
|---|---|---|
| 40 人容量，有 16 人报名并在轮末获得名额 | 待开班，还需补选达到 20 人 | 因报名未达 20 立即删除全部申请 |
| 40 人容量，50 人申请 | 最多录 40 人，按权重排 | 将 50 个报名记录都算成有效已录取人数 |
| 已确认开班 20 人，正常退课后 18 人 | 保持确认开班 | 把班级自动退回待开班 |
| 同一学生报名两个不同课程但上课时间冲突 | 第二笔提交时拒绝且不扣权重 | 等两笔都录取后再随意取消其中一门 |
| 本轮已录取且下一轮有人投入更高权重 | 已有录取不被挤出 | 将所有轮次混在一起重新排序 |
| 最后一轮结束待开班仍不足人数 | 班级取消、名额撤销、必要返还后清零 | 清零后才尝试返权重，导致账目无法核对 |
| 成绩开始录入 | 整班普通退课锁定 | 只禁止已录入分数的那个学生退课 |
| 客户端连续点击提交或撤回 | 操作至多产生一次有效变更 | 重复扣 40、重复返 40 或余额负数 |

## 四、系统核心不变量与技术困难

> 本节属于“必须实现的结果”，不是直接指定唯一的 SQL 语句或表结构。每个不变量都必须有相应测试。

| 编号 | 不变量/约束 | 失败例子 |
|---|---|---|
| INV-01 | 容量为正偶数，`0 ≤ 有效名额人数 ≤ 最大容量` | 并发结算后 40 人容量录取 41 人 |
| INV-02 | 最低开班人数 = 当前合法容量的 1/2，确认开班后不因正常退课取消 | 40 人容量 19 人却标记已确认开班 |
| INV-03 | 学生同学期同课程最多一条有效报名/有效录取目标 | 同时报名同一课程 A、B 班 |
| INV-04 | 学生有效报名和已录取课程之间无实际课表冲突 | 教学周/星期/节次实际相交仍被允许 |
| INV-05 | 同一教师的独立教学班不发生实际授课冲突 | 仅看星期节次，漏检周次造成误判 |
| INV-06 | 可用权重始终 ≥0；每笔提交、撤回、返还与发放只生效一次 | 余额 60 同时两笔 50 都被扣成功 |
| INV-07 | 轮末结算只对本轮有效报名；结果不可因重跑改变 | 重跑随机抽取导致录取者变了 |
| INV-08 | 下一轮不能抢占上一轮已录取名额 | 新申请权重更高就踢出老录取学生 |
| INV-09 | 未达最低门槛的班级在最终取消后不能仍保留有效授课/选课状态 | 退还权重后仍显示学生已选 |
| INV-10 | 选退课与权重变化要一致，最终清零后的合法退课不恢复余额 | 退课成功但人数未减；重复返还 |
| INV-11 | 审核首次录齐触发且不可被重复重启；正式发布统一生效 | 72 小时审核期被教师再次改分重置 |
| INV-12 | 学生只能看到正式生效的当前最终成绩 | 特殊考试审核中看到了新分数 |
| INV-13 | 已发布成绩只能按精准授权更正；特殊考试按批次整体生效 | 老成绩被普通接口直接覆盖 |
| INV-14 | GPA 和排名依据正式数值最终成绩与学籍资格 | 未发布成绩提前影响排名 |
| INV-15 | 业务并发、自动任务重试、重复 API 调用不产生重复扣除、重复生效或部分更新 | 两次任务给同一学生发两次 +50 |

**首版最值得亲自实现并讲清的技术问题**：

- 申请提交时的**权重余额并发扣除**与单笔报名记录的原子性。
- 同学生同学期同课程的报名唯一性、教学周集合冲突和并发写入。
- **轮末批量排名录取**、同权重随机、公平的剩余容量分配、重复结算幂等。
- **待开班 → 确认开班 / 最终取消**、人数变更与已扣权重返还的一致性。
- 普通退课时人数变更、权重返还或清零后不返的时间边界。
- **72 小时到期自动发布**、跨进程/重复触发的幂等、已发布更正和特殊考试批次整体生效。
- GPA 的学分加权与分母判断、`RANK()` 两级排序、不泄露其他学生的数据。

## 五、数据库设计路线与数据模型（第一版不固定表数量）

### 5.1 为什么要重新设计旧版八张表

原先的八张核心表草案用于简单先到先得选课、普通成绩发布；**现在不能直接照搬**。权重报名/结算、每轮补选、退课审计、学籍状态、复杂成绩授权、特殊考试和成绩历史均需要独立的业务事实与关系。

本计划只给**概念模型和设计检查表**，不提前替代 `docs/数据库设计.md` 的最终 ER、DDL 和索引设计；实际表数量以规范化、查询与事务正确性为依据，不作为项目成绩指标。

### 5.2 建议先识别的实体或业务事实

| 领域 | 应考虑的实体/事实 | 关键问题 |
|---|---|---|
| 身份 | 账号、学生、教师、学籍状态 | 账号与业务主体如何绑定？四类学籍如何影响权限？ |
| 课程 | 课程目录、专业、入学年级、选课范围 | 学分何时冻结？停用课程能否影响旧班？ |
| 学期 | 学期、轮次/选课窗口 | 正常选课+两轮补选如何表示和限制时间？ |
| 开课 | 教学班、教学周及节次安排、授课教师 | 容量、最低人数、开班结果与实际学生数如何保持一致？ |
| 选课 | 报名申请、轮次结算、录取关系、退课历史 | 报名不是录取；失败申请是否需要保留？ |
| 权重 | 学期权重余额、投入记录、权重变更流水 | 提交即时扣、失败返、退课返、清零能否可追溯？ |
| 成绩 | 原选课成绩事实、当前正式结果、班级审核与发布 | 特殊状态能否算录齐？如何防止审核重置？ |
| 期限与更正 | 学期录入截止、班级迟交授权、成绩更正申请与审批/执行 | 普通录入与已发布更正如何分开？ |
| 特殊考试 | 学期×课程批次、参加名单、负责教师、考试原始结果 | 一学期一课程一批次、名单冻结、整体生效如何实现？ |
| 查询与统计 | GPA 与排名、班级平均分 | 直接 SQL 计算还是缓存派生值？缓存如何失效？ |
| 审计 | 关键状态变化和修改历史 | 何时产生操作记录？哪种记录绝不能物理删除？ |

上表是**概念设计候选，不是强制一行一表**，尤其不应为了达到某个固定表数机械拆表。

### 5.3 关系和约束检查表

- [ ] 画出“课程 → 学期教学班 → 上课片段 → 报名 → 有效录取 → 最终课程成绩”的主关系。
- [ ] 识别报名与录取之间的**一对多/状态变化**；失败、撤销、退课、最终取消不应留下非法有效关系。
- [ ] 设计“学生 × 学期权重账户”与“每笔报名投入”的关联；余额与流水能相互核对。
- [ ] 能识别三个轮次，避免跨轮次重用结算结果；有清晰轮次结算状态。
- [ ] 班级容量必须为正偶数；最小人数 = 容量 / 2；容量不得小于当前合法录取人数。
- [ ] 正常课程学分冻结，历史课程成绩依旧有效。
- [ ] 教学周采用明确可比较的集合模型；时间冲突可落到 SQL 或可测试服务逻辑。
- [ ] 不在学生+课程跨**全部学期**上添加终身唯一约束。
- [ ] 正式成绩原始分、补考原始分、最终认定分及更正前后历史不可混为一列而失去可追溯性。
- [ ] 普通成绩发布与特殊考试批次审核分别有状态和首次开始时间，不共用一套模糊字段。
- [ ] 同一学期同课程最多一个特殊考试批次的唯一性需要有明确约束。
- [ ] 需要为审计与统计查询考虑外键、NULL、索引与删除/停用策略。

### 5.4 事务边界与数据一致性设计作业

应分别画出以下事务或自动任务的输入、锁定对象、关键操作、失败回滚及幂等条件：

1. 报名成功：验证身份、窗口、选课范围、同课/时间冲突、余额，**扣权重＋创建报名**同成功同失败。
2. 撤回报名：撤回报名＋返还对应投入；重复撤回无二次返还。
3. 轮次结算：关闭该轮报名 → 对各班读取合法有效报名 → 竞争排序/随机 → 录取及落选返还 → 更新容量计数和班级状态；重复任务不可改结果。
4. 退课：校验退课时限与录分状态 → 解除有效选课 → 释放容量 → 依权重有效期选择是否返还 → 审计。
5. 开班终局：确定班级达到最低门槛，或最后一轮后取消待开班班级，并解除名额及返还权重。
6. 首次录齐成绩：最后一份成绩/特殊状态录入时原子开启 72 小时审核，后续改分不重启。
7. 审核到期发布：自动任务在条件满足时对教学班全部成绩**同批正式生效**。
8. 迟交授权与已发布更正：严格区分针对未录完的补录与针对已经正式生效成绩的授权更正。
9. 特殊考试批次：名单冻结、批次成绩录齐、72 小时到期后跨原班**原子更新最终有效结果**。
10. 正式成绩变更：班级统计、GPA 与同年级排名如何反映最新状态，避免更新瞬间暴露部分生效数据。

**实现策略不预先指定唯一答案**。可以考虑 InnoDB 事务、行锁、唯一约束、条件更新、批量结算与幂等键等，但每种选择必须用真实数据库测试证明正确；不能只写一段看似合理的 SQL 作为证据。

### 5.5 SQL、索引与精度

- 首先保证关联正确，再逐步使用 `JOIN`、`GROUP BY`、`HAVING`、`EXISTS`、窗口函数 `RANK()` 与动态 SQL。
- 统计时明确“当前正式有效成绩”与“历史原始成绩”不能混用；0 分参与数值平均与 GPA 学分分母，无数值批准缓考暂时排除。
- 将 **GPA 计算精度**与“页面显示小数位”分开，不能以展示舍入值决定名次。
- 金额式准确数值采用合适的定点类型方案；权重仅为点数，不默认为可以投入小数或 0，合法粒度需在设计评审时明确。
- 每个索引都要说明它解决了什么查询/约束，使用 `EXPLAIN` 观察真实 SQL；不盲目为所有列建索引。

### 5.6 数据库设计评审的交付规格

阶段 0 的数据库设计不是直接得到一个 `schema.sql` 就算结束，至少应能解释以下四类内容。

**A. 实体与关系**

- 每个概念实体为何独立存在；是否有稳定身份；与其他实体是一对一、一对多还是多对多。
- 课程目录与某学期教学班必须分开；报名申请与已获得的名额必须可区分。
- 当前正式成绩、普通原始结果、特殊考试原始结果和授权更正历史必须可追溯。
- 学生学期权重余额与每次权重投入/返还之间要能核对，不能只保存一个会变化的总数而没有来源。

**B. 生命周期与约束**

- 每张业务表的可变字段、创建/结束条件、历史记录保留策略。
- 主键、外键、唯一约束、CHECK、NULL 的业务含义；哪些条件由数据库保证，哪些依赖事务内服务层检查。
- 每个状态的合法转换；不可逆状态以及管理员可修改的边界。
- 严格区分学生的“报名已提交、已撤回、竞争落选、取得名额、退课”和班级的“待开班、确认开班、取消”。

**C. 查询与索引**

- 查询学生本学期当前全部有效报名和已录取课程。
- 查询某教学班本轮有效报名，按权重降序并处理同权重集合。
- 查询教师教学周/星期/节次是否冲突。
- 查询某教学班全部普通成绩是否首次录齐，以及 72 小时到期待发布对象。
- 查询同学期课程唯一特殊考试批次、资格名单和负责人。
- 计算本人累计 GPA、班级平均分以及同入学年级 `RANK()` 名次。
- 对每个候选索引解释：所服务的查询、可能的写入成本、是否需要复合索引。

**D. 事务与恢复**

- 列出每个事务被修改的**全部**记录，而不是只写“加 `@Transactional`”。
- 定义更新顺序和必要并发保护：重复报名、余额同时被多个请求扣除、结算与容量调整、退课与结算竞争。
- 自动任务的开始条件、断点恢复与幂等依据。
- 事务失败后的数据库状态必须仍满足核心不变量；模拟一次关键步骤失败后验证回滚。

**阶段 0 审查通过标准**：你能解释表关系和约束，能够手写三条核心事务的操作顺序，并用少量样例数据证明模型可以表达成功、落选、待开班、取消、退课、最终成绩与历史审计。

### 5.7 数据库设计中需要避免的反模式

| 常见反模式 | 问题 | 更稳妥的思路 |
|---|---|---|
| 只有 `enrollment` 一张表，报名、录取、退课、成绩都塞进去 | 难以区分竞选失败与有效名额，历史缺失 | 区分业务事实/状态，必要时拆开存储 |
| 权重只有一个 `balance` 字段，没有申请投入明细 | 无法准确返还哪一笔，也难以审计 | 让每次权重变化关联来源操作 |
| 靠查到的当前人数决定是否有空位，之后再普通 `INSERT` | 并发时可能超员 | 设计原子占位或受控结算方案 |
| 用 `double` 存 GPA、以显示的两位小数比较并列 | 浮点误差和错误并列 | 定点计算与明确的展示精度 |
| 数值 `0`、未录入、缺考、缓考全靠同一个特殊数字表示 | 成绩计算、审核和补考资格会错误 | 使用明确状态及原始/最终结果 |
| 删除旧课程、历史修读记录或考试原始分 | 无法复算 GPA 和追溯更正 | 停用与历史保留 |
| 同一个学生一次可以存在多笔互相冲突的活动报名 | 结算时还要做复杂自动选一 | 按已确认规则在报名时拒绝冲突 |
| 认为定时任务启动了就必然只执行一次 | 重试可能重复发权重/发布/改成绩 | 状态条件、唯一性和幂等验证 |

### 6.1 分层架构


### 6.3 角色与资源归属（摘要）

| 能力 | 学生 | 教师 | 管理员 |
|---|---|---|---|
| 申请、撤销报名、退课 | **仅正常在读且仅本人** | 不可 | 不得普通绕过规则 |
| 查看权重余额、课表和本人正式成绩 | 本人 | 非学生视图 | 按管理职责 |
| 修改学籍、课程、班级配置 | 不可 | 不可 | 可，且不得绕业务约束 |
| 普通教学班录分/审核期调整 | 不可 | **仅本人负责班级** | 不直接绕开教师授权流程 |
| 更正已发布成绩 | 不可 | 提交申请、授权后执行 | 批准指定对象、分数和期限 |
| 特殊考试成绩 | 不可 | 仅明确授权的批次负责人 | 负责批次管理和授权 |
| 班级成绩统计 | 不看他人明细 | 仅本人授课班级 | 全部合法范围 |
| 同年级名次 | **仅查看自己的名次** | 不提供学生榜单 | 按管理权限处理，不开放学生榜单 |

学生身份必须从认证上下文确认，而不是无条件相信客户端提交的 `studentId`。教师必须校验某班级确属自己授课或自己在特殊考试中具有授权；**拥有 TEACHER 角色不等于能修改任意班级成绩**。

### 6.4 API/错误处理基本规范

- 常见分类：参数非法（400）、未认证（401）、无权访问（403）、资源不存在（404）、规则冲突（409）、内部错误（500）。正式错误码由 API 设计阶段确定。
- 示例规则冲突：余额不足、报名窗口关闭、同课重复、实际课表冲突、超额录取、班级待开/取消、普通退课截止、成绩审核与发布状态冲突。
- 请求必须定义幂等/重复操作语义：撤回、退课、阶段结算、+50 发放、成绩发布和更正执行尤其重要。
- 不能在错误响应中暴露 SQL 堆栈、密码、令牌、其他学生的隐私数据。
- 为自动到期任务配置可重复执行和失败恢复策略，不把“定时任务只会执行一次”当作事实。

### 6.5 建议在 API 设计阶段明确的请求语义

> 以下是设计作业提示，不是强行固定 URL、请求字段或者数据库模型。正式接口以 `docs/API接口设计.md` 审查稿为准。

| 操作 | 正常成功应表达什么 | 最容易遗漏的失败或重复语义 |
|---|---|---|
| 提交报名 | “报名有效、已扣相应权重、等待轮次结算” | 不能假装已经录取；余额不足时不能部分扣除 |
| 撤回报名 | 报名状态失效、权重返还、余额变化可查 | 截止后不得当作撤回；重复点击不二次返还 |
| 查询报名结果 | 区分等待结算、落选、暂定名额、正式有效选课 | 不能把待开班直接写成“确定会正常授课” |
| 执行轮次结算 | 能确认本轮结算结果和幂等状态 | 任务失败/重跑不能再次随机或重复扣返 |
| 合法退课 | 释放名额、更新课表、保存审计 | 清零前后权重返还不同；成绩已开始录入不能退 |
| 教师录成绩 | 结果草稿成功保存并返回审核状态 | 特殊状态、数值 0、未录入要明确区分 |
| 审核到期发布 | 该班级统一正式生效 | 任务重复运行不二次生效；学生不能提前查到 |
| 申请成绩更正 | 进入待审核，不改变学生正式成绩 | 并发活动申请冲突；审批不等于执行 |
| 特殊考试录成绩 | 更新批次草稿结果，不提前覆盖正式分 | 名单未冻结或非负责人无权操作 |
| 查询 GPA/名次 | 只返回当前登录学生的有效数值结果 | 不允许通过修改请求参数获取他人名次 |

**返回错误时应保留一致状态**。例如某次报名因重复课程失败，学生余额必须不变；成绩更正因为授权过期失败，当前正式成绩不得被部分修改。

### 6.6 权限模型的四层检查

所有重要操作至少分清：

1. **身份是否有效**：请求是否已认证，账号是否可用。
2. **角色是否允许该类操作**：学生、教师、管理员分别做什么。
3. **资源是否属于当前主体**：本人报名、教师所授教学班、批次负责人授权。
4. **当前业务状态和窗口是否允许**：正常在读、报名轮次、退课截止、审核期、授权期限。

对 403 与 409 的区分，在接口设计时明确：**权限不够**与**有权限但业务当前不允许**不是同一种失败。错误消息不应泄露其他学生的身份和成绩。

### 阶段 3｜权重报名、分轮录取、开班、补选和退课（第一核心）

**目标**：完成项目最具特色的业务模块，并真正掌握事务、锁、状态和并发。

**实施策略：先正确、再并发、最后自动化；分 6 个可独立验收的子模块。**

**3-A｜选课资格、报名与余额**

1. 识别每学期正常 3 天、首轮补选 2 天、二轮补选 1 天；学生可查询当前轮次和权重余额。
2. 初始化每学期 100 点，第一轮开始时对全体资格学生只发放一次 50 点。
3. 提交报名时校验正常在读、课程范围、教学班开放、课表周次交集、同学期同课程、权重余额。
4. **报名记录＋即时扣除权重**放在原子事务中；余额不足/被拒不扣权重。
5. 截止前撤回未结算报名，返还该笔已扣权重；重复撤回不得多加。

**3-B｜单轮结算与竞争名额**

1. 轮末冻结本轮有效报名，排除已撤回和非法申请。
2. 按班级剩余名额结算，未超额则全部获得名额，超额按**投入权重降序**确定录取者。
3. 同权重且剩余容量不足时由服务端随机，结算结果可追溯，**任务重试不得重新抽签**。
4. 本轮落选返还投入的权重；已录取者的原投入继续扣除。
5. 上一轮已获得的名额不能被下一轮申请者挤掉；以剩余容量承接后续补选。

**3-C｜最低开班人数与两轮补选**

1. 按实际有效录取人数判断 `最低开班人数 = 最大容量 / 2`。
2. 满足最低人数的班级确认开班；不够的先待开班，允许后续轮次继续争取学生。
3. 已确认开班后，之后合法退课导致人数不足也不自动撤销。
4. 第二轮补选最后结算后，不够人数的班级取消；撤销名额并处理相应权重返还。
5. 全部返还完成后清零本学期可用权重；不得再打开常规第三轮。

**3-D｜退课与权重生命周期**

1. 普通退课时限按班级**首次实际上课日起 7 天内**计算，不与正常报名截止混淆。
2. 班级任何有效成绩开始录入后，整个班级的普通退课锁定。
3. 退课合法则释放班级名额，保留独立审计历史；重复退课不能再减人数。
4. 全部选课轮次**最终清零之前**合法退课返还该笔权重；清零之后退课不再恢复可用余额。
5. 退课与名额/账目变更同成败，不可部分成功。

**3-E｜数据库事务与并发实验**

关键场景至少覆盖：

- [ ] 同一学生并发提交两笔总额超过余额的报名，余额不为负。
- [ ] 同一学生并发报名同课程不同班级，只能保留一个有效目标。
- [ ] 同一学生并发报名实际时间冲突课程，不能同时有效。
- [ ] 多学生超额竞争，轮末录取数量不超过剩余容量。
- [ ] 同权重随机结果在重复结算、失败重试后保持不变。
- [ ] 重复补发 +50、重复撤回、重复退课、重复取消，不重复扣还权重。
- [ ] 容量调整与结算并发后仍不超过容量，且容量为偶数。
- [ ] 补选结束、班级最终取消、权重清零遵守正确结算顺序。

真实 MySQL 并发测试可使用 `CountDownLatch` 和多个事务；子线程不能错误复用同一测试事务，测试线程数要与连接池大小匹配。**一次偶然通过不是并发正确性的证据**。

**3-F｜复盘与交付**

- [ ] 写出 `docs/选课事务与并发.md`（名称可按实际目录调整），包括状态图、提交/结算/退课事务、失败回滚和锁顺序。
- [ ] 至少说明两种选课并发故障的根因与修复。
- [ ] 记录覆盖正常、失败、撤销、超额、同权重、待开班、确认开班、最终取消的测试。
- [ ] 亲手用日志/断点查清一次“余额被重复扣除或返还”的可控失败案例。

**阶段 3 硬验收**：可重复执行三轮选课，余额实时正确、最大容量绝不突破、权重排序/随机一致、最小人数开班规则正确、退课与清零边界正确；核心并发测试通过。**不得用简单的先到先得模型代替权重录取。**

| 3.1 | 单笔报名即时扣权重 | 单线程正确、余额不足回滚 | 先做复杂结算 |
| 3.2 | 撤销报名正确返还 | 重复撤销、截止时刻、并发撤销 | 先做 UI 美化 |

**一个可复现的竞争测试数据集**：

```text
教学班：Java A
最大容量：40；最低开班人数：20
前一轮已获得有效名额：37
本轮剩余名额：3
本轮候选权重：50、40、30、30、10
预期：50、40 必录；两个 30 随机选 1；10 落选
结果核查：本轮新增录取恰为 3，班级合计不超过 40
```

上面只是**示例数据**，不意味着真实系统只能有这五名竞争者。录取算法开发时要让它适用于任意合法容量与申请人数。

**幂等与并发的自测重点**：

- 在同一结算任务第一次完成后，再重复调用一次，结果集合、权重余额和退还次数完全不变。
- 模拟结算中途发生异常，必须能说明事务回滚后哪些数据仍保持不变，或如何根据已记录状态安全恢复。
- 对一个学生同时发起两次报名，证明不能重复使用同一余额；对同一课程两个班级并发报名，证明最多一条有效目标。
- 管理员缩容与某轮结算同时发生时，容量仍为正偶数且不能超额。
- 待开班班级最终取消时，所有相关学生名额和权重历史一致，不留“取消了班级但学生课表还在”的脏状态。

**实践反馈要求**：本阶段至少亲自写两次“错误实现 → 失败证据 → 修复 → 回归测试”的复盘，而不是只提交 AI 直接生成的正确代码。

### 阶段 4｜成绩、特殊考试、GPA 与统计（第二核心）

**目标**：从考试事实到正式成绩，再到统计与个人排名的完整闭环。

**4-A｜普通成绩录入与 72 小时审核**

1. 区分数值 0～100、未录入、批准缓考、批准/未批准缺考等合法事实。
2. 教师管理本人班级；缺考/缓考等已记录状态应正确计入“首次录齐”。
3. 最后一名学生首次被录入合法结果时，自动设置首次录齐时刻并开启 72 小时审核。
4. 审核期内教师可以修改但不能清空已录结果，也不能因修改重启计时。
5. 到期自动整班发布；学生不能提前从其他接口或统计旁路看见未正式结果。

**4-B｜普通录分截止与迟交授权**

1. 学期成绩普通截止默认为第 20 周星期日结束后的 14 天，合法区间为该星期日至其后 30 天（含截止日整天）。
2. 截止前管理员可有理由修改，过期后不再通过直接延长普通截止处理。
3. 对具体班级提供合法迟交录入授权，含起止时间、理由、审计且不允许重叠。
4. 已合法开始的 72 小时审核不因普通截止到达而停掉。

**4-C｜已发布成绩更正**

1. 教师发起更正申请，管理员精准批准指定学生、目标成绩和期限。
2. 教师在批准有效期内执行，**执行写入成功时立即生效**，无需第二轮审核。
3. 同一学生×班级同时至多一条待审批/已批未执行活动申请；待审可撤回，超期自动失效。
4. 学生在更正执行前只能看旧正式分数；保留审批和改分历史。

**4-D｜特殊考试批次**

1. 正式原课程不及格自动取得普通补考资格；未经批准缺考按原成绩 0 分参加普通补考。
2. 获批缺考/缓考另有特殊考试资格，必须保留类别区别。
3. 同学期同课程只有一个特殊考试批次，自动跨班汇总合资格学生；考试前管理员冻结名单。
4. 管理员指定批次负责教师；冻结后才可录入批次成绩；允许必要的负责人变更和审计。
5. 冻结名单全部录齐后 72 小时审核、到期批次整体正式生效；结果回到原班，不重新触发原班审核。
6. 普通补考通过最终课程 60 分、绩点 1.0；获批特殊考试通过使用实际原始分；未通过或再次缺考最终 0 分。

**4-E｜复杂 SQL、GPA、排名与权限可见性**

1. 先用手算确定数据集预期，再写 JOIN/聚合 SQL。
2. 班级平均分只纳入已正式生效且有数值的当前最终成绩；0 分参与、无数值批准缓考暂不参与。
3. GPA 按课程学分加权，成绩 60～100 对应 1～5 绩点，不及格 0 绩点但学分进入分母。
4. 同入学年级、正常在读、至少一门正式数值成绩的学生参排；GPA 降序，相同时无当前挂科优先，条件同则 `RANK()` 跳号。
5. 学生只查自己名次；老师只看自己授课班级统计；不公开全体年级排行榜。
6. 已发布成绩更正、特殊考试正式生效或学籍变化后重新得出正确排名。

**阶段 4 测试必测**：

- [ ] 数值 0、`NULL`、缓考、获批缺考、未获批缺考区分正确。
- [ ] 首次全部录齐自动开启 72 小时；审核期修改不重置时间。
- [ ] 到期自动整班发布，重复自动任务/并发写入不造成部分发布。
- [ ] 截止日前后、迟交授权、已发布成绩精准更正均正确。
- [ ] 普通补考 85 分→最终 60、绩点 1.0；获批缓考 85 分→最终 85；补考失败→最终 0。
- [ ] 同学期同课程特殊考试批次唯一、名单冻结、审核后整体生效。
- [ ] GPA 分母包含挂科课程学分，无数值批准缓考不参与。
- [ ] 同年级竞赛排名测试得到 `1,1,3,4`，并正确区分“当前挂科”与“历史已通过”。
- [ ] 学生不能通过统计接口旁路查询他人 GPA 或未正式发布成绩。

**阶段 4 硬验收**：可复现从普通成绩录入到自动发布、特殊考试到最终认定、更正后立即生效、GPA/排名正确查询的全业务链；关键 SQL 在真实 MySQL 上经自动化断言验证。

### 阶段 5｜身份认证、资源归属与审计权限

**目标**：从测试身份切换成真实登录用户，并且正确判断“这个资源是不是你的”。

**实施顺序**：

1. 管理员建立账号与业务主体关联；密码安全哈希存储，不存明文。
2. 选择一种合适的认证方式（Session 或 Token），避免为展示而同时实现多套认证协议。
3. Spring Security 管理未登录 401、角色无权限 403、账号禁用和学籍限制。
4. 学生从登录上下文确定本人 ID，不能通过更换请求 `studentId` 操作别人账户。
5. 教师普通成绩权限按授课班级判断；特殊考试按批次明确授权判断。
6. 管理员的更正审批、迟交授权、教师变更和学籍维护必须有审计。
7. 重新运行阶段 1～4 的全部正常与失败测试，确认安全模块没有打断业务。

**任务清单**：

- [ ] 学生/教师/管理员身份认证和密码哈希。
- [ ] 角色与资源归属两级校验。
- [ ] 非在读学生仅保留合法历史查询权限。
- [ ] 学生不得查看他人权重、成绩、排名和完整榜单。
- [ ] 教师仅看本人班级统计；无权改他人普通成绩。
- [ ] 更正申请、特殊考试负责人权限与对应审计正确。
- [ ] 每类敏感接口验证未登录、错误角色、正确角色但错误资源、合法访问四类情况。

**验收**：真实用户能执行对应业务，越权和跨用户数据访问可靠拒绝；日志与错误信息不泄露凭据或个人敏感数据。

#### 阶段 5 权限测试矩阵

| 资源或操作 | 合法访问 | 必须拒绝的例子 |
|---|---|---|
| 我的权重余额 | 登录学生本人 | 通过修改学生 ID 查看其他学生余额 |
| 报名与退课 | 正常在读学生本人 | 休学学生或任意教师代替学生普通选退课 |
| 成绩查询 | 学生本人已正式生效成绩 | 查看他人、未发布成绩、内部考试原始记录 |
| 普通教学班录成绩 | 本教学班授课教师 | 任意同角色教师修改不相干教学班 |
| 更正审批 | 有管理权限的管理员 | 教师自行批准自己的申请 |
| 更正执行 | 已获精准授权的教师 | 修改非授权学生、其他分数或过期执行 |
| 特殊考试录入 | 指定批次负责人 | 非负责教师修改该批次 |
| 成绩统计 | 教师本人负责的教学班、管理员权限范围 | 教师查看其他教师全部班级统计 |
| 同入学年级名次 | 学生本人名次 | 查询完整排行榜或他人名次 |

**测试顺序**：先验证正常身份，再测试未登录、角色错误、资源归属错误、学籍或时间状态不符合。不能只凭“管理员和教师的 URL 不同”认定权限安全。

### 阶段 6｜质量、异常恢复、SQL 性能与工程化

**目标**：让复杂业务在重复请求、失败和并发下稳定，并留下可验证的质量证据。

**任务清单**：

- [ ] 统一检查 Controller/Service/Mapper 的职责、事务注解是否真正生效、是否存在捕获异常后错误提交。
- [ ] 重点回归报名扣权重、撤回返还、结算排序、随机重试、最终取消、退课清零边界。
- [ ] 回归普通成绩 72 小时、截止/迟交、更正、特殊考试批次整体生效。
- [ ] 补齐真实 MySQL 集成测试及多线程并发测试；数据可隔离、可重复清理。
- [ ] 统一错误码、异常处理、请求追踪标识和日志脱敏。
- [ ] 用真实数据执行至少两条复杂 SQL 的 `EXPLAIN`，说明索引是否合理。
- [ ] 记录至少 3 个实际排障案例：现象→假设→证据→修复→回归。
- [ ] 完成一次有针对性的代码审查与重构，比较修改前后测试结果。
- [ ] 评估自动任务重试、失败恢复、重复发布、重复发权重的幂等逻辑。
- [ ] 完善测试报告并明确实际运行环境和所用数据集；不编造吞吐或性能提升数字。

**验收**：核心不变量均有自动测试；并发测试可重现、失败能定位；SQL 优化有证据；重构没有破坏业务行为。

#### 阶段 6 的质量门槛及排障练习

| 质量维度 | 必须有的证据 | 不能作为替代 |
|---|---|---|
| 正确性 | 业务断言、数据库行结果、异常回滚测试 | 接口返回 200 |
| 并发安全 | 多线程或多事务测试、多次重复运行、核心不变量检查 | 单人手工点击两次 |
| 自动任务 | 重试、不提前发布、不重复发权重的测试 | “定时任务正常启动”的日志 |
| SQL 查询 | 真实执行的 EXPLAIN 与测试数据 | 直接声称使用了索引 |
| 安全性 | 401/403/资源归属校验和脱敏检查 | 只在前端隐藏按钮 |
| 可维护性 | 服务层边界清晰、适度重构、回归测试通过 | 代码文件数量越多越好 |
| 可交付性 | README、独立环境、脚本、Compose 可重复运行 | 仅个人电脑上可以启动 |

**建议排障复盘的三个重点方向**（实际遇到什么就记录什么，不编造已发生的问题）：

1. **并发选课**：为什么双请求会同时看到可用余额？锁住哪个对象才能防止重复扣除？
2. **成绩自动发布**：为什么定时任务重复触发？如何保证不会出现部分发布或提前可见？
3. **复杂 SQL**：为什么一个 JOIN 产生重复行？为什么不及格课程进入了 GPA 分母，批准缓考却不应该进入？

每次复盘至少留下：触发步骤、输入数据、日志/SQL、根因、修复思路、验证结果和 Git Commit（存在时填写）。

## 九、测试策略与验收矩阵

### 9.1 测试类型

| 类型 | 适用任务 | 结果要求 |
|---|---|---|
| 单元测试 | 纯校验、绩点公式、日期计算、状态转换 | 测试稳定、易定位原因 |
| MySQL 集成测试 | 真实 Mapper、事务、唯一约束、JOIN、窗口函数 | 与实际 InnoDB 行为一致 |
| 并发测试 | 同学生并发报名、余额扣除、轮次结算、退课 | 多次运行仍满足不变量 |
| 自动任务测试 | +50 发放、审核到期发布、批次正式生效 | 重复运行不重复生效 |
| 权限测试 | 其他学生成绩、其他教师班级、越权管理 | 非法访问被明确拒绝 |
| 端到端测试 | 管理员开课→选课→成绩→特殊考试→排名 | 跨模块数据与状态一致 |
| 容器复现 | Compose 应用与数据库、持久化及部署 | 按 README 可复现 |

### 9.2 首版必须覆盖的核心场景

| 编号 | 场景 | 预期结果 |
|---|---|---|

| T21 | 教师执行合法精准成绩更正 | 新成绩立即生效、历史保留 |

### 9.4 测试数据集的设计方法

为保证自动化测试能覆盖业务差异，建议构造少量**互相独立的合成数据集**，不使用真实学生身份。

| 数据集 | 必备数据 | 主要验证 |
|---|---|---|
| D1：学籍和课程范围 | 正常在读、休学、退学、已毕业；两专业两年级 | 学籍、身份、专业/年级资格 |
| D2：教学周与时间 | 连续周、不连续周、相邻节次、重叠节次 | 教师/学生时间冲突 |
| D3：容量和最低人数 | 40 容量、19/20/40/41 人边界 | 待开班、确认开班、容量与偶数约束 |
| D4：竞争排序 | 不同权重、相同权重、名额不足、跨轮次已录取 | 录取正确、同权重随机、不可重排 |
| D5：权重生命周期 | 100 初始、投入扣除、撤回/落选/退课返还、+50、清零 | 账户余额和流水一致 |
| D6：普通成绩 | 0、55、60、100、缓考、批准/未批准缺考、未录入 | 完整性、审核、正式发布 |
| D7：特殊考试 | 普通补考 85/55、批准缓考 85/55、再次缺考 | 资格、最终认定、原始/最终分分离 |
| D8：GPA 排名 | 同年级不同 GPA、同 GPA 不同挂科状态、休学与恢复 | `RANK()`、次级排序、资格排除 |
| D9：重复及并发 | 同账号多请求、重复任务、延迟执行 | 不重复扣还、不超员、不部分发布 |

**测试组织建议**：

- 每个测试案例从可控前置数据开始，不依赖上一个测试的偶然执行顺序。
- 模拟并发时明确连接池大小与事务范围；不同工作线程不能误以为处于同一个测试事务。
- 随机同权重结果，不要求某个具体学生必然被选中，而要断言“选中人数正确、同权重范围正确、重试结果稳定”。
- 72 小时相关测试使用可注入时钟或独立的到期执行入口；不依赖真正等待。
- 测试失败时要能从数据、日志与断言定位原因，不能反复手工修库使测试通过。

### 9.5 项目整体回归的最小执行顺序

1. 数据库 schema/seed 能从零创建并导入。
2. 人员、学期、课程、教学班和排课规则正确。
3. 选课时间窗口、资格、余额、同课程唯一和时间冲突正确。
4. 正常轮次与两次补选的竞争结算、同权重随机、开班确认和最终取消正确。

**项目版本发布前**，所有 P0 测试不得因“暂时只影响罕见情况”而被跳过；确实无法完成的功能应明确标注未完成，不得计入已交付范围。

## 十、Git 工作流与日常执行标准

### 10.1 一次小任务的标准过程

1. 从当前阶段取一个足够小的具体目标，先明确必要知识点与验收案例。
2. 自己实现最关键部分，或在 AI 提供的局部示例帮助下理解并改写。
3. 本地运行、打断点或查看 SQL 与日志，先验证一个正常路径。
4. 增加失败/边界测试，确认异常时数据确实回滚或保持一致。
5. 使用 `git diff` 检查修改，整理无关文件，提交语义明确的 Commit。
6. 将真实完成情况、错误、解决过程和下一步写入 `notes/开发记录.md`。
7. 一个知识点过关后再继续，避免一次外包过多实践机会。

### 10.2 建议必须亲手熟悉的 Git 操作

```bash
git status
git diff
git add <指定文件或目录>
git commit -m "feat: implement student create API"
git log --oneline --max-count=10
git switch -c feature/enrollment-weight
```

以上命令只是使用示例，执行之前确认当前仓库和文件状态；不要把不存在的 Commit 写成已完成。

### 10.3 每个功能的完成定义（Definition of Done）

- [ ] 业务规则对应需求编号可以追溯。
- [ ] 输入、输出、正常、非法、边界与重复请求行为已确认。
- [ ] SQL、数据约束、事务与权限规则正确。
- [ ] 单元或真实数据库测试通过，关键跨表事务有失败回滚验证。
- [ ] 关键业务并发或自动任务具有可复现的验证证据。
- [ ] API 文档、相关设计文档和开发记录同步更新。
- [ ] 代码没有硬编码密码或泄露其他学生隐私。
- [ ] Git 提交内容清晰，可由自己解释实现和取舍。

### 10.5 AI 辅助边界与代码审查清单

**可以充分交给 AI 的工作**：整理变更记录、把业务规则转为测试场景草稿、检查 Markdown 一致性、建议边界测试、审查 SQL 与日志、帮助定位异常和解释代码。

**建议保留亲自实践的工作**：核心实体关系、报名扣还权重、选课事务和结算状态机、首次录齐/到期生效、复杂 GPA/排名 SQL、至少一组真实并发测试和关键 Git 操作。

AI 提供代码时先核查：

- 它是否准确区分了报名和录取、已录取和已开班、原始成绩和正式成绩？

- 是否真的覆盖了已经确定的失败与重复请求分支？
- 是否引入未确认的规则（例如自动录取冲突课程、额外补选轮次）？
- 是否通过真实 MySQL 运行，而不是仅有静态说明？
- 我是否能够不依赖 AI 解释主要 SQL、锁定对象和回滚结果？
