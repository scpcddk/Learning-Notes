# 后端 × AI 应用 × 云原生：两年成长路线（修订版）

> **规划周期**：2026 年 10 月—2028 年 6 月（大二至大三结束）  
> **版本日期**：2026 年 10 月 26 日  
> **长期职业方向**：AI 应用工程师 / AI Engineering，具备扎实的 Java 后端与云原生工程能力  
> **近期现实目标**：2027 年暑期争取后端实习；在此之前形成能独立开发、测试、部署、讲清楚的完整项目。

---

## 一、战略定位：从“云原生 + AIOps”调整为“后端支撑的 AI 工程”

### 1.1 核心定位

**以 Java 后端构建系统，以 Python 和大模型技术赋予系统 AI 能力，以 Linux、Docker 和云原生手段实现可靠交付。**

```text
                         AI 应用工程师
                              │
          ┌───────────────────┼───────────────────┐
          │                   │                   │
      后端工程基础          AI 应用能力          云原生工程能力
          │                   │                   │
   Java / Spring Boot     LLM API / RAG      Linux / Docker
   MySQL / Redis          Tool Calling       CI/CD / Kubernetes
   API / 事务 / 测试       Agent / 评估       可观测性 / 排障
          └───────────────────┼───────────────────┘
                              │
                     可运行、可维护的实际系统
```

不以“掌握框架数量”或“做完 Demo 数量”衡量进步，而以**能否独立交付一个有业务价值、能解释设计与故障的项目**衡量。

### 1.2 对旧版计划的关键修改

| 旧版安排 | 修订后安排 | 原因 |
|---|---|---|
| 校招定位偏“云原生 Java / 工业互联网 + AIOps” | 首要定位为 **AI 应用工程师**；后端和云原生是核心竞争力，AIOps 是可选专长 | 与当前职业目标一致，同时保留后端就业选择 |
| 直接围绕智慧换热站进行全部学习 | **先完成较小的 Spring Boot 项目，再演进智慧换热站等综合项目** | 降低初期复杂度，先把请求、业务、数据库、测试、部署真正串起来 |
| 2027 年上半年集中拆微服务 | **优先高质量单体 / 模块化单体；有实际需求再拆微服务** | 微服务不是项目成熟的必经步骤，过早拆分会挤占基础训练 |
| AI 主要是 Pandas、异常检测，最后转向 AIOps | **LLM API → Structured Output → Embedding → RAG → Tool Calling → Agent → 工程化** | 与已确认的 AI 学习主线一致 |
| K8s、Kafka、Nacos、SkyWalking 等按日期逐项引入 | **以问题驱动选技术，设置必修 / 选修** | 避免为凑技术栈而增加无意义复杂度 |
| 严格按照日历推进 | **时间作为参考，阶段验收决定是否前进** | 保持与课程、比赛、实习的实际节奏兼容 |

### 1.3 三条长期主线与优先级

1. **后端主线（大二最高优先级）**：Spring Boot、MyBatis/MyBatis-Plus、MySQL、Redis、工程开发与完整项目。
2. **AI 主线（贯穿两年，大三提升权重）**：Python、LLM API、结构化输出、RAG、工具调用、Agent、AI 应用评估与部署。
3. **云原生 / 工程主线（先低频打基础，后面深挖）**：Git、Linux、Docker、网络基础、CI/CD、Kubernetes、可观测性。

**算法、计算机基础、英语、课程学习和健康管理属于贯穿性基础，不能为追求项目进度而全部挤掉。**

## 二、项目体系：一个训练项目 + 一个长期综合项目

保留原计划的“一个系统随能力持续演进”思想，但不把每个知识点都强行塞进同一个项目。

### 项目 A：学生—课程—成绩管理系统（近期训练项目）

**目的**：恢复 Spring Boot 手感，强化 MyBatis/MySQL，将已学知识变成独立编码能力。

**最小业务范围：**

- 学生、课程、选课与成绩管理；
- CRUD、分页、条件筛选、关联查询；
- 统一参数校验、异常处理和规范化 API 返回；
- 合理的数据库表设计、索引及事务；
- Git 提交记录、README、接口文档和必要测试；
- 使用 Docker 或 Docker Compose 完成至少一次可复现部署。

**阶段原则**：先做出完整业务闭环，不以提前增加 Redis、MQ、微服务为目标。

**完成标准**：从空项目到数据库建表、开发、调试、测试、部署，能够基本独立完成；能够讲清一次请求从 Controller 到数据库的完整链路。

### 项目 B：智慧换热站 / 工业互联网平台（长期综合项目）

**沿用旧版规划的智慧换热站方向**，但将其定位为可逐步扩展的综合项目，而不是要求大二一次性做完所有工业能力。如果缺少设备或真实数据，可以先使用模拟采集与标注的样例数据。

```text
阶段 B1：业务单体
设备 / 测点 / 采集记录 / 基础告警 / 用户权限
                ↓
阶段 B2：可靠工程交付
日志 / 缓存 / 部署 / 故障排查 / 自动化测试
                ↓
阶段 B3：AI 功能接入
设备文档 RAG / 告警解释 / 运维工具调用 / 评估
                ↓
阶段 B4：云原生增强（按需）
容器编排 / CI-CD / 可观测性 / 弹性与可靠性
                ↓
阶段 B5：AIOps 扩展（可选）
异常检测 / 故障辅助定位 / 证据链与人工确认
```

**技术选择原则：**

- Spring Boot + MyBatis + MySQL 构成基础；Redis 在出现适合的缓存或临时状态场景时引入。
- EMQX / MQTT 适用于设备数据采集；MinIO 用于文件和对象存储；Nginx 用于反向代理。
- SRS 只有在明确存在音视频接入需求时才加入，不为技术展示强制接入。
- Kafka、Nacos、Gateway、Sentinel、Redisson、SkyWalking 等属于解决具体问题的备选技术，**不作为项目完成的硬指标**。
- AI 功能应该能说明：模型输入是什么、外部证据从哪里来、输出如何校验、效果怎么评估、失败时怎么办。

## 三、阶段路线（以验收结果为准，不以日期强制跳关）

## 阶段 1：补齐后端闭环，完成独立项目

**参考时间：2026.10—2027.1**  
**定位：大二当前主线；同时保持 AI 学习频率。**

### 1. 后端重点

- [ ] 完成 MyBatis-Plus 剩余内容：条件构造器、条件更新、分页、自动填充、逻辑删除、乐观锁基本概念。
- [ ] 复习 Spring Boot：依赖注入、Controller、Service、请求参数、响应、配置及异常处理。
- [ ] 串联 Spring 事务、MyBatis 执行流程、MySQL 事务和连接资源管理。
- [ ] 完成项目 A 的数据库设计、核心业务接口、分页与关联查询。
- [ ] 补充基础测试、日志、参数校验、API 文档及 Git 工作流。
- [ ] 掌握项目的本地启动、基本排障与容器化运行。

### 2. 同期 AI 重点

- [ ] 以现有 Python + LLM API 代码为基础完成阶段验收，不重复大量已掌握的基础练习。
- [ ] 开始 Structured Output：JSON Schema、结构校验、非法输出处理。
- [ ] 视进度进入 Embedding 基础，不要求本阶段完成 RAG 全链路。

### 3. 同期工程基础

- [ ] Git：分支、提交、合并、冲突处理、远程仓库与基本协作。
- [ ] Docker：镜像、容器、端口、卷、网络、Dockerfile、Compose，结合项目练习。
- [ ] Linux：继续按专项计划缓慢学习，不将“看过命令”视为“能排障”。

### 4. 阶段验收

- [ ] 能独立实现并调试至少一条完整业务链路：HTTP → Controller → Service → Mapper → MySQL。
- [ ] 有可运行的项目 A、README、数据库脚本和接口说明。
- [ ] 能演示分页、事务、异常处理及至少一种关联查询。
- [ ] 能用 Git 管理开发过程，并完成一次可复现部署。
- [ ] 能说明项目中至少三个真实遇到的问题、定位过程和解决方法。

> **退出条件**：项目 A 达到“可独立交付”的基本水准后，才把主要精力转向复杂业务项目；不必把每个 MyBatis-Plus 插件都研究到源码级别。

## 阶段 2：实习准备与真实工程能力

**参考时间：2027.2—2027.6**  
**定位：2027 年暑期后端实习前的核心准备期。**

### 1. 后端工程深化

- [ ] 建设项目 B 的最小版本：设备管理、测点数据、基础告警、必要的权限管理。
- [ ] 系统练习接口设计、表结构、索引、`EXPLAIN`、事务边界和常见性能问题。
- [ ] 按业务需要学习 Redis：缓存模型、过期策略、缓存一致性基础。
- [ ] 补充认证授权、安全基础、必要的单元测试与接口测试。
- [ ] 学会通过日志、HTTP 状态、SQL 执行、Docker 容器状态排查常见故障。
- [ ] 视业务需要使用 MQTT / EMQX、MinIO；不强求一次加入全部中间件。

### 2. 实习能力准备

- [ ] 形成一份可展示的后端项目简历描述，突出独立实现与技术取舍。
- [ ] 梳理 Java、Spring、MySQL、Redis、网络、操作系统、Git、Linux 常见问题。
- [ ] 保持算法练习，但不把全部时间转向竞赛难题。
- [ ] 练习讲解项目架构、关键业务流程、一次故障排查和一次性能优化。
- [ ] 提前关注实习招聘的开始时间、地点、到岗要求与持续时间。

**现实约束**：原先希望优先在沈阳线下实习，但学校暑假可能只有约一个半月，不应默认能满足所有企业常见的三个月及以上实习要求。应优先筛选到岗时间匹配的机会，并准备校内项目、开源协作或实际业务实践作为补充。

### 3. 同期 AI 重点

- [ ] 完成 Embedding：文本向量、相似度、基础检索与评估概念。
- [ ] 进入 RAG：文档切分、索引、召回、检索结果与回答引用。
- [ ] 尝试独立完成一个小型可运行的问答应用，不要求复杂 Agent。

### 4. 阶段验收

- [ ] 项目 B 最小版具备真实业务闭环，能够稳定运行。
- [ ] 能从数据库到接口、再到部署独立定位常见错误。
- [ ] 有能在面试中清晰展示的代码、文档、运行演示和技术复盘。
- [ ] 至少经历一轮简历修改、模拟面试或真实岗位投递反馈。

> **重点提醒**：本阶段的目标不是赶进度学完 Spring Cloud，而是先有较扎实的后端工程能力，争取真实开发环境。

## 阶段 3：AI 应用工程化，完成后端与 AI 融合

**参考时间：2027.9—2028.1**  
**定位：大三开始，逐步提高 AI 主线权重。**

### 1. AI 技术路线

- [ ] 结构化输出：Schema、校验、异常恢复。
- [ ] RAG 深化：查询改写、检索质量、召回评估、文档更新与权限控制。
- [ ] Tool Calling：工具参数校验、权限、超时、失败处理及副作用操作确认。
- [ ] Agent：状态管理、工具选择、多步任务、循环退出条件、日志与错误恢复。
- [ ] AI 服务工程：FastAPI、异步 I/O、模型 API 限流与重试、费用和延迟统计。
- [ ] 安全与可靠性：提示注入风险、敏感信息处理、外部文本可信度与人工兜底。

### 2. 与项目 B 融合

优先完成**一个有明确价值的 AI 功能**，再增加其他能力：

**推荐功能：设备知识库 + 告警辅助解释。**

```text
运维人员提问 / 告警事件
         ↓
Spring Boot 业务服务
         ↓
Python / FastAPI AI 服务
         ↓
文档检索（RAG） + 安全的只读业务工具
         ↓
LLM 生成解释与建议
         ↓
结构校验 + 引用来源 + 日志记录
         ↓
返回业务系统，由人工判断与执行
```

- [ ] 上传设备手册、排障文档或明确标注的模拟资料。
- [ ] 支持带来源引用的问答，不把模型猜测包装为事实。
- [ ] 让 AI 查询经过授权的设备状态或告警记录；优先使用只读工具。
- [ ] 建立小型测试集，比较普通问答、检索问答和不同检索参数的表现。
- [ ] 记录失败案例、延迟、API 成本和改进措施。

### 3. ML / DL 的定位

- 大三可以开始系统学习机器学习基础、评价指标、训练与过拟合等概念。
- 在应用层项目达标前，**不强制同时深挖 PyTorch、Transformer 训练、LSTM、时序预测和 Agent**。
- 只有在拥有可用的时序数据、明确指标和简单基线后，才引入 Isolation Forest、Prophet 或其他异常检测方法。

### 4. 阶段验收

- [ ] 具备一个独立运行、能够与 Java 后端交互的 AI 服务。
- [ ] 完成至少一种 RAG 或工具调用功能，能展示真实输入、输出及失败处理。
- [ ] 能用自己整理的测试问题评估回答质量，而不只演示成功案例。
- [ ] 能解释何时不应使用 Agent、何时规则系统更合适。

## 阶段 4：云原生交付与可观测性，形成综合项目

**参考时间：2028.2—2028.6**  
**定位：围绕已有业务和 AI 服务做可靠交付，不为技术栈而技术栈。**

### 1. 工程交付（优先）

- [ ] Dockerfile 优化、环境变量与配置管理、健康检查、日志、持久化数据。
- [ ] 使用 Docker Compose 运行本地多服务环境。
- [ ] GitHub Actions 或其他 CI：构建、基础测试、镜像产物。
- [ ] Kubernetes 基础：Pod、Deployment、Service、Ingress、ConfigMap、Secret、探针。
- [ ] 能在本地集群部署至少一个后端服务和一个 AI 服务，理解其基本访问与故障排查过程。
- [ ] 有实际扩缩容需求后，再研究 HPA；不以跑通 HPA 为全部目标。

### 2. 可观测性（优先）

- [ ] 区分 Metrics、Logs、Traces，能说明它们分别解决什么问题。
- [ ] 逐步接入 Prometheus、Grafana 和 OpenTelemetry 等工具。
- [ ] 按需要选择 Loki 或其他日志方案；先解决“能够定位故障”，不追求组件齐全。
- [ ] 对一次真实或模拟故障进行记录：表现、指标、日志、定位证据、修复措施。

### 3. 分布式与微服务（按需选修）

只有在现有模块确实遇到独立部署、不同扩缩容需求、团队协作边界或明显的复杂性问题时，才考虑拆分服务。

可选学习顺序：

1. 先掌握模块化单体、模块边界、接口契约；
2. 再考虑 Gateway、服务发现 / Nacos、OpenFeign 等；
3. 真有异步处理需求时学习消息队列（Kafka 等）；
4. 发生流量治理或分布式一致性问题时，再专项学习限流、熔断、幂等与补偿；
5. SkyWalking、Sentinel、Redisson 等工具根据实际问题选择，而非全部必装。

### 4. AIOps（可选加分方向，不再是强制最终定位）

在已有日志、指标和稳定的观测链路之后，可探索：

- [ ] 规则型告警与异常检测基线；
- [ ] 结合日志、指标和文档给出故障线索；
- [ ] LLM 辅助总结故障、提供待验证的根因假设；
- [ ] 明确标注不确定性，避免将 AI 推测当成确定 RCA 结果；
- [ ] 高风险操作必须人工确认，不能让 Agent 直接执行破坏性运维命令。

### 5. 阶段验收

- [ ] 项目 B 拥有可复现部署流程、基础自动化检查和故障排查文档。
- [ ] 至少一条业务请求能通过日志、指标或 Trace 得到定位线索。
- [ ] 后端服务与 AI 服务可以协作运行，并具备合理的异常兜底。
- [ ] 能清楚解释：为什么选择当前架构、为什么没有（或为什么需要）拆微服务。

## 四、贯穿两年的基础能力

| 方向 | 重点内容 | 学习方式 |
|---|---|---|
| Java / Spring | Java 21、集合、并发基础、JVM/GC 基础、Spring IOC/AOP、Spring MVC、事务 | 项目问题驱动 + 专项复习 |
| 数据库 | MySQL、InnoDB、索引、执行计划、锁、MVCC、事务、Redis | 结合真实 SQL、查询分析和测试 |
| 网络 / 操作系统 | TCP/IP、HTTP、DNS、端口、进程、线程、同步、文件与权限 | 配合学校计算机网络、操作系统课程 |
| 工程工具 | Git、Maven、Linux、Shell、Docker、调试、日志、测试 | 直接服务当前项目 |
| AI / Python | Python、httpx、FastAPI、异步 I/O、LLM API、RAG、Agent | 独立编写 → Review → 修改 → 评估 |
| 算法与数据结构 | 基础数据结构、常见算法思想、复杂度、面试相关题型 | 保持长期低中频训练 |
| 英语 | 听力、口语、技术文档阅读 | 延续每天约 25 分钟的训练习惯 |

已学内容不因出现在计划中就自动视为需要从头重学；未实操验证的内容也不因“学过”自动标记完成。

### 5.1 大二与大三的投入原则

这里的比例仅指**技术自主学习时间**，不包括学校必修课、考试复习、比赛刚性任务与日常生活。

| 时期 | 主要权重 | 说明 |
|---|---|---|
| 大二当前—2027 年暑期前 | 后端项目优先，AI 稳步推进，Docker/Git 随项目学习 | 先形成实习竞争力，避免多线抢进度 |
| 2027 年暑期 | 实习 / 真实项目实践优先 | 根据岗位要求临时调整技术学习 |
| 大三上 | 提高 AI 应用与工程融合的投入 | 做出有验证、有评估的 AI 功能 |
| 大三下 | AI 工程 + 云原生交付并重 | 完善质量、部署、可观测性和代表项目 |

无需机械执行旧版“大二 80% 后端 / 20% AI，大三 50% 云原生 / 50% AI”。学期课程、比赛与项目难度变化时，比例应调整。

### 5.2 可执行的每周安排

**正常周（在学校和比赛任务允许的条件下）：**

- 后端 / 当前项目：优先保证连续的深度开发时间；可以延续每天约 2 小时的目标，但不必天天额外加新知识。
- AI：每周 2 次正式学习（每次 60—90 分钟），视精力增加 1 次短复习。
- 算法：保留每周稳定练习；优先复盘错题，不为数量牺牲质量。
- Docker / Git / Linux：优先依附项目实践，另外安排小块专项复习。
- 计算机组成原理、概率论、学校作业：按考试和课程节点提高优先级。
- 英语、阅读、运动：保持可持续的低成本习惯。

**忙碌周（考试、比赛冲刺、项目交付）：**

1. 只保留一条必须推进的技术主线；
2. AI 缩为一次复习或小规模实践，不强制每周学习新模块；
3. 暂停扩展中间件、Kubernetes 等非紧急新主题；
4. 保留必要睡眠与运动，不用长期透支换学习时长。

### 5.3 优先级判定规则

出现任务冲突时，依次考虑：

1. **硬截止时间**：课程考试、比赛提交、真实项目交付、实习面试；
2. **当前阶段主线**：完整后端项目 / 当前 AI 工程任务；
3. **高复利基础**：算法、网络、操作系统、Git、测试和英语；
4. **可延期扩展**：新框架、冷门中间件、超出需求的分布式架构。

**同一时间最多保留一条重型工程项目主线 + 一条较轻的 AI 学习线。** ANIC 比赛冲刺期间，比赛可临时替代项目主线，结束后再恢复。

## 七、执行原则与复盘机制

### 7.1 六条原则

1. **项目优先于堆栈**：先做完整单体，再按需要引入缓存、消息队列、微服务和 K8s。
2. **AI 持续推进**：即使后端是大二主线，也不长期中断 Python + LLM API → RAG → Agent 的学习。
3. **工程真实可验证**：不能用“知道概念”代替“能自己写、能调试、能部署”。
4. **已掌握的少重复，薄弱点要补透**：学习中坚持讲解 → 示例 → 独立实践 → 检查 → 纠错。
5. **不假设任务已完成**：每次推进计划前先确认实际进度，未验证内容保持待办状态。
6. **允许动态调整**：实习、课程、比赛和个人精力变化时，可以延后非关键阶段，不把日程落后当成能力失败。

### 7.2 每月一次简短复盘

记录以下五个问题：

- 本月真正完成了什么（代码、项目、笔记、测试、文档）？
- 哪些内容只是了解，还不能独立使用？
- 当前最影响项目进展的一个技术短板是什么？
- 下月唯一最重要的阶段产出是什么？
- 哪些任务应暂停、删除或合并？

### 7.3 阶段切换的判断

**不因为计划表上的日期到了就进入下一阶段。** 只有在当前阶段最重要的项目产出、独立实现能力和基本排障能力达到验收标准后，才系统推进下一阶段；其余非关键内容可作为后续补充。
