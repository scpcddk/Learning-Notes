### 0.2 推荐使用环境

- **练习工程基线**：JDK 21、Spring Boot 3.3.13、MyBatis 3.x / MyBatis-Plus、Maven、JUnit Jupiter（JUnit 5）。接入学生选课系统时，以项目完成兼容性验证后的实际 `pom.xml` 和 Maven Wrapper 为准。
- **数据库与运行环境**：MySQL 8、Windows PowerShell、可选 WSL/Ubuntu 和 Docker Desktop。
- **测试技术顺序**：JUnit 5 → Mockito → MockMvc → 真实 MySQL → Testcontainers → Apifox/Postman → k6/JMeter → JaCoCo/CI。
- **版本原则**：依赖版本优先接受当前 Spring Boot / Maven 的兼容管理；看到新教程中的 API 先核对自身版本，不直接复制。
- **安全原则**：所有写入、回滚、负载、并发实验均在练习项目或独立测试环境完成，不连接正式数据库。

### 单元 05｜断言扩展、异常与失败消息

**学习目标**：确保异常情况真的被测试到，而不是“方法没有崩溃就通过”。

#### A. 逐知识点学习清单

- [ ] 掌握 `assertThrows` 的异常类型与 lambda 写法
- [ ] 知道 `assertThrows` 验证类型后，何时还需检查异常消息或错误码
- [ ] 理解 `assertDoesNotThrow` 的合理使用范围
- [ ] 认识 `assertAll`：一次验证多个相互关联的可观察属性
- [ ] 认识浮点数比较为何可能需要误差范围；业务金额优先理解 `BigDecimal` 规则
- [ ] 理解 `assertIterableEquals` 等集合类断言的基本用途
- [ ] 为可读的失败结果编写断言消息，不复制无意义描述
- [ ] 区分预期业务异常与程序缺陷异常，不把所有异常都当正确行为
- [ ] 了解异常路径也应检验状态没有发生不该发生的变化
- [ ] 理解“测试抛异常”与“测试失败时抛异常”这两个概念不同

#### B. 自己动手实操清单

- [ ] 为非法金额、余额不足等行为写 `assertThrows`
- [ ] 检查异常类型以及必要的错误信息/错误码
- [ ] 验证失败请求不会使余额变化（可以先针对纯内存对象）
- [ ] 让预期异常与实际异常不一致，阅读 JUnit 失败输出

#### C. 本单元验收清单

- [ ] 会独立写正常与异常两类测试

### 8.1 需求确认与测试数据准备

- [ ] 从项目最新需求文档确认“报名申请、录取、撤回、退课、取消开班”的状态定义

- [ ] 为测试使用独立数据库和独立账号，不碰真实数据

### 8.2 业务功能候选测试场景

本清单用于按风险选题。后期可结合阶段 5 的 `T06` 并发权重和 `T16–T18` 成绩发布练习，在实际项目中沿用同一套验收编号。

- [ ] **申请提交**：合法申请后，返回成功且持久化记录正确
- [ ] **申请提交**：余额不足的申请被拒绝，余额与报名记录不发生错误变化
- [ ] **边界值**：使用恰好等于可用余额的权重，结果符合最终需求
- [ ] **非法输入**：权重为负数、零或超出合法范围时符合接口契约（先确认是否允许零）
- [ ] **重复提交**：请求重试不导致不应发生的重复扣减或重复报名
- [ ] **报名截止**：在截止前后提交或撤回，结果符合生效规则
- [ ] **竞争录取**：不同权重学生录取顺序符合确定的排序规则
- [ ] **同权竞争**：同分/同权情况下的处理策略按正式规则验证
- [ ] **班级容量**：录取人数不得超过最大容量
- [ ] **最低人数**：人数不足时处于规定状态，最终取消时进行规定的补偿
- [ ] **申请撤回**：在允许撤回的状态下，释放/返还的金额正确
- [ ] **竞争失败**：未录取申请的最终余额和状态符合正式规则
- [ ] **正式退课**：权重处理依当前已确认版本执行，不沿用旧规则
- [ ] **异常中断**：多次数据库写入中的一处失败后不存在半提交
- [ ] **并发重复**：同时请求同一资源不会破坏余额、容量和唯一约束
- [ ] **越权**：学生不能未经授权修改他人的报名或权重
- [ ] **分页查询**：页码、大小、总数、空页、排序符合接口契约
- [ ] **结果查询**：录取、落选、待开班等状态与数据库一致

### 8.3 每个功能按层补测试

- [ ] 先用测试用例表写清需求与预期，标记“规则已确认/待确认”
- [ ] 再为纯业务计算写 JUnit 单元测试
- [ ] 再为 Service 分支写 Mockito 测试（若有外部依赖）
- [ ] 再为 Controller 写 MockMvc 输入、输出、异常测试
- [ ] 最后为关键数据库约束、事务和并发写真实集成测试
- [ ] 每次修复一个 Bug 都添加相应回归用例

**选课项目首次实践的最小交付物**：针对**一个已经实现且需求稳定**的功能，形成“用例表 + 5～8 条自动化测试 + 一次缺陷复现/修复 + 可重复运行说明”。

## 11. 错题/复盘规范与 AI 使用边界

### 11.1 按核心知识点推进

1. **回顾（5～10 分钟）**：回忆上次内容、核实实际完成项。
2. **讲解（15～20 分钟）**：定义 → 使用场景 → 常见错误。
3. **最小示例（10～15 分钟）**：只讲当前知识点需要的代码。
4. **自己操作（20～35 分钟）**：优先本人编写、运行、修改；一般只给 1～2 个练习。
5. **检查纠错（约 10 分钟）**：从预期/实际/根因/修复四项定位问题。
6. **归档（约 5 分钟）**：更新对应 `- [ ]`、记录错题和下一次起点。

### 11.2 学会自己验收 AI/Agent

- [ ] 由自己先定义测试意图与预期，AI 不替代需求判断
- [ ] 可以让 AI 解释报错、提出最小修改建议，但自己执行和检查
- [ ] 需要委托 AI 编写代码时，限定文件和行为范围
- [ ] 审查 AI 是否只把预期写成当前实现返回值，以致“假通过”
- [ ] 亲自运行关键测试并核实报告；快测用 `mvn test`，配置好集成测试后用 `mvn verify` 执行含数据库的回归
- [ ] 使用 `git diff` 查看修改与新测试，确认没有越界更改
- [ ] 能亲自解释每个断言目的和未覆盖风险后再打勾

## 13. 结业综合实战：独立测试一个已完成的业务功能

### 13.1 项目准备

- [ ] 选定一个已经实现、需求规则已确认、具备可运行接口和持久化行为的业务功能
- [ ] 找到对应需求、Controller、Service、Mapper、数据库表
- [ ] 明确测试数据库与测试数据隔离方案
- [ ] 写出功能可能出错的前三种风险

### 13.2 测试设计与实现

- [ ] 独立完成至少 8 条可验证测试用例（数量可按质量适当调整）
- [ ] 为纯业务逻辑补 JUnit 正常、边界、异常测试
- [ ] 对有外部依赖的 Service 关键分支使用 Mockito
- [ ] 用 MockMvc 验证至少两类接口输入输出场景
- [ ] 对影响数据一致性的规则执行真实 MySQL 测试
- [ ] 如果此功能有并发风险，设计最终状态不变量检查
- [ ] 对暂无法实践的内容标记“待前置条件”，不编造已测结果

如果所选功能涉及权重申请或成绩发布，可直接复用阶段 5 中相应的 `T06` 或 `T16–T18` 用例。综合实战还需选一条已实现的接口路径，用启动后的本地服务器和隔离 MySQL 发送一次真实 HTTP 请求，断言响应及数据库最终状态。服务器线程中提交的事务不会随测试方法上的 `@Transactional` 自动回滚，应在测试后显式清理或重建数据。

### 13.3 缺陷复现、交付与复盘

- [ ] 故意制造或找到一个真实缺陷，先运行测试看到失败
- [ ] 自己定位并解释问题成因，再修复代码
- [ ] 运行相关测试与必要的回归测试，记录结果
- [ ] 通过 `mvn verify`（项目有 Maven Wrapper 时用对应的 Wrapper 命令）执行完整回归，保存命令、所需环境、数据准备与清理方法
- [ ] 保存测试报告或终端输出，确认真实 MySQL 用例实际运行并记录通过、失败和跳过情况
- [ ] 能说清单元、Web、数据库测试分别防住了什么风险
- [ ] 能说明仍没有覆盖哪些风险，以及下一步如何补充
- [ ] 独立讲解整个“需求 → 测试设计 → 执行 → 修复 → 回归”流程

**结业判定**：完成首页四项核心成果和上面的综合实践，并能独立解释关键断言、运行报告及覆盖范围。
