# 问题诊断思维模型笔记

> 来源：2026-07-06 与 Kimi 的对话实践
> 案例：DeepSeek 代码题回答重复输出的 bug 诊断

---

## 一、**核心模型：漏斗式排除法**

```text
宽泛描述 → 缩小范围 → 锁定根因 → 验证假设
```

---

## 二、五步诊断流程

### Step 1：接收信息，建立初始假设

**原则**：多假设并行，不急于锁定单一答案。

**操作**：

- 仔细倾听/阅读对方描述的现象
- 基于经验和常识，列出所有可能的假设
- 给每个假设标注置信度和依据

**本案例初始假设**：

| 假设 | 依据 | 初始置信度 |
| ------ | ------ | ----------- |
| 模型生成层面的重复循环 | 语言模型常见 bug | 中等 |
| 后处理/渲染层的复制错误 | 用户强调"完全一模一样" | 较高 |
| "思维链"与最终答案混淆 | 用户说"不是思考过程" | 较低 |
| 特定题型触发 | 待验证 | 未知 |

---

### Step 2：索要证据，缩小范围

**原则**：每个新信息都要用来排除错误假设。

**关键提问方向**：

- 重复的内容是否**完全一致**？（区分模型生成 vs 系统复制）
- 是否**所有题型**都触发？（判断通用性 vs 特异性）
- 重复是从哪里开始的？（开头/中间/结尾）
- 平台/客户端是否有差异？

**本案例关键证据**：

- 用户贴出完整回答 → 确认**逐字逐句、从标题开始完全重复**
- "代码题经常这样" → 确认**题型相关性**

**范围缩小结果**：

```text
模型生成重复 ❌  →  完全一致，不是渐进式重复
思维链混淆 ❌    →  不是思考+答案结构
后处理 bug ✅    →  最可能
代码块渲染分支 ✅ →  高度相关
```

---

### Step 3：构建因果链，提出根因假设

**原则**：用因果逻辑串联已知事实，形成可解释的假设。

**本案例因果链**：

```text
代码题
  ↓
包含代码块 (```)
  ↓
触发代码格式化后处理
  ↓
后处理逻辑错误：同一段内容被渲染两次
  ↓
用户看到完全重复的输出
```

**为什么是这个假设？**

| 证据 | 支撑点 |
| ------ | -------- |
| "完全一致" | 排除模型生成，指向系统复制 |
| "代码题经常" | 指向代码块这个特定触发条件 |
| 其他题型正常 | 确认不是通用输出 bug |

---

### Step 4：设计验证实验

**原则**：好诊断必须有可证伪的预测。

**本案例验证方案**：

| 实验 | 控制变量 | 预期结果 | 若不符则修正 |
| ------ | --------- | --------- | ------------- |
| 纯文字算法题（无代码块） | 移除代码块 | 不重复 | 假设错误，重新排查 |
| 非算法题但带代码块 | 保留代码块，换题型 | 可能重复 | 确认代码块是触发条件 |
| 显式约束"不要重复" | 人为干预 | 可能绕过 | 了解系统对约束的敏感度 |

---

### Step 5：给出临时 Workaround

**原则**：根因未修复前，提供可操作的绕过策略。

**本案例 workaround**：

- 在 prompt 中加显式约束："请直接给出解答，不要重复输出任何内容"
- 要求纯文字描述，不要代码块格式

---

## 三、**模型的关键要点总结**

| 要点 | 说明 | 本案例体现 |
| ------ | ------ | ----------- |
| **先发散，后收敛** | 不急着给答案，先列多种可能 | 初始列出 4 个假设 |
| **用证据淘汰假设** | 每个新信息都要排除错误方向 | "完全一致"排除模型生成假设 |
| **关注"反常识"细节** | 异常特征往往指向根因 | "从标题开始重复"指向系统复制 |
| **提出可验证的预测** | 诊断的价值在于指导下一步行动 | 设计 3 组对照实验 |
| **区分"是什么"和"怎么办"** | 根因分析 + 临时方案并行 | 给出假设 + workaround |

---

## 四、**通用应用场景**

这个模型适用于任何"奇怪现象"的诊断：

1. **软件 bug 排查**
2. **系统故障分析**
3. **实验异常解释**
4. **日常问题定位**

**通用步骤**：

```text
1. 描述现象（频率、触发条件、表现形式）
2. 列出假设（技术问题？操作问题？外部因素？）
3. 设计最小测试（改变一个变量，观察现象变化）
4. 根据结果修正假设
5. 循环直到收敛
```

## 五、本案例的信息效率分析

用户的两个关键反馈分别起到了什么作用：

| 反馈内容 | 排除的假设 | 确认的假设 |
| --------- | ----------- | ----------- |
| "完全一致，从标题开始重复" | 模型生成重复 ❌ | 系统复制错误 ✅ |
| "代码题经常这样" | 通用输出 bug ❌ | 代码块触发 ✅ |

> **启示**：高质量的问题描述能大幅提升诊断效率。描述时尽量包含：
>
> - 现象的具体表现形式
> - 触发条件和频率
> - 已尝试过的排查步骤

---

## 六、一句话总结

> [!IMPORTANT]
> **诊断的本质不是"猜对答案"，而是"用证据快速排除错误答案"**
