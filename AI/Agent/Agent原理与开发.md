## 1. 先掌握唯一主线：Agent Loop

```text
用户目标
   ↓
读取可用上下文（用户消息、历史、工具清单、工作目录等）
   ↓
模型判断：回答？还是调用工具？
   ├── 直接回答 → 输出并结束
   └── 选择工具 → 发出结构化工具调用请求
                     ↓
               运行环境检查权限并执行工具
                     ↓
               获取返回结果 / 错误
                     ↓
               将结果加入上下文
                     ↓
               再次交给模型判断 → 继续或结束
```

这是一幅**教学简图**：不同 Agent 的实际调度、工具权限、记忆和会话管理实现可能不同。

### 1.1 一次最小的工具调用发生了什么？

以“查看项目中有哪些测试文件”为例：

1. 用户提出目标，Agent 看到可用工具的名称和输入约束。
2. **模型**提出调用某个文件搜索工具，并提供参数；这一步本身并没有读文件。
3. **Agent 运行时 / Harness**验证工具调用，按权限策略实际访问文件系统。
4. 工具返回文件列表或错误，运行时把结果作为新消息加入上下文。
5. 模型依据新信息决定直接回答、再读某个文件，或者停止并请求更多信息。

**关键区别**：模型负责生成判断与调用意图；真正执行文件、Shell、网络等操作的是模型之外的代码与运行环境。**Tool Calling 不等于模型直接拥有操作系统权限。**

### 1.2 工具调度：串行与并行

一次模型回复可能产生多个工具调用意图。运行时可以顺序执行，也可以在互不依赖时并发执行：

| 方式 | 执行顺序 | 适用情况 | 主要风险 |
| --- | --- | --- | --- |
| 串行 | 工具 A 完成后再执行 B | 后一步依赖前一步结果，或操作同一共享状态 | 耗时较长 |
| 并行 | 多个独立调用同时执行 | 读取互不相关的文件、独立的查询请求 | 并发冲突、顺序与成本不易预估 |

能否并行取决于**依赖关系**：读取几个互不相关的文件可以并行；“先写 `config.json`、再读 `config.json`”必须串行。涉及同一文件写入、共享缓存或外部限流接口时，还要考虑冲突与配额。

> [!important] 并发上限不等于实际并发数
> 配置的并行数表示单步允许同时执行的最大工具调用数量，不代表每次用满，也不等于 Agent 数量或 Agent Loop 的最大循环次数。

**DSH 观察（0.2.2-rc.1，2026-11-06）**

Web UI 的「插件 → Agent 循环」中有配置项「并行工具调用数」，当时值为 `10`。这是界面配置观察，尚未实测并行执行效果；字段名称、默认值会随版本变化。

并行提升的是独立任务的调度效率，不保证减少 Token 消耗：每个工具的参数与结果仍会进入上下文；任务本身存在串行依赖时，调高并行数也不会缩短流程。

## 2. 把系统拆成五个部分

| 部分 | 负责什么 | 典型问题 |
| --- | --- | --- |
| **模型（Model）** | 根据上下文生成文本或工具调用意图 | 为什么选择这个工具？模型是否理解任务？ |
| **工具（Tools）** | 文件操作、Shell、HTTP、数据库等具体能力 | 输入与输出是什么？调用失败会返回什么？ |
| **运行时 / Harness** | 驱动循环、调用工具、调度消息、管理中止 | 谁真正执行命令？如何限制步骤数？ |
| **上下文与状态** | 对话历史、工具结果、任务进度、必要的持久化数据 | 很长的任务如何保留重要信息？ |
| **权限与执行环境** | 沙箱、身份、路径和网络边界、审批策略 | 哪些文件或服务不能访问？出错如何恢复？ |

这五个部分可用于分析一次 Agent 操作中，判断、执行、结果反馈与权限控制分别由谁负责。

### 2.1 Extension：扩展 Agent 的程序能力

> [!note] 扩展如何提供新功能
> Extension 通过程序代码接入 Agent 运行时提供的 API。以 Pi 为例，扩展可以注册交互命令、提供模型可调用的工具，也可以订阅模型切换、工具调用等事件。

| 机制 | 入口与作用 | 示例 |
| --- | --- | --- |
| `pi.registerCommand()` | 注册用户在交互界面触发的命令，由命令处理函数执行操作 | `/hello-agent` 显示通知；自定义状态命令查询已有信息 |
| `pi.registerTool()` | 注册供模型选择调用的工具，由运行时执行工具实现并回传结果 | 提供一个新的查询或计算工具 |
| `pi.on()` | 订阅运行时事件，在指定时机执行扩展逻辑 | 观察模型切换、处理工具调用相关事件 |

`ctx.ui.notify()` 用于显示界面提示。一个只发送固定通知的命令处理函数，无需请求模型生成回答；是否使用模型、Shell 或网络，取决于该处理函数的实现。

**状态查询示例：** 可通过 `ctx.cwd` 获取工作目录，通过 `ctx.model` 获取当前模型，通过 `ctx.sessionManager.getSessionId()` 获取会话 ID。注册前应检查同名命令；为避免冲突，可采用 `/my-status` 这样的名称。

> [!important] Skill 与 Extension 的职责
> Skill 主要指导 Agent **如何使用已有能力**完成任务；Extension 通过代码**增加或改变程序能力**。Skill 可以有 `/skill:名称` 这样的加载入口，但这不同于通过代码注册新的运行时命令或工具。

> [!warning] 注册命令不能创造底层不存在的能力
> 自定义状态命令只能展示 API 或其他真实数据源能够提供的信息，不能凭空增加沙箱、审批或权限控制。扩展运行在 Pi 进程内，具有相同的操作系统权限，应审查其代码和来源。

**官方依据（2026-11-05）**：[Pi Extensions](https://pi.dev/docs/latest/extensions) · [Pi Skills](https://pi.dev/docs/latest/skills)。创建、运行结果等个人实践单独保存在[实践记录](./Agent实践案例/Agent实践记录.md)。

### 2.2 Pi Extension：注册模型可调用的自定义工具

`pi.registerTool()` 将工具描述、参数结构和实际执行函数连接到 Pi 运行时。它与交互命令的区别见 2.1 节：用户提出任务后，模型生成工具调用请求，由 Pi 执行对应实现，再把工具结果交还模型。

| 结构 | 职责 | `greet_user` 示例 |
| --- | --- | --- |
| `name` | 模型调用时使用的工具标识 | `greet_user` |
| `label` | 界面中显示的名称 | `Greet User` |
| `description` | 描述工具用途，帮助模型判断是否适用 | 为指定姓名返回问候语 |
| `parameters` | 定义工具输入的结构 | `Type.Object({ name: Type.String() })` 要求提供字符串 `name` |
| `execute()` | 工具真正执行的程序逻辑 | 根据 `params.name` 构造问候语 |
| `content` | 返回给模型的内容块 | 文本 `Hello, Alice!` |
| `details` | 工具结果附带的结构化数据 | 本例为空对象 `{}` |

**一轮调用如何完成：**

```text
用户提出问候任务
    ↓
LLM 生成工具调用：greet_user，参数 name="Alice"
    ↓
Pi 运行时将调用交给已注册的 execute()
    ↓
工具返回文本：Hello, Alice!
    ↓
结果加入上下文，LLM 根据结果生成最终回复
```

这里，LLM 负责理解任务、选择工具并生成参数；Extension 提供注册信息和实现代码；Pi 运行时负责执行与结果回传。模型生成工具调用意图，本身不会执行 TypeScript。

> [!important] 注册能力与选择行为是两件事
> 描述和参数结构帮助模型调用工具，但不保证模型在所有任务中都选择正确。显式要求调用 `greet_user` 可以验证执行链路；开放任务下的工具选择、错误参数和失败恢复，需要另行验证。

> [!warning] 简单文本工具的能力范围
> 问候工具示例只展示参数传入、执行和文本结果反馈。外部 API、副作用处理、复杂参数与权限控制是另外的工程问题；真实执行边界由运行环境决定。

完整代码及调用方法见[工具手册 5.9 节](./Agent工具使用手册.md#59-pi-extensions注册模型可调用的工具)，实际结果见[案例 008：自定义工具实践](./Agent实践案例/Agent实践记录.md#案例-008pi-自定义工具-greet_user)。接口依据：[Pi 官方 Extensions 说明](https://pi.dev/docs/latest/extensions)（2026-11-05 核对）。

## 3. Agent 与 LLM API 的关系

LLM API 中的常见机制与 Agent 的关系如下：

- **messages 多轮对话** → Agent 的消息历史与工具返回记录。
- **Streaming / SSE** → 向用户持续展示文本、进度或事件；流式输出本身不等于 Agent。
- **HTTP 错误、超时与 429** → 模型请求层的失败处理。
- **异常回滚** → 需要进一步区分“恢复消息历史”与“撤销已经真实执行的文件/数据库操作”。

新增的核心能力是：**在模型输出工具调用意图后，程序实际调度工具，并把结果交还给模型继续判断。**

> [!important] 恢复 messages 不等于回滚副作用
> `messages = old_messages` 只能恢复内存中的对话列表，不能回滚已经执行的 Shell、网络请求或数据库写入；外部副作用需要独立的事务、备份或补偿机制。

## 4. Agent 为什么需要停止条件？

并非“只要模型想继续，就可以一直调用工具”。实际系统至少需要考虑：

- **成功停止**：目标已完成，关键结果已有证据。
- **请求人工参与**：需要额外权限、缺少需求或触及高风险操作。
- **失败停止**：重复失败、无法修复、缺少必要依赖或输入。
- **预算停止**：超过步骤数、时间、Token/费用或其他资源上限。

在自己实现的 Agent 中，这些条件应由程序逻辑明确约束，而不是仅靠提示词要求“适时停止”。

## 5. 错误处理与重试：不能“一律重试”

| 失败类型 | 例子 | 处理方向 |
| --- | --- | --- |
| 模型调用暂时失败 | 429、部分超时、暂时性 5xx | 有限重试；遵守 `Retry-After`；避免无限退避 |
| 工具参数不正确 | 缺必填字段、路径错误 | 纠正参数；必要时让模型重新选择 |
| 权限不足 | 文件访问被拒、需要审批 | 停止或请求授权；不擅自提权 |
| 任务前提不成立 | 文件不存在、数据库与预期不一致 | 报告证据，重新确认目标 |
| 有外部副作用的执行失败 | 写数据库/发布/发送消息执行一半 | 先确认实际状态；考虑幂等、事务和补偿，**不要盲目重试** |

**重点**：API 429 的“退避重试”和对实际业务操作的“重新执行”是不同风险级别的问题。

## 6. 上下文不是“越多越好”

一个 Agent 在每一步通常需要知道：当前目标、最近工具结果、相关文件片段、已做决定和剩余任务。

上下文不等于全部聊天记录。一次请求里还可能包含系统指令、运行环境信息（工作目录、可用工具与 Skill 的描述）、工具结果等；这些内容共同占用上下文，所以简单任务也可能产生较高的 Token 用量。

DSH 的「轨迹」会把会话按系统、用户、上下文、工具、助手等类别展示，可作为观察上下文组成的直观示例（0.2.2-rc.1 界面观察）。

长任务会出现上下文过长、重复信息或历史噪声。常见做法包括：

- 只引入与当前问题相关的文件片段。
- 把已确认的进度整理成简短摘要，同时保留必要证据位置。
- 将可复查状态放入文件、测试或任务清单，而不是只依赖模型“记住”。

相关机制包括上下文压缩（compaction）、持久会话、记忆系统与多 Agent 协作。

### 6.1 子 Agent、会话分支与会话分叉

这些机制都与上下文有关，但解决的问题不同。下面的分支与分叉按 Pi 的行为区分；不同产品的命名与实现不一定相同。

#### 6.1.1 会话分支

**会话分支**允许从已有历史节点继续，保留不同的后续对话路径。两个分支共享分叉点之前的历史，后续消息分别发展：

```text
共同历史
├── 分支 A：继续原来的文件分析任务
└── 分支 B：尝试另一种解决方案
```

它适合比较方案、回到先前讨论重新尝试，并减少重复说明背景。返回历史节点后发送新消息，可以形成另一条路径，原有路径仍然保留。

#### 6.1.2 子 Agent

**子 Agent**由主 Agent 委派子任务，具有自己的任务执行上下文。主 Agent 负责说明任务与边界、传递所需信息、收集结果；能否并行、如何继承上下文和获得工具权限，取决于系统实现。

#### 6.1.3 机制对比

| 机制 | 主要用途 | 运行与历史关系 |
| --- | --- | --- |
| **Subagent（子 Agent）** | 主 Agent 委派子任务，等待并汇总结果 | 子 Agent 在各自线程工作，可并行；主 Agent 接收结果摘要，具体传入的上下文由实现与任务安排决定 |
| **Session Branch（会话分支）** | 在同一会话中保留不同的发展路径 | Pi 的 `/tree` 用于在同一会话树中导航；下一次请求使用活动路径，不会因此自动并行执行 |
| **Session Fork（会话分叉）** | 从既有历史创建独立会话 | Pi 的 `/fork` 从较早的用户消息创建新会话；`/clone` 从当前位置复制活动分支；创建新会话本身不等于任务委派 |
| **并行工具调用（Parallel Tool Calls）** | 同一轮执行多个互不依赖的工具调用 | 可并发执行，但不产生新的 Agent 或上下文分支 |

**并行工具调用与子 Agent 不在同一层。** 前者是在同一轮工具执行阶段同时运行多个互不依赖的工具，不产生新上下文；后者由主 Agent 委派任务，子 Agent 拥有独立执行过程，再把结果交回主 Agent 汇总。工具调度的并发见[1.2 节](#12-工具调度串行与并行)。

> [!note] DSH 的子智能体配置（0.2.2-rc.1 界面观察，尚未实际运行）
> 「插件 → 子智能体」中可见：最大递归深度 `1`、并行数量上限 `8`、允许 Agent 为子智能体选择模型（关闭）。
>
> 按官方仓库 `master` 分支的设置说明，委派工具沿用深度设置时，`1` 允许主 Agent 创建直接子 Agent。工具可以指定自己的深度限制。并行容量由同一主 Agent 下各层子 Agent 共享，主 Agent 本身不占名额。模型选择开关控制委派时能否自行选模型，实际使用的模型取决于委派工具和后端配置。[DSH 子智能体设置](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/client/ui-settings-subagent/README.md#use-this-package) · [DSH 子智能体运行时](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/subagent/subagent/README.md#activation-capacity)
>
> 提高并行上限可以让更多已委派的独立任务同时运行。模型调用次数和 Token 用量取决于实际委派的任务及其上下文。本次仅观察了界面，未验证该版本的运行行为。

例如，分析 Spring Boot 项目时，让两个子 Agent 分别调查 Controller / Service 与 Mapper / SQL，再汇总调用链，属于任务委派；从已有讨论另开一条路线，分别尝试不同分析方案，属于会话分支或分叉。

Codex 的子 Agent 适合可独立拆分的工作，也会增加 Token 消耗和协调成本。参见 [OpenAI 官方 Subagents 说明](https://learn.chatgpt.com/docs/agent-configuration/subagents)（2026-11-05 核对）。

#### 6.1.4 上下文隔离与文件隔离

**上下文分开不等于文件系统分开。** 共用目录时，一个 Agent 或分支修改文件后，其他会话也能读到新状态；返回历史节点不会恢复旧文件。

独立目录或 Git worktree 可以分开工作文件，实际访问权限仍需由沙箱、容器或操作系统控制。会话分支不能充当文件备份或安全隔离机制。

### 6.2 会话文件与当前上下文的区别

#### 6.2.1 会话记录的组织方式

Pi 将会话持久化为 `.jsonl`，用条目的 `id` / `parentId` 表示历史关系；同一文件可以保存多个分支。

**保存了完整历史，不等于每次请求都发送整份文件**：当前上下文沿活动分支组织，也可能包含压缩摘要或切换分支时生成的摘要。

#### 6.2.2 分支摘要与上下文压缩

切换分支时，选择不生成摘要，就不额外带入离开分支的摘要；选择生成摘要，则会把其中的工作概括后加入目标路径。

因此，不同分支既可以分别发展，也可以通过摘要传递相关信息，无需复制另一条分支的全部消息。**分支摘要**用于切换路线时保留信息，**上下文压缩**用于减少当前请求需要携带的历史，两者都不等于删除原始会话记录。参见 [Pi 官方摘要机制说明](https://pi.dev/docs/latest/compaction)。

这可以联系到 Python 多轮对话中的 `messages` 与 `trim_messages()`：它们都涉及选择模型本次看到的信息，但 Pi 的树形持久化与摘要机制有各自实现，不能简单视为同一种裁剪函数。

**官方依据（2026-11-05）**：[Pi 会话格式](https://pi.dev/docs/latest/session-format) · [会话与上下文](https://pi.dev/docs/latest/sessions)。操作入口见[工具手册 5.4 节](./Agent工具使用手册.md#54-操作文件终端命令与会话)。

### 6.3 会话分支的应用：同一任务的多方案比较

Session Branch 可用于从同一任务背景探索不同方案，保留各自的分析路线，再比较取舍。适用场景包括架构设计、Bug 根因假设、提示词与工具策略对比；普通小问题不必为了形式拆成多个分支。

#### 6.3.1 示例：三种分析路线

以“分析 Spring Boot 查询接口较慢的原因”为例，先在共同历史中提供接口代码、问题证据、目标和限制，再分别探索：

| 分支 | 分析方向 | 需要收集的证据 |
| --- | --- | --- |
| A：SQL 方案 | 查询语句与索引相关的问题 | SQL、执行计划及待验证的优化假设 |
| B：代码方案 | Controller / Service / Mapper 调用与数据处理 | 源码位置、调用关系与可能重复的操作 |
| C：缓存方案 | 缓存是否适合该接口 | 读写特点、数据时效要求和一致性约束 |

这是方案探索示例，不代表三个方向都必须采用，也不代表已取得性能收益。

#### 6.3.2 操作步骤

1. 固定共同起点：写清任务目标、代码基线、限制和验收标准，给对应节点添加标签。
2. 从共同起点继续，只分析方案 A，保存有证据支持的结论、待验证事项与主要取舍。
3. 用 `/tree` 返回同一个起点，选择 `No summary`，分别探索 B、C，避免额外带入前一条路线的摘要；尽量保持模型与其他比较条件一致。
4. 将各分支结论整理到同一份对比表，比较预期收益、实现复杂度、风险和维护成本。需要模型汇总时，显式提供各方案结论；它不会自动读取所有分支的后续消息。
5. 确定候选方案后，再在受控环境中实现和验证。未经实际测量的性能收益，只能作为预期或假设记录。

在 Pi 中，这些分支通常由用户逐一切换、逐一执行；保留三条路线不会自动启动三个并行 Agent。导航与摘要行为见 [Pi 官方会话说明](https://pi.dev/docs/latest/sessions)。

#### 6.3.3 如何选择机制

| 目标 | 可采用的机制 |
| --- | --- |
| 保留上下文，探索或审查另一条路线 | 会话分支 |
| 分别保存不同代码实现 | 从同一代码基线建立的独立 Git worktree 或测试目录 |
| 并行执行独立任务 | 子 Agent 或其他调度机制 |

代码实现期间，文件隔离应另行安排；会话分支不能替代代码版本管理。

更完整的应用场景与操作方法见[会话分支工作流](./Agent方法指南/会话分支工作流.md)，包括多假设排障、反向审查、失败路线回退和组合验证。

## 7. 安全：提示词不能替代执行边界

项目文件、网页、命令输出也可能包含误导 Agent 的指令，即**提示注入（Prompt Injection）**风险。实际安全控制应放在工具权限、隔离环境、凭据范围与审批机制中。

统一的日常安全规范只在[Agent工具使用手册·第 3 节](./Agent工具使用手册.md#3-安全基线与-git-检查)维护，此处不重复。

## 8. 原理观察示例

### 8.1 Pi：观察工具调用与结果反馈

选择一个**无敏感数据的隔离目录**，让 Pi 搜索一个文件并总结内容，观察：

1. 模型准备调用的工具及其参数；
2. 工具实际返回了什么；
3. 返回结果怎样影响下一步；
4. 如何结束或处理中途错误。

这些信息对应一次循环中的调用意图、真实执行、结果回传与停止判断。

### 8.2 DSH：观察插件与运行时的分工

通过具体插件示例，考察插件如何提供能力、如何注册与组合，以及它如何与 Agent 运行时交互。

### 8.3 理解检查

1. Agent 说“我要运行命令”，命令就已经执行了吗？为什么？
2. 工具返回错误后，模型可以做什么？运行时又必须控制什么？
3. 把 `messages` 恢复为旧列表，是否能撤销此前的数据库写入？
4. 为什么工作目录不等于安全沙箱？
