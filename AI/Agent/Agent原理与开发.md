## 1. 先掌握唯一主线：Agent Loop

```text
用户目标
   ↓
读取可用上下文（用户消息、历史、工具清单、工作目录等）
   ↓
模型判断：回答？还是调用工具？
   ├── 直接回答 → 输出并结束
   └── 选择工具 → 发出结构化工具调用请求
                     ↓
               运行环境检查权限并执行工具
                     ↓
               获取返回结果 / 错误
                     ↓
               将结果加入上下文
                     ↓
               再次交给模型判断 → 继续或结束
```

这是一幅**教学简图**：不同 Agent 的实际调度、工具权限、记忆和会话管理实现可能不同。

### 一次最小的工具调用发生了什么？

以“查看项目中有哪些测试文件”为例：

1. 用户提出目标，Agent 看到可用工具的名称和输入约束。
2. **模型**提出调用某个文件搜索工具，并提供参数；这一步本身并没有读文件。
3. **Agent 运行时 / Harness**验证工具调用，按权限策略实际访问文件系统。
4. 工具返回文件列表或错误，运行时把结果作为新消息加入上下文。
5. 模型依据新信息决定直接回答、再读某个文件，或者停止并请求更多信息。

**关键区别**：模型负责生成判断与调用意图；真正执行文件、Shell、网络等操作的是模型之外的代码与运行环境。**Tool Calling 不等于模型直接拥有操作系统权限。**

## 2. 把系统拆成五个部分

| 部分 | 负责什么 | 典型问题 |
| --- | --- | --- |
| **模型（Model）** | 根据上下文生成文本或工具调用意图 | 为什么选择这个工具？模型是否理解任务？ |
| **工具（Tools）** | 文件操作、Shell、HTTP、数据库等具体能力 | 输入与输出是什么？调用失败会返回什么？ |
| **运行时 / Harness** | 驱动循环、调用工具、调度消息、管理中止 | 谁真正执行命令？如何限制步骤数？ |
| **上下文与状态** | 对话历史、工具结果、任务进度、必要的持久化数据 | 很长的任务如何保留重要信息？ |
| **权限与执行环境** | 沙箱、身份、路径和网络边界、审批策略 | 哪些文件或服务不能访问？出错如何恢复？ |

先能够把一次真实的 Agent 操作映射到这五部分，再研究框架源码。

## 3. 与已经学习过的 LLM API 有什么关系？

已有的 Python + LLM API 学习可以直接迁移：

- **messages 多轮对话** → Agent 的消息历史与工具返回记录。
- **Streaming / SSE** → 向用户持续展示文本、进度或事件；流式输出本身不等于 Agent。
- **HTTP 错误、超时与 429** → 模型请求层的失败处理。
- **异常回滚** → 需要进一步区分“恢复消息历史”与“撤销已经真实执行的文件/数据库操作”。

新增的核心能力是：**在模型输出工具调用意图后，程序实际调度工具，并把结果交还给模型继续判断。**

> 重要：`messages = old_messages` 只能恢复内存中的对话列表，不能回滚已经执行的 Shell、网络请求或数据库写入；外部副作用需要独立的事务、备份或补偿机制。

## 4. Agent 为什么需要停止条件？

并非“只要模型想继续，就可以一直调用工具”。实际系统至少需要考虑：

- **成功停止**：目标已完成，关键结果已有证据。
- **请求人工参与**：需要额外权限、缺少需求或触及高风险操作。
- **失败停止**：重复失败、无法修复、缺少必要依赖或输入。
- **预算停止**：超过步骤数、时间、Token/费用或其他资源上限。

在自己实现的 Agent 中，这些条件应由程序逻辑明确约束，而不是仅靠提示词要求“适时停止”。

## 5. 错误处理与重试：不能“一律重试”

| 失败类型 | 例子 | 处理方向 |
| --- | --- | --- |
| 模型调用暂时失败 | 429、部分超时、暂时性 5xx | 有限重试；遵守 `Retry-After`；避免无限退避 |
| 工具参数不正确 | 缺必填字段、路径错误 | 纠正参数；必要时让模型重新选择 |
| 权限不足 | 文件访问被拒、需要审批 | 停止或请求授权；不擅自提权 |
| 任务前提不成立 | 文件不存在、数据库与预期不一致 | 报告证据，重新确认目标 |
| 有外部副作用的执行失败 | 写数据库/发布/发送消息执行一半 | 先确认实际状态；考虑幂等、事务和补偿，**不要盲目重试** |

**重点**：API 429 的“退避重试”和对实际业务操作的“重新执行”是不同风险级别的问题。

## 6. 上下文不是“越多越好”

一个 Agent 在每一步通常需要知道：当前目标、最近工具结果、相关文件片段、已做决定和剩余任务。

长任务会出现上下文过长、重复信息或历史噪声。常见做法包括：

- 只引入与当前问题相关的文件片段。
- 把已确认的进度整理成简短摘要，同时保留必要证据位置。
- 将可复查状态放入文件、测试或任务清单，而不是只依赖模型“记住”。

**待后续深入**：上下文压缩（compaction）、持久会话、记忆系统与多 Agent 协作。当前只需理解动机，不要求实现。

### 6.1 子 Agent、会话分支与会话分叉

这些机制都与上下文有关，但解决的问题不同。下面的分支与分叉按 Pi 的行为区分；不同产品的命名与实现不一定相同。

**会话分支**允许从已有历史节点继续，保留不同的后续对话路径。两个分支共享分叉点之前的历史，后续消息分别发展：

```text
共同历史
├── 分支 A：继续原来的文件分析任务
└── 分支 B：尝试另一种解决方案
```

它适合比较方案、回到先前讨论重新尝试，并减少重复说明背景。返回历史节点后发送新消息，可以形成另一条路径，原有路径仍然保留。

**子 Agent**由主 Agent 委派子任务，具有自己的任务执行上下文。主 Agent 负责说明任务与边界、传递所需信息、收集结果；能否并行、如何继承上下文和获得工具权限，取决于系统实现。

| 机制 | 主要用途 | 运行与历史关系 |
| --- | --- | --- |
| **Subagent（子 Agent）** | 主 Agent 委派子任务，等待并汇总结果 | 子 Agent 在各自线程工作，可并行；主 Agent 接收结果摘要，具体传入的上下文由实现与任务安排决定 |
| **Session Branch（会话分支）** | 在同一会话中保留不同的发展路径 | Pi 的 `/tree` 用于在同一会话树中导航；下一次请求使用活动路径，不会因此自动并行执行 |
| **Session Fork（会话分叉）** | 从既有历史创建独立会话 | Pi 的 `/fork` 从较早的用户消息创建新会话；`/clone` 从当前位置复制活动分支；创建新会话本身不等于任务委派 |

例如，分析 Spring Boot 项目时，让两个子 Agent 分别调查 Controller / Service 与 Mapper / SQL，再汇总调用链，属于任务委派；从已有讨论另开一条路线，分别尝试不同分析方案，属于会话分支或分叉。Codex 的子 Agent 适合可独立拆分的工作，也会增加 Token 消耗和协调成本。参见 [OpenAI 官方 Subagents 说明](https://learn.chatgpt.com/docs/agent-configuration/subagents)（2026-11-05 核对）。

**上下文分开不等于文件系统分开。** 共用目录时，一个 Agent 或分支修改文件后，其他会话也能读到新状态；返回历史节点不会恢复旧文件。独立目录或 Git worktree 可以分开工作文件，实际访问权限仍需由沙箱、容器或操作系统控制。会话分支不能充当文件备份或安全隔离机制。

### 6.2 会话文件与当前上下文的区别

Pi 将会话持久化为 `.jsonl`，用条目的 `id` / `parentId` 表示历史关系；同一文件可以保存多个分支。**保存了完整历史，不等于每次请求都发送整份文件**：当前上下文沿活动分支组织，也可能包含压缩摘要或切换分支时生成的摘要。

切换分支时，选择不生成摘要，就不额外带入离开分支的摘要；选择生成摘要，则会把其中的工作概括后加入目标路径。因此，不同分支既可以分别发展，也可以通过摘要传递相关信息，无需复制另一条分支的全部消息。**分支摘要**用于切换路线时保留信息，**上下文压缩**用于减少当前请求需要携带的历史，两者都不等于删除原始会话记录。参见 [Pi 官方摘要机制说明](https://pi.dev/docs/latest/compaction)。

这可以联系到 Python 多轮对话中的 `messages` 与 `trim_messages()`：它们都涉及选择模型本次看到的信息，但 Pi 的树形持久化与摘要机制有各自实现，不能简单视为同一种裁剪函数。

**官方依据（2026-11-05）**：[Pi 会话格式](https://pi.dev/docs/latest/session-format) · [会话与上下文](https://pi.dev/docs/latest/sessions)。操作入口见[工具手册 5.4 节](./Agent工具使用手册.md#54-操作文件终端命令与会话)。

### 6.3 会话分支的应用：同一任务的多方案比较

Session Branch 可用于从同一任务背景探索不同方案，保留各自的分析路线，再比较取舍。适用场景包括架构设计、Bug 根因假设、提示词与工具策略对比；普通小问题不必为了形式拆成多个分支。

以“分析 Spring Boot 查询接口较慢的原因”为例，先在共同历史中提供接口代码、问题证据、目标和限制，再分别探索：

| 分支 | 分析方向 | 需要收集的证据 |
| --- | --- | --- |
| A：SQL 方案 | 查询语句与索引相关的问题 | SQL、执行计划及待验证的优化假设 |
| B：代码方案 | Controller / Service / Mapper 调用与数据处理 | 源码位置、调用关系与可能重复的操作 |
| C：缓存方案 | 缓存是否适合该接口 | 读写特点、数据时效要求和一致性约束 |

这是方案探索示例，不代表三个方向都必须采用，也不代表已取得性能收益。

**操作方法：**

1. 固定共同起点：写清任务目标、代码基线、限制和验收标准，给对应节点添加标签。
2. 从共同起点继续，只分析方案 A，保存有证据支持的结论、待验证事项与主要取舍。
3. 用 `/tree` 返回同一个起点，选择 `No summary`，分别探索 B、C，避免额外带入前一条路线的摘要；尽量保持模型与其他比较条件一致。
4. 将各分支结论整理到同一份对比表，比较预期收益、实现复杂度、风险和维护成本。需要模型汇总时，显式提供各方案结论；它不会自动读取所有分支的后续消息。
5. 确定候选方案后，再在受控环境中实现和验证。未经实际测量的性能收益，只能作为预期或假设记录。

在 Pi 中，这些分支通常由用户逐一切换、逐一执行；保留三条路线不会自动启动三个并行 Agent。导航与摘要行为见 [Pi 官方会话说明](https://pi.dev/docs/latest/sessions)。

**按任务需要选择机制：** 方案探索可用会话分支；分别实现代码方案可用从同一代码基线建立的独立 Git worktree 或测试目录；需要并行执行时，再使用子 Agent 或其他调度机制。代码实现期间，文件隔离应另行安排，会话分支不能替代代码版本管理。

更完整的应用场景与操作方法见[会话分支工作流](./方法指南/会话分支工作流.md)，包括多假设排障、反向审查、失败路线回退和组合验证。

## 7. 安全：提示词不能替代执行边界

项目文件、网页、命令输出也可能包含误导 Agent 的指令，即**提示注入（Prompt Injection）**风险。实际安全控制应放在工具权限、隔离环境、凭据范围与审批机制中。

统一的日常安全规范只在[Agent工具使用手册·第 3 节](./Agent工具使用手册.md#3-安全基线本目录唯一的通用安全规范)维护，此处不重复。
