## 1. 最重要的原则：按风险决定交互方式

**不用每个小任务都先“出方案—确认—执行—再确认”**。关键是目标是否明确、权限是否恰当、风险是否可控。

| 模式 | 何时使用 | 建议行为 |
| --- | --- | --- |
| **探索模式** | 不清楚原因/需求，刚接手项目，要理解调用链 | **只分析**：定位文件、列证据与待验证假设，暂不改代码 |
| **执行模式** | 目标、可修改范围、验收标准已明确，属于低/中风险 | **直接完成并验证**：在授权范围内修改、运行允许的测试、报告 diff 与结果，不为每一处小改动重复确认 |
| **审批模式** | 删除或批量覆盖、真实数据库写入/迁移、部署、敏感凭据、未知脚本等 | **关键步骤前暂停**：说明影响、备份与回退方式，获得明确授权后再执行 |

**注意**：以上模式是**任务协作约定**，不是 Agent 的内置安全权限。真实边界依赖所用工具的审批、沙箱和操作系统权限；统一规则请查看[工具手册第 3 节](../Agent工具使用手册.md#3-安全基线与-git-检查)。

## 2. 最小任务卡：只写真正影响结果的信息

正常任务通常只需要 4 项，不必每次粘贴十几条规范：

```text
【目标】要完成的具体任务与预期行为。
【范围】相关项目/目录/入口文件；不能碰的部分。
【模式】探索（只读）/ 执行（可按范围直接改并验证）/ 审批（列出关键步骤等待授权）。
【验收】怎样证明做对了：测试、具体输出、调用链证据、diff 等。
```

当背景或权限复杂时再补充限制（不能联网、只能测试库等）。默认遵守工具手册中的安全基线。

### 2.1 示例：探索模式（Spring Boot 调用链）

```text
目标：分析 StudentController 某接口如何调用 Service 与 Mapper。
范围：只读当前 Spring Boot 项目的相关源码，不修改文件或真实数据库。
模式：探索。
验收：给出类/方法/路径、关键调用链和仍需验证的判断。
```

### 2.2 示例：执行模式（明确的小改动）

```text
目标：为指定 Service 的一个已存在方法补充单元测试。
范围：只允许修改对应测试目录；不改生产代码或依赖配置。
模式：执行。在范围内直接完成并运行本地安全测试，不必每一步等待确认。
验收：报告新增用例、真实执行命令、通过/失败结果及 git diff。
```

以上均为**可复用指令示例**，不是已执行记录。若测试会连接真实数据库或外部服务，应在运行前判断风险、调整到测试环境或请求单独批准。

## 3. 执行闭环：任务 → 证据 → 变更 → 验收

### 3.1 任务前

- 确认所在项目目录、当前分支与 `git status`；不要覆盖已有未提交工作。
- 确定是探索、执行还是审批模式，给出允许的操作范围。
- 选一项最重要的验收标准，例如“指定测试通过”或“能指出调用链的源文件位置”。

### 3.2 执行中

- 先阅读**与问题有关**的文件，不要求 Agent 遍历所有仓库内容。
- 让关键判断有证据：文件路径、具体报错、测试输出；不必要求它展示内部推理过程。
- 明确的小任务允许 Agent 连续完成、执行测试；出现越界、意外副作用或高风险操作时再停下来核对。
- 修复失败时先看日志与复现步骤，不让 Agent 无限制地“试到成功”。

### 3.3 验收时

1. 看实际修改的文件和主要 diff，辨认是否有无关改动。
2. 检查运行了哪些测试，以及真实退出状态、失败日志；**没运行就是没验证**。
3. 针对业务逻辑抽查关键行为和边界条件。
4. 最终留一条“做了什么—证据—尚未解决”的结论。

**常用检查命令与安全注意**统一见[工具手册第 3 节](../Agent工具使用手册.md#3-安全基线与-git-检查)。

对 Maven 项目，在确认测试环境不连接生产资源的前提下，可按实际项目选择：

```powershell
.\mvnw.cmd test  # 仓库自带 Maven Wrapper 时
mvn test         # 系统已安装并配置 Maven 时
```

## 4. 高频可复用工作流

| 任务 | 推荐模式 | 最重要的验收证据 |
| --- | --- | --- |
| 理解陌生 Java 项目 | 探索 | Controller → Service → Mapper 的真实路径、方法与调用关系 |
| 定位事务或 SQL Bug | 探索，定位根因后再转执行 | 报错/复现条件、具体源码位置、最小验证结果 |
| 补单元测试 | 执行（前提是测试环境安全） | 用例列表、实际测试输出、测试文件 diff |
| 小范围重构 | 执行 | 限定文件变更、测试通过、功能无回退证据 |
| 数据库迁移/部署 | 审批 | 影响范围、备份、恢复步骤与执行日志 |
| 比较 Codex、Pi、DSH | 探索 | 同一任务的正确性、工具调用、限制与成本说明 |

### 4.1 多分支探索与方案决策

从共同节点探索不同路线，分别用于假设验证、方案设计、反向审查或组合实验，再根据实际证据选择继续的位置。分支的价值还包括保留上下文、记录失败路径和回到合适节点重新调查。

详细方法已集中到[会话分支工作流](../Agent方法指南/会话分支工作流.md)，包含八类用法、通用步骤、典型场景，以及[组合实验的流程图与提示词](../Agent方法指南/会话分支工作流.md#4-多方案探索与组合验证)。

会话分支管理上下文，Git 管理代码版本；涉及不同实现时需另行安排工作文件，不能按分支意见的多少替代测试。

### 4.2 使用 Git 的重点

Agent 负责建议和执行**已授权的局部修改**；你负责确认变更是否正确，再决定是否提交。若出现 `non-fast-forward`，先检查本地与远端分叉情况，不因为 Agent 建议就直接强推。

## 5. 怎样记录实践：只记录可迁移经验

符合任意一条才值得记：学到可重复的技巧、解决复杂问题、出现典型误操作/幻觉、或发现有证据支持的工具差异。普通成功对话可以不记录。

### 5.1 快速记录（多数时候够用）

```markdown
- 日期：
- 工具 / 版本 / 环境：
- 任务与边界：
- 关键做法（1～2 句）：
- 证据（diff / 测试 / 路径）：
- 可复用结论：
```

### 5.2 典型案例（少量、必要时）

```markdown
### YYYY-MM-DD｜案例名称

**状态**：已验证 / 部分验证 / 未解决
**工具及环境**：

**目标与边界**：
- 期望：
- 允许操作：
- 验收标准：

**关键过程**：
1. Agent 的关键判断及对应证据：
2. 发生的一次遗漏/问题（如有）：
3. 采取的修正：

**真实验证**：
- 变更文件及关键 diff：
- 执行命令与实际结果：
- 尚未验证之处：

**下次可复用的方法**：
```

不保存密钥和整段敏感日志。每条案例必须明确区分“Agent 声称”与“自己验证”。

## 6. 下一次真实实践：Codex CLI 分析 Java 项目（【待实践】）

> 本节是**准备执行的任务卡**，不是一次已完成的 Java 项目分析案例。Codex CLI 已有 Git 笔记分析与 Python 代码修改记录，见[Agent实践记录](./Agent实践记录.md)。

**建议任务**：在熟悉的小型 Spring Boot 项目中，定位某个查询接口的 Controller → Service → Mapper 调用链。

**操作方式**：先在单独任务目录/可控仓库中验证 CLI 已安装，再选择探索模式；要求输出类名、方法名、文件路径和仍未确认的部分。

**可勾选的验收项**：

- [ ] `codex --version` 成功，记录版本。
- [ ] 确认工作目录与当前 Git 状态。
- [ ] Agent 引用了具体源文件位置。
- [ ] 至少人工核查两处调用关系。
- [ ] 确认未产生意外修改，并保存一条快速记录。

完成后把**实际任务、输出证据、错误或遗漏**写入第 7 节，不必继续堆叠提示词模板。
