# Agent 工作流与实践

> **定位**：把 Agent 作为工程工具，沉淀可以重复执行、可以验证的开发工作流，而不是保存聊天记录。
>
> **适用场景**：Java / Spring Boot / MyBatis 项目、Git 练习、Python + LLM API 项目，以及后续 Docker、Agent 开发实验。
>
> **建立日期**：2026-11-04。文中标为「示例」的任务是演示模板，**不是已经完成的个人实践**。
>
> **工具安装、版本和命令**：见 [Agent工具使用手册.md](./Agent工具使用手册.md)。

## 1. 使用理念：先明确目标，再考虑用哪个 Agent

通常只问四个问题：

1. **要完成什么？** 例如：理解调用链、排查 Bug、补测试、重构一个模块。
2. **允许做什么？** 只读、允许编辑、允许测试、是否允许联网/修改数据库。
3. **如何验收？** 文件位置、单元测试、预期行为、日志与 Git diff。
4. **怎样回退？** Git 分支、变更清单、备份、测试环境。

### 风险分级

| 级别 | 任务 | 建议做法 |
| --- | --- | --- |
| 低 | 解释代码、梳理调用链、总结文档 | 优先只读，要求引用文件位置 |
| 中 | 编写测试、修改少量代码、重构单模块 | 先建分支；限定范围；审查 diff 并运行测试 |
| 高 | 批量改文件、迁移数据、部署、接触凭据 | 使用隔离环境；审批关键步骤；保留备份与回滚方案 |

> 注意：Agent 的文字承诺不是安全边界。中高风险任务需借助工具审批、系统权限和沙箱。特别是 Pi 不应被默认当作“逐项审批”的安全环境。

## 2. 通用三阶段工作流

### 阶段 A：开始前（任务和边界）

- 明确当前项目目录和任务目标。
- 运行 `git status`，确认现有修改属于谁；必要时创建独立分支或 Git worktree。
- 写出**不允许**触碰的部分：例如数据库真实数据、密钥、其他业务模块。
- 明确验收标准：哪些测试通过、哪些文件变更是允许的。

**任务委托模板**：

```text
【目标】请完成：<一个可验证的具体任务>
【背景】项目是 <技术栈/入口/关键文件>。
【范围】只允许分析或修改 <目录/文件>；不要扩大改动范围。
【权限】<只读 / 可修改 / 可运行哪些命令>；高风险操作先申请确认。
【约束】不要触碰密钥、生产数据库或其他无关模块。
【输出】先说明思路；完成后列出改动文件、验证命令、结果与未解决问题。
【验收】<测试条件或预期行为>。
```

### 阶段 B：执行中（小步、有依据）

1. 先让 Agent 识别入口、依赖和相关文件。
2. 要求解释“为什么这样判断”，尽量给出文件路径和关键代码。
3. 一次只做一个小范围修改，避免同时重构多个无关模块。
4. 遇到失败先分析日志和报错，不要无限重试或反复改配置。
5. 看到危险命令、未知依赖下载或越界读取时，立即中止并人工判断。

### 阶段 C：完成后（独立验证）

在仓库目录中核对：

```powershell
git status
git diff
git diff --check
```

如果文件已经暂存，还需要 `git diff --cached`。逐项检查：

- 改动是否仅限于约定范围？是否误改了无关文件？
- 是否暴露了敏感信息，或新增了不必要的依赖？
- 是否存在未经验证的假设？
- 测试是否运行，结果是否可复现？
- 是否有副作用：数据库更新、生成文件、配置修改、网络操作？

**Maven 项目测试命令（按实际项目环境选一项）**：

```powershell
# 项目若包含 Maven Wrapper
.\mvnw.cmd test

# 或：系统已安装 Maven
mvn test
```

运行前确认测试是否连接真实数据库或外部服务。测试成功不代表业务逻辑一定正确，还需检查关键行为与边界情况。

## 3. 高频场景与可复用指令

### 3.1 理解陌生项目（只读）

**适用**：接手 Spring Boot 项目、复习旧项目、定位 Controller → Service → Mapper 链路。

```text
请只读分析当前 Spring Boot 项目。
1. 从指定 Controller 方法开始，追踪 Service 和 Mapper 调用。
2. 标出关键的类、方法和对应文件路径。
3. 区分已从源码确认的事实与需要验证的推测。
4. 不修改文件、不执行会改变环境状态的命令。
最后用简短步骤总结调用链。
```

**验收**：至少抽查两处关键调用与实际代码是否一致；不要仅凭自然语言总结。

### 3.2 定位 Bug（先分析，后修改）

**适用**：Spring 事务问题、MyBatis SQL 异常、接口返回不符合预期。

```text
现象：<错误信息/预期与实际结果>
复现条件：<输入和环境>
请先定位可能原因，按证据强弱排序。
每个原因说明对应代码位置、还缺什么证据、如何最小化验证。
第一轮只分析，不改代码和数据库。
```

**验收**：是否能稳定复现；是否找到了根因，而不是仅掩盖异常；有无新增回归测试。

### 3.3 编写或补充测试

```text
请先阅读现有测试风格，再为 <指定类/方法> 提议最小测试集。
列出正常路径、边界条件、异常路径。
先给测试方案，不修改生产代码。
获得许可后再写测试；运行结果需报告真实执行的命令和失败原因。
```

**验收**：测试覆盖关键行为；失败时给出可信的报错，不能把“没运行”写成“通过”。

### 3.4 小范围修改 / 重构

```text
目标：<单个问题>。
只允许修改 <明确路径>。
先给变更计划和可能风险，等我确认后再修改。
不进行与目标无关的重命名、格式化或依赖升级。
完成后给出文件变更列表、关键 diff、实际运行的测试。
```

**验收**：修改范围受控、行为不回退、未引入无关差异。

### 3.5 Agent 配合 Git

建议流程：

1. 开始前：`git status`，必要时创建任务分支。
2. Agent 工作：只让它处理当前任务，不同时混入其他调整。
3. 完成后：`git diff` 与 `git diff --check`，人工检查变更。
4. 运行测试：通过后再考虑提交；提交信息用一句话准确描述改动。
5. 发现错误：先判断哪些改动属于自己，**不要**直接运行可能丢失未提交工作的清理命令。

**经验重点**：Agent 可以提出提交建议，但提交前应该由自己确认 diff 和测试结果。若遇到 `non-fast-forward`，先弄清本地与远程分支的差异，不让 Agent 直接强推。

## 4. 怎样记录一次有价值的 Agent 实践

### 4.1 什么时候记录？

仅当满足下列任意一点：

- 新学会一个能够重复使用的 Agent 操作方式。
- 解决了一个较难的问题，过程有可迁移价值。
- 出现权限、安全、误改文件、幻觉等典型错误。
- 比较不同 Agent 完成同一任务，发现有证据支撑的差异。

普通的“解释一段代码成功”“帮我写一个简单函数”，无需单独记录。

### 4.2 两级记录法

**A. 30 秒简记**（用于多数情况）：

```markdown
- 日期：YYYY-MM-DD
- 工具 / 环境：Codex CLI / Windows PowerShell / 版本待填
- 任务：
- 关键做法：
- 验证结论：
- 下次可复用的一句话：
```

**B. 完整案例**（仅用于有代表性的实践）：

```markdown
### YYYY-MM-DD｜案例标题

**状态**：已验证 / 部分验证 / 未解决
**工具与版本**：
**环境与仓库**：只写必要信息，不记录私密地址和密钥

#### 任务与边界
- 目标：
- 允许读取/修改：
- 禁止操作：
- 验收标准：

#### 关键操作
1. ...
2. ...
（只摘必要的提示词、操作和命令，不复制完整会话。）

#### 证据与验证
- 相关文件 / 关键报错：
- 执行过的测试命令：
- 实际结果：
- Git 变更范围：

#### 复盘
- 有效的做法：
- Agent 的错误或限制：
- 下次如何改进：
```

**保存位置建议**：本文件保留工作流和案例索引。随着实践增加，再单独建 `实践案例/` 目录；在案例数很少时不要提前创建大量空文件。

### 4.3 演示案例（仅示例，尚未执行）

**任务**：用 Codex 分析 `@Transactional` 下内部调用为何没有预期回滚。

- **边界**：只读分析 Service、Mapper 相关代码；不修改数据库。
- **提问重点**：是否通过 Spring 代理调用、传播行为是否符合预期、异常是否被捕获、实际事务边界在哪。
- **验收**：独立核对注解位置、调用方式，必要时通过独立测试环境的集成测试确认。
- **待记录的结果**：只有实际跑完后，才写“已验证”及测试输出；在此之前不能当作个人经验。

## 5. 同任务比较 Codex / Pi / DSH（以后再做）

为了公平，统一使用**相同的只读任务、相同仓库版本、相似的上下文输入与权限边界**。模型和成本条件不同也要注明，不能把模型能力全部归因于 Agent 框架。

| 维度 | 如何评价 |
| --- | --- |
| 正确性 | 代码定位、事实判断是否可靠 |
| 可控性 | 是否遵守目录、操作权限边界；是否便于审查 |
| 可解释性 | 能否看到工具调用、依据和关键过程 |
| 工程效率 | 是否减少人工重复工作，不只看回答速度 |
| 结果验证 | 是否主动建议或实际执行合理的测试 |
| 学习价值 | 是否帮助理解 Agent Loop、工具、插件和上下文 |

只需比较一次典型任务，不必做大规模榜单或为每个工具单独创建项目。

## 6. 低成本实践节奏（与现有学习主线并行）

| 时段 | 重点 | 唯一最小产出 |
| --- | --- | --- |
| 第 1 次（约 30 分钟） | Codex CLI 只读代码分析 | 一条经核对的简记 |
| 第 2 次（约 30–45 分钟） | Codex 小改动 + Git diff / 测试 | 一次完整验证 |
| 第 3 次（约 30–45 分钟） | Pi 隔离环境体验工具调用 | 一张手写 Agent Loop 简图或简记 |
| 第 4 次（约 30–45 分钟） | Pi 扩展机制或 DSH 插件入门 | 解释一种扩展机制，不要求写插件 |
| 后续（按需） | 在真实项目中复用工作流 | 只追加新的经验与踩坑 |

**停止规则**：若这一周后端、课程或比赛任务已较重，就跳过 Agent 专项体验。日常已通过 Codex 完成的真实开发任务，可以直接作为实践素材，无需额外“刷工具”。
