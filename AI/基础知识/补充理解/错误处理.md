# 1. 学习目标与验证口径

LLM API 程序除了能发送问题、显示回答，还需要处理认证失败、HTTP 错误、网络中断、超时、响应格式异常和流式回答不完整等情况。

本阶段的目标是：**分类识别失败、保护消息历史、对适当错误进行有限重试，并给出准确提示。** 当前学习策略仅对 HTTP 429 自动重试；最多发送 3 次请求，默认等待 2、4 秒，有效整数 `Retry-After` 优先，单次等待超过 30 秒则停止。

阅读笔记时区分三种证据：

| 验证方式 | 能说明什么 |
|---|---|
| 静态检查 | 阅读代码、推导语法和控制流程，尚未执行对应路径 |
| Mock 模拟测试 | 用可控响应执行被测函数，检查调用、返回值和状态；不验证真实网络 |
| 真实环境运行 | 验证当时的源文件、配置与实际 API 交互 |

局部示例用于解释原理，不能代替完整源文件；模拟验证方法与边界输入见第 18 节。

## 2.1 返回前先完成状态恢复

函数走到末尾而没有遇到 `return`，也会隐式返回 `None`。但“返回失败信号”与“恢复历史消息”是两件事；不能仅靠函数结束代替回滚。

在 `ask_ai()` 的最终失败分支中，应先恢复历史，再结束函数：

```python
messages = old_messages
return None
```

这段代码位于函数内部，变量作用域和备份方式见第 8 节。若先执行 `return None`，后面的回滚就不会运行。成功分支也应明确 `return answer`，避免保存了回答却隐式返回 `None`。

# 3. HTTP 请求、响应与错误的不同层次

## 3.1 正常请求的基本路径

```text
用户输入问题
   ↓
构造 headers、JSON 请求体与 URL
   ↓
httpx.stream("POST", ...)
   ↓
收到 HTTP 响应状态和响应头
   ↓
response.raise_for_status()
   ↓
逐行读取 SSE 流、解析 JSON
   ↓
判断是否收到 [DONE]
   ↓
完整成功：保存回答并 return answer
```

要区分“**HTTP 请求成功**”与“**业务回答成功**”。HTTP 200 只能说明 HTTP 层返回了成功状态，不能保证返回了合法、完整、符合预期的 LLM 回答。

## 3.2 HTTP 状态码与 `raise_for_status()`

```python
with httpx.stream("POST", url, headers=headers, json=data, timeout=60.0) as response:
    response.raise_for_status()
    for line in response.iter_lines():
        ...
```

`response.raise_for_status()` 在 HTTPX 中对非成功状态（包括 3xx/4xx/5xx）报告 `httpx.HTTPStatusError`。它并不负责 JSON 结构校验，也不会自动对某个 HTTP 状态进行重试。

捕获状态码：

```python
except httpx.HTTPStatusError as e:
    status = e.response.status_code
    print(status)
```

这里 `e.response` 表示 HTTP 错误所对应的响应对象；因此可以读取 `.status_code`、`.headers` 等信息。

与之相对，`httpx.ConnectError` 等传输异常通常没有“服务端返回的 HTTP 响应”可读，不能一概使用 `e.response.status_code`。

## 3.3 三种不同的失败层次

| 层次 | 示例 | 检查方式 | 处理思路 |
|---|---|---|---|
| HTTP 层错误 | 401、429、500 | `raise_for_status()` / `HTTPStatusError` | 按状态码分类 |
| 网络/传输层错误 | `ConnectError`、`ReadTimeout` | `RequestError` / `TimeoutException` | 提示网络或超时，必要时回滚 |
| 数据/业务层错误 | 200，但 JSON 结构错误、业务字段标识失败、缺少 `[DONE]` | `json.loads()`、类型/字段校验、完成标记 | 拒绝错误内容，不保存不完整回答 |

有些 API 在 HTTP 200 的 JSON 响应体内仍然通过自定义字段表示业务失败，例如：

```json
{"success": false, "error": "model_not_available"}
```

这只是说明**部分 API 可能采用这种模式**，不能未经核实就认定 DeepSeek 的标准接口一定使用这一结构。应以实际 API 协议为准。

同理，非 2xx 响应可能携带 JSON 错误说明；`raise_for_status()` 只能先把 HTTP 状态报出来，并不会自动把其业务含义解释给用户。

# 4. HTTPX 异常类型与捕获顺序

## 4.1 需要建立的异常继承结构

```text
httpx.HTTPError
├── httpx.HTTPStatusError
│   └── 由 HTTP 响应状态触发（如 401、429、500）
└── httpx.RequestError
    └── httpx.TransportError
        ├── httpx.TimeoutException
        │   ├── httpx.ConnectTimeout
        │   ├── httpx.ReadTimeout
        │   ├── httpx.WriteTimeout
        │   └── httpx.PoolTimeout
        ├── httpx.ConnectError
        ├── httpx.ReadError
        └── 其他传输异常
```

图示突出课程涉及的主要类型，不代表 HTTPX 所有异常子类。

**重点区分**：`HTTPStatusError` 与 `RequestError` 是两条不同的错误分支。服务端明确响应了 HTTP 429，和本地无法建立连接，不应混成一种错误。

## 4.2 推荐的捕获顺序

```python
try:
    ...
except httpx.HTTPStatusError as e:
    ...
except httpx.ReadTimeout:
    ...
except httpx.ConnectTimeout:
    ...
except httpx.TimeoutException:
    ...
except httpx.RequestError:
    ...
except (json.JSONDecodeError, KeyError, IndexError, ValueError) as e:
    ...
```

顺序说明：

- `HTTPStatusError`：判断具体 HTTP 状态码，429 可走专门的有限重试逻辑；
- `ReadTimeout`：等待流式网络数据超时，可能已经输出过部分答案；
- `ConnectTimeout`：建立连接超时；
- `TimeoutException`：处理剩余的写超时、连接池等待超时等；
- `RequestError`：处理其他请求/传输异常；
- JSON 和字段异常：处理格式错误或应用自己主动抛出的校验错误。

`json.JSONDecodeError` 是 `ValueError` 的子类，放在同一个 `except (...)` 元组里略有冗余，但不妨碍正常捕获。

**审查要点**：避免重复 `RequestError` 捕获，同时保留 `TimeoutException`，覆盖 `WriteTimeout`、`PoolTimeout` 等其余超时。

## 4.3 为什么 `RequestError` 不必然意味着用户断网？

`RequestError` 范围较广。它既可能在建立连接前发生，也可能在收到 HTTP 200 和部分响应内容之后，传输过程中再发生。因此：

- 不能一看到 `RequestError` 就断言“用户网络断开”；
- 某个异常处理分支触发时，可能已经在终端打印了一部分文本；
- 对话历史恢复不等于撤销屏幕输出，也不等于撤销服务器已做的工作。

# 5. HTTP 状态码的分类处理

## 5.1 常见状态码速查

| 状态码 | 常见含义 | 当前项目的策略 | 提示原则 |
|---|---|---|---|
| 400 | 请求格式或参数不符合要求 | 不自动重试 | 检查请求参数 |
| 401 | 身份认证失败 | 不自动重试 | 检查 API Key 和认证配置 |
| 402 | 某些 API 使用该状态表示支付、余额等问题 | 不自动重试 | 结合 API 文档与响应体判断 |
| 422 | 某些 API 使用该状态表示参数语义无效 | 不自动重试 | 检查字段和值 |
| 429 | 请求受限流、并发或其他配额策略影响 | **有限重试** | 指数退避、`Retry-After`、等待上限 |
| 500 | 服务器内部错误 | 当前阶段不自动重试 | 提示稍后手动重试 |
| 503 | 服务暂时不可用 | 当前阶段未添加自动重试 | 提示服务暂不可用，稍后再试 |

状态码具有通用 HTTP 语义，但具体平台是否使用某个码、响应体包含哪些字段，应参考该平台实际文档。比如 429 背后的具体限制可能是请求速率、token 速率、并发等，并非一定只有一种原因。

## 5.2 用一个 `except` 内的 `if/elif` 分类

```python
except httpx.HTTPStatusError as e:
    status = e.response.status_code

    if status == 401:
        print("API 身份认证失败（401），请检查 API Key 和认证配置")
    elif status == 429:
        print("API 请求受到限流（429）")
    elif status == 500:
        print("API 服务器处理请求时发生内部错误（500），请稍后重试")
    else:
        print(f"HTTP 请求失败，状态码：{status}")

    messages = old_messages
    return None
```

上述片段是**不含重试的基础分类形式**，用于解释结构。最终 429 会有自己的 `continue` 和等待策略，详见后文。

为什么不写三个相同的 `except httpx.HTTPStatusError`？因为第一个匹配的 `except` 已经抓住了所有 `HTTPStatusError`，后两个不会再按状态码分类运行。

**易错点**：末尾的 `messages = old_messages`、`return None` 应与整个 `if/elif/else` 条件结构同层缩进，使 401、500、普通 HTTP 错误以及最终失败的 429 都能经过回滚。429 符合继续重试条件时用 `continue` 跳过末尾回滚。

# 6. 使用人工构造的 HTTP 响应验证错误处理

```python
import httpx

request = httpx.Request("POST", "https://example.com/chat")

for status in (401, 429, 500):
    response = httpx.Response(status, request=request)
    try:
        response.raise_for_status()
    except httpx.HTTPStatusError as e:
        print("捕获状态码：", e.response.status_code)
```

`httpx.Request(...)` 只创建请求描述，`httpx.Response(...)` 在内存中构造响应，两者都不发送网络请求。`request=request` 中，左边是参数名，右边是已创建的请求对象；`raise_for_status()` 根据合成状态码抛出异常。

真正调用 `httpx.post(...)` 或进入 `with httpx.stream(...)` 才会尝试发送请求。将合成响应注入 `ask_ai()` 后，还可验证提示、返回值及消息内容是否恢复，方法见第 18 节。

> 测试函数若只打印、没有显式返回值，结果就是 `None`；对它调用 `len()` 会抛出 `TypeError`。

# 7. JSON、SSE 与 API 响应结构校验

## 7.1 为什么 HTTP 200 之后还要校验？

HTTP 响应可以成功，但业务内容仍有问题：

- 收到不是合法 JSON 的文本；
- 顶层不是字典；
- `choices` 缺失；
- `choices` 为空列表或类型不对；
- `choices[0]` 不是字典；
- `delta` 不是字典；
- `content` 不是预期类型；
- 连接结束时始终没有 `[DONE]`。

因此要把“读到数据”和“确定能安全使用数据”分开。

## 7.2 `json.loads()` 与常见异常

```python
import json

chunk = json.loads('{"choices": [{"delta": {"content": "你好"}}]}')
```

JSON 语法错误时可能抛出 `json.JSONDecodeError`，属于 `ValueError` 家族。

## 7.3 `dict.get()` 默认值的真实行为

```python
# chunk 是一个字典，其中已经有 "choices" 这个键，它的值是空列表 []。
chunk = {"choices": []}

# get("choices", [{}]) 的意思是：
# 1. 找到 "choices" 这个键，就返回它对应的值。
# 2. 找不到这个键，才返回备用值 [{}]。
# 注意：[{}] 是“包含一个空字典的列表”，与空列表 [] 不同。
choices = chunk.get("choices", [{}])

# 这里键存在，所以取到原来的 []；值为空，不等于键不存在。
print(choices)  # 输出 []，不会使用备用值 [{}]。

# 对照：空字典中没有 "choices" 这个键，才会使用备用值。
print({}.get("choices", [{}]))  # 输出 [{}]。
```

`dict.get(key, default)` 只有在**键不存在**时才返回默认值，不能用它替代数据类型和长度检查。

```python
chunk = {"choices": []}
chunk.get("choices", [{}])[0]  # IndexError

chunk = {"choices": [None]}
chunk.get("choices", [{}])[0].get("delta", {})  # AttributeError
```

历史错题的关键区别：

| 数据结构 | 访问后的情况 |
|---|---|
| `choices` 键缺失 | `get(..., [{}])` 返回默认列表 |
| `choices: []` | 返回空列表，随后 `[0]` 报 `IndexError` |
| `choices: [None]` | `[0]` 得到 `None`，再 `.get()` 报 `AttributeError` |

不要把默认值理解成“值为空或非法时自动修正”。

## 7.4 安全校验模式

下面展示教学中强调的分步检查方式（适用于当前程序预期的含回复数据的事件）：

```python
if not isinstance(chunk, dict):
    raise ValueError("响应事件不是 JSON 对象")

choices = chunk.get("choices")
if not isinstance(choices, list) or not choices:
    raise ValueError("响应事件缺少有效的 choices")

first_choice = choices[0]
if not isinstance(first_choice, dict):
    raise ValueError("choices[0] 格式不正确")

delta = first_choice.get("delta", {})
if not isinstance(delta, dict):
    raise ValueError("delta 格式不正确")

content = delta.get("content")
if content is not None:
    if not isinstance(content, str):
        raise ValueError("content 应为字符串")
    print(content, end="", flush=True)
```

**适用范围说明**：这是一种针对当前接口预期格式的严格校验策略。某些流式 API 会发送不包含回复文本的事件，甚至允许 `choices: []` 的用量统计事件；若接口文档支持这种事件，应按协议专门跳过或处理，而非一概认定服务器错误。

## 7.5 SSE 的 `data:` 与 `[DONE]`

OpenAI 兼容的流式 Chat Completions 常见输出形式：

```text
data: {"choices":[{"delta":{"content":"你好"}}]}

data: {"choices":[{"delta":{"content":"！"}}]}

data: [DONE]
```

典型处理方式：

```python
completed = False
answer = ""

for line in response.iter_lines():
    if not line.startswith("data:"):
        continue

    payload = line[5:].strip()
    if payload == "[DONE]":
        completed = True
        break

    chunk = json.loads(payload)
    # 校验结构后再取内容
```

- `data:` 是 SSE 数据行的前缀；
- `[DONE]` 是当前 Chat Completions 流约定的结束标记；
- `[DONE]` 不是 JSON，不应传给 `json.loads()`；
- `break` 跳出读取行的循环，接着检查 `completed`；
- 正常关闭连接却没有收到 `[DONE]`，仍应视作当前程序的一次不完整响应。

这里的“网络数据块”和“SSE 事件/模型 token”不一定一一对应，后面讨论 `ReadTimeout` 时尤其需要注意。

# 8. 对话历史备份、恢复与状态一致性

## 8.1 失败为什么需要回滚消息？

对话式 LLM 通常将历史消息一起发送：

```python
messages = [
    {"role": "system", "content": "你是一个助手"},
    {"role": "user", "content": "你好"},
    {"role": "assistant", "content": "你好！"},
]
```

假设新输入为“解释 Spring Boot”。如果在发送前就把这条用户消息加入历史，而请求后来失败：

```python
messages.append({"role": "user", "content": "解释 Spring Boot"})
```

如果不回滚，下次用户继续提问时，历史中会保留一条**没有对应完整回答**的失败消息，导致后续上下文不一致。

本项目选择的基本策略是：**成功才提交本轮用户问题与完整 assistant 回答；失败恢复之前的历史消息。**

## 8.2 备份、添加、成功保存与失败恢复

```python
old_messages = messages.copy()  # 本轮请求之前的备份
messages.append({"role": "user", "content": question})

# ...请求和处理响应...

# 成功：保存完整回答
messages.append({"role": "assistant", "content": answer})
return answer

# 失败分支中：
messages = old_messages
return None
```

上述代码为了展示两个分支，**不是一个可以原样连续执行的完整函数**；实际应由 `try/except` 和 `if completed` 控制分别进入成功或失败路径。

## 8.3 为什么当前使用浅拷贝 `messages.copy()`？

本项目只追加消息或裁剪列表，**不原地修改旧消息字典**，因此 `messages.copy()` 足够用于失败回滚。浅拷贝共享内部对象的原理与反例，见 [浅拷贝与消息备份](异常处理.md#五浅拷贝与消息备份)。

## 8.4 `global messages` 与重新绑定变量

如果 `ask_ai()` 内使用：

```python
messages = old_messages
```

且 `messages` 定义在模块全局，那么需要：

```python
def ask_ai(question):
    global messages
    ...
```

理由：`messages.append(...)` 是修改已有列表对象；`messages = old_messages` 则是给变量**重新绑定一个列表对象**。后者在函数中会涉及作用域规则。

如果没有正确处理作用域，可能发生 `UnboundLocalError` 或只修改局部变量，从而无法恢复预期的全局历史。

更工程化的写法，是以后把 `messages` 放进类/状态容器中，或作为参数传入并显式返回新状态，减少依赖全局变量。本阶段暂时保留原有 `global` 设计，以便聚焦错误处理。

## 8.5 拼写错误不会自动报错，但会破坏回滚

```python
messsages = old_messages  # 错误：多写一个 s，赋值给了另一个变量。
```

Python 会把 `messsages` 当作合法变量名，原来的 `messages` 没有恢复。应写成 `messages = old_messages`，并检查实际消息内容，不能仅凭没有报错判断回滚成功。

## 8.6 `data["messages"]` 的引用细节

假设：

```python
old_messages = messages.copy()
messages.append({"role": "user", "content": question})
data = {"messages": messages}
```

此时 `data["messages"]` 和全局 `messages` 暂时指向同一个列表。后来若执行：

```python
messages = old_messages
```

只是将全局 `messages` 重新绑定到备份列表，并**不会自动更改** `data["messages"]` 中保存的原有列表引用。

这也是为什么 429 中间重试时推荐：

- 在循环外只追加一次用户问题；
- 尚有重试机会时，保持本轮请求状态不变，直接等待并 `continue`；
- 真正决定失败时才回滚 `messages` 并 `return None`。

这样 `data` 的消息上下文和每次重试内容保持一致，不会因为中途重绑列表造成混乱。

## 8.7 回滚的能力边界

`messages = old_messages` 只能恢复**本地**内存中的聊天记录：

- 不能撤销已经通过 `print()` 显示的部分文本；
- 不能撤销服务端已经执行过的计算；
- 不能保证服务端未扣费、未记录本次请求；
- 不会自动清理此前输出的半句回答。

所以流式输出失败时提示“**本轮对话未保存**”，而不是“之前发生的一切都被撤销”。

# 9. Timeout：超时的类别、配置及真实含义

## 9.1 HTTPX 的四种主要 Timeout

| 类型 | 阶段 | 含义 | 用户可理解的说法 |
|---|---|---|---|
| `ConnectTimeout` | 建立连接 | 在允许时间内没建立好连接 | 连接 API 服务器超时 |
| `ReadTimeout` | 等待网络接收数据 | 等下一段响应数据等得太久 | 读取模型响应超时 |
| `WriteTimeout` | 发送请求数据 | 发送请求数据的操作超时 | 发送请求超时 |
| `PoolTimeout` | 等待连接池资源 | 无法及时从连接池获得连接 | 请求资源等待超时 |

`WriteTimeout` 的“write”指**写入网络请求数据**，不是写入本地磁盘文件。

`PoolTimeout` 在使用共享 `httpx.Client`、`AsyncClient` 或并发请求时更容易理解：请求需要等待连接池中可用的连接资源。

## 9.2 `timeout=60.0` 的真正含义

```python
with httpx.stream("POST", url, timeout=60.0, ...) as response:
    ...
```

**不能简单理解为“整次调用总共最多运行 60 秒”。** HTTPX 超时主要约束连接、读取、写入和连接池等待等操作/无数据活动区间。

例如，流式回复持续数分钟，但网络数据持续到达、各次读取都没有超过读取超时阈值，依然可能不触发 `ReadTimeout`。

也就是说：

- `ReadTimeout` 更关注**等待下一批网络数据**的时间；
- 不严格等于“等待下一个 SSE 完整事件”或“等待下一个 token”的时间；
- 并不自动实现整个 API 调用的总耗时上限。

如果未来有业务上的总请求时间限制，需要另外设计总时限/取消机制，不能只依赖单个 `read` timeout。

## 9.3 分别设置四类超时

```python
import httpx

timeout = httpx.Timeout(
    connect=5.0,
    read=60.0,
    write=10.0,
    pool=5.0,
)

with httpx.stream(
    "POST",
    url,
    timeout=timeout,
    headers=headers,
    json=data,
) as response:
    ...
```

也可以使用带默认值和专门覆盖的形式：

```python
timeout = httpx.Timeout(60.0, connect=5.0)
```

这里 `timeout=timeout` 的左边是调用参数名，右边是代码中已创建的变量。**创建 `Timeout` 对象本身不会开始计时，也不会发起请求。**

## 9.4 `ReadTimeout` 可能发生在部分回答之后

假设：

```text
Spring Boot 是一个……
（流式输出已经显示到终端）
（随后等待下一批网络数据超时）
```

程序会抛出 `httpx.ReadTimeout`。根据本项目设计：

```python
except httpx.ReadTimeout:
    messages = old_messages
    print("\n读取超时：模型响应中断，本轮对话未保存")
    return None
```

关键事实：

1. `print(text, end="", flush=True)` 已经输出的文字仍留在屏幕上；
2. 局部变量 `answer` 可能已经累积了部分文本；
3. 本轮用户问题和未完成的 assistant 回复都不会被保存在历史消息中；
4. 不自动发起新的生成请求，避免重复输出和重复服务端处理。

注意 `\n` 的作用：如果已经打印了一部分没有换行的文本，错误提示应从新的一行开始，避免和模型回答黏在一起。

## 9.5 合成超时测试 vs. 真实超时

手动执行：

```python
request = httpx.Request("POST", "https://example.com")
raise httpx.ReadTimeout("模拟读取超时", request=request)
```

这会立即抛出合成异常，不等待真实超时。需要检查消息回滚等完整行为时，应按第 18 节将异常注入实际 `ask_ai()`。

# 10. 流式输出中断与 `[DONE]` 完整性校验

## 10.1 `completed` 为什么要单独存在？

```python
answer = ""
completed = False

for line in response.iter_lines():
    ...
    if payload == "[DONE]":
        completed = True
        break
```

接收了一部分数据，并不等于完整接收。`completed` 相当于**本轮流式响应的提交条件**。

在本程序采用的 Chat Completions SSE 协议中，只有观察到 `[DONE]` 才认为正常完成；即使 HTTP 200 的连接自行关闭，如果没看到结束标记，也不提交本轮历史。

## 10.2 完成与未完成时的处理

```python
print()  # 前面的流式 print 使用 end=""，先换行

if completed:
    messages.append({
        "role": "assistant",
        "content": answer,
    })
else:
    print("流式响应未正常结束：未收到结束标记，本轮对话未保存")
    messages = old_messages
    return None

return answer
```

- 成功分支：保存 assistant 回答，并通过函数 `return answer` 返回字符串；
- 失败分支：给出准确提示、回滚、返回 `None`；
- 不要删掉条件之后的 `return answer`，否则成功路径可能隐式返回 `None`。

## 10.3 缺少 `[DONE]` 与 `ReadTimeout` 不同

| 场景 | 能确定的事实 | 不应随意推断 |
|---|---|---|
| 捕获 `ReadTimeout` | 等待网络读取时发生超时异常 | 不能仅凭此断言服务器崩溃 |
| `completed is False` | 处理结束时，没有观察到协议要求的结束标记 | 不能断言一定是读取超时或某个具体服务故障 |

二者都可能出现“用户看到了部分回答，历史消息没有保存”的现象，但错误来源不同，提示措辞应准确。

## 10.4 为什么不能简单对任何流式异常自动重试？

流式输出不是原子操作。重试之前可能已经：

- 发送了完整或部分请求；
- 收到若干 SSE 片段；
- 把部分回答显示给用户；
- 消耗了服务端计算资源或 API 额度。

盲目重试可能产生：

```text
第一次：Spring Boot 是一个……（超时）
第二次：Spring Boot 是一个……（再次从头生成）
```

用户会看到重复文字，也可能产生额外消耗。当前基础版本采取保守策略：**只对 HTTP 429 按约定进行有限重试，不对已产生部分内容的 `ReadTimeout` 自动重试。**

# 11. HTTP 429：限流概念与重试适用性

## 11.1 HTTP 429 的含义

`429 Too Many Requests` 表示请求受到限制，通常与速率、并发或平台配额策略相关。不能仅靠状态码推出唯一原因。

常见限流模型的理解示例：

- **固定窗口**：例如一个 10 秒窗口最多接收 5 次请求；
- **滑动窗口**：统计最近连续时间区间内的调用；
- **令牌桶**：按速率补充令牌，有令牌才能请求，允许一定突发；
- **并发限制**：同时进行中的请求数达到阈值。

以上只是限流算法示例，**并非对 DeepSeek 当前限流策略或配额数值的断言**。

## 11.2 什么错误值得重试？

HTTP 状态码的处理策略统一见 [常见状态码速查](#51-常见状态码速查)。500、503 等短暂故障有时适合重试，但需结合请求语义判断；本项目仅对 429 实施有限重试。

网络故障可能发生在服务端已经处理请求之后，再次发送会重复执行或产生额外费用；已输出部分文本的读取超时还会重复显示回答。因此本项目不自动重试这些情况（见第 10.4 节），响应结构错误也不靠再次请求来解决。

## 11.3 `Retry-After` 是什么？

在 HTTP 响应头中，服务器有时提供建议等待时间：

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 10
```

常见格式：

1. 整数秒数：`Retry-After: 10`；
2. HTTP 日期：`Retry-After: Wed, 21 Oct 2026 07:28:00 GMT`。

本阶段**只实现整数秒数**。若返回日期格式，当前代码会按“不符合本版本秒数字符串格式”处理，使用指数退避备用策略。之后可以按标准扩展日期解析。

`Retry-After` 也不是成功保证：等待指定时间后重新请求，仍可能再次收到 429。

# 12. 有限重试循环：`for`、`continue`、`break` 与 `return`

## 12.1 `max_retries` 指“额外重试次数”

```python
max_retries = 2

for attempt in range(max_retries + 1):
    ...
```

`range(3)` 依次产生 `0、1、2`。含义：

| `attempt` | 行为 | 是否属于重试 |
|---|---|---|
| 0 | 初始请求 | 否 |
| 1 | 第一次重试 | 是 |
| 2 | 第二次重试 | 是 |

因此，`max_retries = 2` 表示**最多三次 HTTP 请求**，不是两次。

同理，若 `max_retries = 3`，在所有请求均被允许尝试的情况下，最多执行四次请求。

## 12.2 为什么一定把 `try/except` 放在循环里面？

推荐结构：

```python
for attempt in range(max_retries + 1):
    try:
        # 在这里发请求
        ...
    except httpx.HTTPStatusError as e:
        if e.response.status_code == 429 and attempt < max_retries:
            # 等待后再发起下一次请求
            continue
        # 最终失败
        messages = old_messages
        return None
```

当一次请求发生 429 时，异常必须能在**当前循环这一轮**被捕获和决定是否重试。若把整个循环包进一个外部 `try`，异常一旦跳到外层 `except`，通常就不容易回到原循环的下一轮。

## 12.3 `continue`、`break`、`return None` 的区别

| 语句 | 作用范围 | 用于本项目什么情况 |
|---|---|---|
| `continue` | 当前最近一层循环，转入下一轮 | 429 仍有重试机会，等待完成后继续 |
| `break` | 退出最近一层循环 | 可用于退出 SSE 行循环；不适合直接代替失败回滚 |
| `return None` | 结束整个函数 | 最终失败、等待超限或不能恢复的错误 |

### 本次学习的真实错误：超限时错误使用 `break`

曾出现：

```python
if wait_seconds > max_wait_seconds:
    print("等待时间过长")
    break
```

这只会跳出最近一层 `for attempt`，**不自动执行**循环中本来安排的 `messages = old_messages`。如果函数接着结束，本轮用户问题可能残留在历史记录中。

正确目标：

```python
if wait_seconds > max_wait_seconds:
    print("等待时间过长，请稍后再试")
    messages = old_messages
    return None
```

## 12.4 判断还有重试机会时，用 `<` 而不是 `<=`

```python
if attempt < max_retries:
    ...
```

设置 `max_retries = 2` 时：

| `attempt` | 判断 | 行为 |
|---|---|---|
| 0 | `0 < 2`，True | 可以等待后重试 |
| 1 | `1 < 2`，True | 可以等待后重试 |
| 2 | `2 < 2`，False | 不再等待，最终失败 |

若最后一轮还使用 `<=`，就可能出现“已经没有下一轮请求，却仍然执行等待”的错误。

## 12.5 请求上下文只添加一次，临时回答每轮重新初始化

推荐组织结构：

```python
old_messages = messages.copy()
messages.append({"role": "user", "content": question})

# 只有一次：组装请求上下文
data = {"messages": messages, "stream": True, ...}

for attempt in range(max_retries + 1):
    answer = ""
    completed = False
    try:
        # 每轮重新发送请求
        ...
```

- 本轮用户问题在循环外**只添加一次**；
- 每一次尝试是新的生成过程，`answer` 和 `completed` 必须在循环内重新初始化；
- 成功时才追加完整的 assistant 回复；
- 429 允许继续重试时不回滚；
- 最终失败才回滚并返回 `None`。

**如果把 `messages.append(user)` 写到循环内**，每次 429 后都有可能多添加一遍相同用户问题，污染对话上下文。

# 13. 指数退避与 `time.sleep()`

## 13.1 为什么不能立即重试？

初版代码曾只有：

```python
print("等待后重试")
continue
```

`print()` 只是输出文字，`continue` 只是开始下一轮循环，**两者都不会产生等待**。实际执行会变成：

```text
第 1 次请求 → 429
立即第 2 次请求 → 429
立即第 3 次请求 → 429
结束
```

这容易给已经限流的服务增加额外压力，也通常无法解决速率限制。

## 13.2 固定等待与指数退避

固定等待：

```python
time.sleep(2)
```

每次等待 2 秒。指数退避：

\[
t_n = t_0 \times 2^{n-1}
\]

本项目约定：初始等待时间 2 秒，`attempt` 从 0 开始，所以：

\[
\boxed{wait\_seconds = 2^{attempt+1}}
\]

```python
wait_seconds = 2 ** (attempt + 1)
print(f"等待 {wait_seconds} 秒后重试")
time.sleep(wait_seconds)
continue
```

| `attempt` | 公式 | 等待时间 |
|---|---|---|
| 0 | `2 ** 1` | 2 秒 |
| 1 | `2 ** 2` | 4 秒 |
| 2 | 无需计算 | 重试机会已耗尽 |

## 13.3 `time.sleep()` 的同步阻塞含义

```python
import time

time.sleep(2)
```

它会阻塞当前线程约 2 秒，之后程序才继续执行。对于本阶段同步版 `httpx.stream()` 是可用的基础方案。

在未来的异步代码中，通常应使用 `await asyncio.sleep(...)` 等异步等待方式，而不是在事件循环上直接用阻塞式 `time.sleep()`。

若缺少：

```python
import time
```

运行到 `time.sleep(...)` 时会触发 `NameError`。

## 13.4 字符串和整数不能直接相加

整数 `wait_seconds` 不能直接与字符串用 `+` 拼接，可用 f-string 输出：

```python
print(f"等待 {wait_seconds} 秒后重试")
```

# 14. `Retry-After`：读取、校验、备用策略及上限

## 14.1 从 `HTTPStatusError` 获取响应头

```python
retry_after = e.response.headers.get("Retry-After")
```

`e.response.headers` 是响应头集合。`.get(...)` 的值可能是：

| 响应头 | `retry_after` 的值 | 类型 |
|---|---|---|
| `Retry-After: 10` | `"10"` | `str` |
| 未提供该头 | `None` | `NoneType` |
| `Retry-After: abc` | `"abc"` | `str` |
| `Retry-After: 1.5` | `"1.5"` | `str` |
| HTTP 日期形式 | 类似 `"Wed, 21 Oct 2026 ... GMT"` | `str` |

不能直接执行：

```python
wait_seconds = int(retry_after)
```

因为：

```python
int("10")   # 10
int("abc")  # ValueError
int(None)   # TypeError
```

## 14.2 当前版本只接受 ASCII 非负整数秒数字符串

格式校验按以下顺序进行，完整安全处理代码集中在第 15.4 节：

- 先确认是字符串，防止对 `None` 调用字符串方法；
- `isascii()` 要求由 ASCII 字符构成；
- `isdigit()` 要求全部为数字字符；
- 二者结合，限定本阶段支持的普通 ASCII 数字秒数；
- 否则回退到指数退避。

**为什么同时使用 `isascii()` 和 `isdigit()`？** 某些 Unicode 数字字符可能通过 `isdigit()`，但并非当前约定的 ASCII 十进制数字，甚至未必能被 `int()` 按预期解析。

## 14.3 超过最大等待时间时：截断，还是放弃？

本项目设置：

```python
max_wait_seconds = 30
```

若服务器建议：

```http
Retry-After: 3600
```

有两种不同的决策：

**方案 A：截断**

```python
wait_seconds = min(wait_seconds, max_wait_seconds)
```

只等 30 秒再重试。问题是服务器建议等 3600 秒，客户端过早重试可能再次触发限流。

**方案 B：放弃本次自动重试——本项目采用**

```python
if wait_seconds > max_wait_seconds:
    print("服务器建议等待时间超过自动等待上限，请稍后再试")
    messages = old_messages
    return None
```

**好处**：

- 不让命令行程序长时间阻塞；
- 不擅自缩短服务器明确建议的等待时间；
- 把这次请求视为最终失败，恢复历史消息；
- 避免无意义地继续发送请求。

## 14.4 永远先算出 `wait_seconds`，再判断上限

历史真实错误：

```python
retry_after = e.response.headers.get("Retry-After")
if retry_after >= max_wait_seconds:  # 错误
    ...
```

`retry_after` 可能是 `"60"` 或 `None`，与整数 `30` 比较会抛出 `TypeError`。

另一个错误：

```python
if wait_seconds > max_wait_seconds:  # 错误：可能尚未赋值
    ...
else:
    wait_seconds = int(retry_after)
```

错误点：先使用 `wait_seconds`，后给它赋值。可能抛出 `UnboundLocalError`；如果上一轮循环赋过值，还可能错误地使用旧值。

**正确顺序**是：

```text
读取 Retry-After
    ↓
校验格式并确定当前轮 wait_seconds
    ↓
统一检查 wait_seconds 是否超限
    ↓
超限：回滚并 return None
未超限：sleep，然后 continue
```

# 15. `Retry-After` 超长数字：先比较、后转换

## 15.1 为什么普通 `isdigit()` 还不够？

```python
retry_after = "9999999999999999999999999999999999999999"
```

它是纯 ASCII 数字，但实际值显然远超 30 秒。特别是在极端情况下，如果数字字符串异常长，Python 对十进制字符串转整数有安全位数限制，`int(retry_after)` 可能触发 `ValueError`。

即使可以成功转换，把几百万秒先转换为巨大整数再和 30 比较，也没有业务必要。

**本项目的思路**：只需知道是否超过最大上限，无须把所有输入完整转换为整数。

## 15.2 规范化：去掉前导零

```python
normalized = retry_after.lstrip("0") or "0"
```

| 原始字符串 | 规范化结果 | 含义 |
|---|---|---|
| `"00000000000000000000020"` | `"20"` | 仍是 20 秒 |
| `"000"` | `"0"` | 0 秒 |
| `"999999"` | `"999999"` | 不变 |

- `lstrip("0")`：去掉开头连续的字符 `0`；
- 如果全部是零，就会得到空字符串 `""`；
- `or "0"`：将空结果规范化为 `"0"`。

## 15.3 用数字字符串长度和字典序比较

对于已经验证为**仅含 ASCII 十进制数字**、且**去掉了多余前导零**的非负整数字符串：

1. 位数更多 → 数值更大；
2. 位数相同 → 字典序更大的字符串代表更大的数值。

```python
limit = str(max_wait_seconds)

too_long = (
    len(normalized) > len(limit)
    or (
        len(normalized) == len(limit)
        and normalized > limit
    )
)
```

| `normalized` | 与 `"30"` 比较 | 是否超限 |
|---|---|---|
| `"10"` | 位数相等，字典序较小 | 否 |
| `"30"` | 相等 | 否 |
| `"60"` | 位数相等，字典序较大 | 是 |
| `"999999999999"` | 位数更多 | 是 |

**注意比较前提**：必须先校验类型和字符，再规范化。不能直接拿 `"abc"` 通过长度去比较数字。

## 15.4 最终安全处理结构

```python
retry_after = e.response.headers.get("Retry-After")
max_wait_seconds = 30

if (
    isinstance(retry_after, str)
    and retry_after.isascii()
    and retry_after.isdigit()
):
    normalized = retry_after.lstrip("0") or "0"
    limit = str(max_wait_seconds)

    too_long = (
        len(normalized) > len(limit)
        or (
            len(normalized) == len(limit)
            and normalized > limit
        )
    )

    if too_long:
        print("服务器建议等待时间超过 30 秒，请稍后再试")
        messages = old_messages
        return None

    wait_seconds = int(normalized)
else:
    wait_seconds = 2 ** (attempt + 1)

# 备用策略也应统一接受上限检查
if wait_seconds > max_wait_seconds:
    print("自动重试所需等待时间过长，请稍后再试")
    messages = old_messages
    return None

print(f"等待 {wait_seconds} 秒后重试")
time.sleep(wait_seconds)
continue
```

本段假定它处于 `ask_ai()` 函数中、`global messages` 已声明、`old_messages` 和 `attempt` 已定义，且外层已经通过 `if attempt < max_retries:` 判断仍有重试机会。

## 15.5 三个容易写错的地方

| 错误写法或顺序 | 原因 | 正确做法 |
|---|---|---|
| 未检查类型就 `retry_after.lstrip("0")` | 响应头缺失时是 `None`，会抛出 `AttributeError` | 先确认是字符串，再校验数字格式 |
| 未校验数字就比较字符串长度 | `"abc"` 也可能被误判为等待超限 | 非法格式使用指数退避 |
| 规范化后仍 `int(retry_after)` | 原始值含海量前导零时，仍可能触发转换长度限制 | 判断未超限后，转换 `int(normalized)` |

## 15.6 当前版本的明确功能边界

- 接受：`"0"`、`"10"`、`"00020"` 等 ASCII 非负整数秒数字符串；
- 超出 30 秒：停止自动重试，不进入 `int()` 转换巨大的秒数；
- 缺失或不符合支持格式：使用指数退避；
- **不解析** HTTP 日期形式的 `Retry-After`；
- 也没有做跨多次请求的**总等待时间**约束，只有单次等待上限和总重试次数约束；
- 如果将来开放用户自行配置很大的 `max_retries` 或 `max_wait_seconds`，应重新评估整数、时间预算及其他安全边界。

# 16. 面向用户的友好错误提示

## 16.1 只说已经知道的事实

提示应尽量说明：**发生了什么、程序如何处理、用户接下来能做什么**。单凭异常或状态码，不能断言 API Key 一定拼错、服务器整体崩溃，或用户本地一定断网。

| 场景 | 建议提示 |
|---|---|
| HTTP 401 | API 身份认证失败（401），请检查 API Key 和认证配置 |
| HTTP 429，次数耗尽 | API 请求受到限流（429），重试次数已用完，请稍后再试 |
| HTTP 429，等待过长 | 服务器建议等待时间超过 30 秒，已停止自动重试，请稍后再试 |
| HTTP 500 | API 服务器处理请求时发生内部错误（500），请稍后重试 |
| 其他 HTTP 错误 | HTTP 请求失败，状态码：XXX，请检查请求或稍后重试 |
| 连接超时 | 连接 API 服务器超时，本轮对话未保存 |
| 读取超时 | 读取模型响应超时，本轮对话未保存 |
| 其他网络请求异常 | 网络请求发生异常，请检查网络连接或稍后重试。本轮对话未保存 |
| JSON/结构错误 | 响应数据格式异常，本轮对话未保存 |
| SSE 结束标记缺失 | 流式响应未正常结束：未收到结束标记，本轮对话未保存 |

这些是提示设计建议；实际采用的文案以配套代码为准。

## 16.2 三个容易误导用户的细节

- **429 的两种退出原因要分开**：第三次仍返回 429 才是次数耗尽；第一次收到 `Retry-After: 60` 就退出，是等待超限。
- **“请稍后重试”是操作建议**：500 分支没有 `continue`，程序就不会自动重试。
- **缺少 `[DONE]` 不代表读取超时**：这里只能确认未观察到正常结束标记；异常差异见第 10.3 节。

流式文本使用 `end=""` 输出后，异常提示应以 `\n` 换行，避免粘在半段回答后面。提示“本轮对话未保存”指本地历史回滚，不代表屏幕文字被清除或服务端处理被撤销。

## 16.3 用户提示与开发者日志

`ConnectError`、`ReadError` 等异常名可用于开发排查，面向用户则应提供易懂的说明。后续可用 `logging` 记录异常类型、处理路径、重试次数和必要上下文，并对敏感内容脱敏。不要打印完整 API Key、Authorization 头或敏感请求体。

# 18. Mock 模拟测试的思路与方法

## 18.1 测试真实业务函数，替换网络与等待

Mock 用可控制的响应或异常触发指定分支，不依赖真实服务恰好出现错误。测试应运行配套代码中的 `ask_ai()`，替换它使用的 `httpx.stream` 与 `time.sleep`，检查调用次数、等待参数、返回值和消息历史。

手工 `raise` 适合验证单一捕获分支；Mock 业务函数适合验证整条处理路径。两者的证据范围见第 1 节。

下文用 `main` 表示导入后的配套代码模块。测试脚本可放在 `错误处理.py` 同一目录；导入准备见第 18.4 节。

## 18.2 用 `patch.object` 注入异常

```python
from unittest.mock import patch
import httpx

# main 是按第 18.4 节导入的业务模块；先完成导入，再运行此片段。
# 只创建请求描述，供异常记录请求信息；不会发送网络请求。
request = httpx.Request("POST", "https://example.com/chat")

# 在 with 范围内，把 main.httpx.stream 临时替换成模拟函数。
with patch.object(
    main.httpx,  # 要替换哪个对象上的属性。
    "stream",   # 要替换的属性名，即原来的网络请求函数。
    # side_effect 指定异常：调用替身时立即抛出，不真正连接服务器。
    side_effect=httpx.ConnectTimeout("模拟连接超时", request=request),
):
    # ask_ai 仍运行真实业务逻辑，但请求处会进入连接超时处理分支。
    result = main.ask_ai("新问题")
# 离开 with 后，原来的 stream 自动恢复。
```

`patch.object` 在 `with` 内临时替换模块实际使用的函数，退出后恢复。这里 `ask_ai()` 会运行，但网络出口被替换；应断言返回 `None`，且 `main.messages` 与调用前内容相同。

## 18.3 模拟部分输出后 `ReadTimeout`

用生成器先产生一条合法 SSE 内容，再抛出异常：

```python
# 沿用上一节的 httpx 和 request；调用此函数会得到一个生成器。
def fake_lines():
    # 第一次读取：先返回一行合法 SSE，让 ask_ai 显示部分回答。
    yield 'data: {"choices":[{"delta":{"content":"MyBatis 是一个持久层框架"}}]}'
    # 继续读取下一行时：抛出超时，模拟回答中途断开。
    raise httpx.ReadTimeout("模拟读取超时", request=request)
```

借助 `MagicMock` 把它接到上下文管理器上：

```python
from unittest.mock import MagicMock

# MagicMock 创建可配置的替身对象，这里让它扮演 HTTP 响应。
response = MagicMock()
# .return_value 指定调用结果：iter_lines() 返回上面定义的生成器。
response.iter_lines.return_value = fake_lines()

# stream() 返回的对象还要支持 with，所以另建一个上下文管理器替身。
context = MagicMock()
# ask_ai 进入 with ... as response 时，__enter__() 返回假的响应。
context.__enter__.return_value = response
# 离开内部 with 时不吞掉异常，让 ask_ai 的 except 接着处理。
context.__exit__.return_value = False

# 调用 stream() 时返回 context；mock_stream 用来查看调用记录。
with patch.object(main.httpx, "stream", return_value=context) as mock_stream:
    before = main.messages.copy()  # 保存调用前的历史，供回滚检查。
    result = main.ask_ai("新问题")
    # assert 表示检查条件；不满足时会抛出 AssertionError，说明测试失败。
    assert result is None                 # 请求失败，应返回 None。
    assert main.messages == before        # 检查消息内容确实恢复了。
    assert mock_stream.call_count == 1     # 只请求一次，没有自动重试。
```

`__exit__` 返回 `False`，使流内异常继续交给业务函数处理。这个场景还应检查：部分文字已经输出，随后出现读取超时提示，且没有第二次请求。消息回滚不会清除屏幕上的部分回答。

## 18.4 导入时执行代码的陷阱

配套代码用 `if __name__ == "__main__":` 保护交互循环，因此导入不会触发 `input()`。但它在**模块导入时**检查 `DEEPSEEK_API_KEY`，所以必须先准备环境变量：

```python
import os
from unittest.mock import patch

# 临时向环境变量写入虚假测试密钥，让模块通过导入时的配置检查。
# 退出 with 后，环境变量会恢复原状。
with patch.dict(os.environ, {"DEEPSEEK_API_KEY": "mock-test-key"}):
    # 导入同目录的 错误处理.py，并用 main 作为简短名称。
    import 错误处理 as main
# 这一步只准备模块；后续调用 ask_ai 前仍须替换 stream，阻断真实请求。
```

`mock-test-key` 是模拟用的虚假值。调用 `ask_ai()` 前仍需替换网络出口；准备环境变量本身不会阻止真实请求。

## 18.5 对重试和状态做实质断言

429 测试可通过 `stream` 的 `side_effect` 列表，按顺序提供“429、429、成功”的响应对象；这些对象需支持上下文管理器、`raise_for_status()` 和 `iter_lines()`。同时替换 `sleep`，检查真实传入的参数而不等待：

```python
# 替换 sleep 后，只记录“应该等多久”，测试不会真的等待。
with patch.object(main.time, "sleep") as mock_sleep:
    # 示意骨架：这里还需注入“429、429、成功”的响应并调用 ask_ai。
    ...

# call_args_list 保存每次 sleep 调用的参数；call.args[0] 是第一个位置参数。
# 例如 sleep(2)、sleep(4) 会提取成 [2, 4]，检查两次退避时间是否正确。
assert [call.args[0] for call in mock_sleep.call_args_list] == [2, 4]
```

除提示文字外，还应验证：

- HTTP 请求次数是否符合限制，耗尽后没有第四次请求；
- 成功返回完整字符串，用户问题只添加一次，assistant 回答正确保存；
- 最终失败返回 `None`，消息**内容**恢复到原状，而不仅是数量相同；
- 等待超限时没有调用 `sleep`，也没有再次请求；
- 缺少 `[DONE]` 时拒绝保存不完整回答。

测试对象应始终指向要验收的源文件，避免只测另写的简化函数；修改代码后，应重新验证受影响的场景。

## 18.6 容易遗漏的边界输入

| 场景 | 应验证的行为 |
|---|---|
| `Retry-After: 0`、`30`、`31` | 0 和 30 秒允许等待；31 秒超过上限，不等待、不重试并回滚 |
| `Retry-After: 10` | 优先采用服务器建议，不使用默认的 2 秒退避 |
| `Retry-After` 缺失或为 `abc` | 回退到指数退避，不直接进行整数转换 |
| 异常超长数字 | 在字符串阶段判断超限，不转换巨大整数 |
| 海量前导零后接 `20` | 去掉前导零后按 20 秒处理，不能仅凭原始长度判为超限 |
| HTTP 401 | 不自动重试；返回 `None`，恢复历史并提示认证失败 |

# 20. 错误处理决策流程

## 20.1 核心原则

> [!tip]
> **发请求前备份状态，发请求时按层分类错误，收到流数据后逐步校验，只在完整成功后提交；遇到可恢复的 429 才进行有限、有等待的重试，最终失败统一回滚并给出准确提示。**

## 20.2 决策流程

```text
开始 ask_ai(question)
    │
    ├── 备份 old_messages
    ├── 添加本轮 user 消息（仅一次）
    └── for attempt = 0, 1, 2
          │
          ├── 重置 answer、completed
          │
          └── 发起 HTTP 流式请求
               │
               ├── HTTP 401 / 500 / 其他不可重试 HTTP 错误
               │      └── 友好提示 → 回滚 → return None
               │
               ├── HTTP 429
               │      ├── 重试次数已用完
               │      │      └── 提示 → 回滚 → return None
               │      └── 仍有机会
               │             ├── 读取、验证 Retry-After
               │             ├── 无效/缺失：指数退避
               │             ├── 等待超限：提示 → 回滚 → return None
               │             └── sleep → continue
               │
               ├── ConnectTimeout / ReadTimeout / 其他请求异常
               │      └── 提示 → 回滚 → return None
               │
               └── HTTP 成功并读取 SSE
                      ├── JSON/SSE 结构非法
                      │      └── 提示 → 回滚 → return None
                      ├── 流结束但无 [DONE]
                      │      └── 提示 → 回滚 → return None
                      └── 收到 [DONE]
                             ├── 保存完整 assistant 回复
                             └── return answer
```
