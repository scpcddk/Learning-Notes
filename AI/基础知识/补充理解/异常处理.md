本文解释异常机制与消息备份；HTTP/API 分类、流式校验和重试策略见 [错误处理.md](错误处理.md)。

## 一、什么是异常处理？

程序运行时，可能因为输入不合法、网络请求失败、数据格式错误等原因出现异常。

例如：

```python
result = 10 / 0
```

运行时会产生 `ZeroDivisionError`，导致程序无法正常执行后续代码。

异常处理的作用是：**发现程序运行中的错误，并按照预先设计的方式进行处理，让程序能够合理地恢复或结束。**

## 二、`try` 和 `except`

### 1. 基本结构

```python
try:
    result = 10 / 0
    print("计算成功")
except ZeroDivisionError:
    print("不能除以零")

print("程序继续运行")
```

输出：

```text
不能除以零
程序继续运行
```

执行过程：

1. 执行 `try` 中的代码。
2. 除法产生异常，跳过 `try` 中剩余的代码。
3. 匹配对应的 `except`，执行异常处理。
4. 异常被捕获后，继续执行后续代码。

### 2. 捕获不同类型的异常

```python
try:
    number = int("hello")
    result = 10 / number
except ValueError:
    print("转换失败")
except ZeroDivisionError:
    print("不能除以零")
```

输出：

```text
转换失败
```

原因是 `int("hello")` 首先触发 `ValueError`，因此第二个 `except` 不会执行。

**注意：** 多个 `except` 可以分别处理不同类型的异常。一次异常发生后，通常只执行第一个匹配的处理分支。

### 3. 使用 `as e` 获取异常信息

```python
try:
    number = int("hello")
except ValueError as e:
    print(e)
    print(type(e).__name__)
```

- `e`：保存异常对象，可以查看具体错误信息。
- `type(e).__name__`：获取异常类型的名称。

这样可以帮助我们定位问题，而不只是告诉用户“程序出错了”。

### 4. 捕获顺序：子类先于父类

`except` 从上到下匹配，捕获某个异常类时，也会匹配它的子类。需要分别处理时，应把具体异常放在前面：

```python
try:
    result = 10 / 0
except ZeroDivisionError:
    print("不能除以零")
except ArithmeticError:
    print("其他算术错误")
```

`ZeroDivisionError` 是 `ArithmeticError` 的子类。如果把 `except ArithmeticError` 放在前面，它会先捕获除零异常，后面的专用分支便无法执行。

### 5. `else`：没有异常时执行

```python
try:
    number = int("12")
except ValueError:
    print("转换失败")
else:
    print("转换成功：", number)
```

`else` 只在 `try` 正常执行到末尾、没有抛出异常时执行；如果 `try` 提前 `return`、`break` 或 `continue`，也不会进入 `else`。

把成功后的操作放在 `else`，可以缩小 `try` 的范围，避免把后续操作的错误误当成前一步的失败。**`else` 中的异常不会被同一组 `except` 捕获**，仍会向外传播。

## 三、`raise`：主动抛出异常

当程序发现某种情况不应该继续执行时，可以主动抛出异常。

```python
try:
    raise ValueError("输入不合法")
except ValueError as e:
    print(e)
```

输出：

```text
输入不合法
```

需要区分：

| 语句 | 作用 |
|---|---|
| `raise` | 主动抛出异常 |
| `except` | 捕获匹配的异常 |
| `as e` | 获取异常对象，以便查看错误信息 |

在 AI API 项目中，如果 API 密钥不存在，可以主动抛出异常：

```python
import os

api_key = os.environ.get("DEEPSEEK_API_KEY")

if not api_key:
    raise RuntimeError("未设置 DEEPSEEK_API_KEY")
```

这里使用 `RuntimeError` 报告配置错误，避免程序带着无效配置继续运行。

## 四、`finally`：执行收尾代码

`finally` 中的代码通常无论 `try` 是否发生异常都会执行。

```python
try:
    print("A")
    raise ValueError("请求失败")
except ValueError:
    print("B")
finally:
    print("C")

print("D")
```

输出：

```text
A
B
C
D
```

执行顺序：

1. 执行 `try`，打印 `A`。
2. 主动抛出异常。
3. `except` 捕获异常，打印 `B`。
4. `finally` 执行，打印 `C`。
5. 程序继续执行，打印 `D`。

三个关键字的作用：

- `try`：执行可能出错的代码。
- `except`：处理匹配的异常。
- `finally`：执行收尾代码。

即使 `try` 或 `except` 中执行了 `return`，`finally` 通常仍会在函数返回前运行；异常未被捕获时，也会先执行收尾代码再继续传播。避免在 `finally` 中写 `return`，否则可能覆盖原来的返回值或异常。

注意：如果进程被强制终止等特殊情况发生，不能保证 `finally` 一定执行。

### AI API 项目中的应用

流式请求可以用上下文管理器管理资源：

```python
with httpx.stream(
    "POST",
    url,
    headers=headers,
    json=data,
    timeout=timeout
) as response:
    ...
```

这里的 `url`、`headers`、`data`、`timeout` 由请求配置提供。`with` 会在退出代码块时关闭流式响应，因此不需要为了关闭这个响应而额外添加 `finally`。

## 五、浅拷贝与消息备份

### 1. 使用 `copy()` 备份列表

```python
messages = ["旧消息"]
old_messages = messages.copy()

messages.append("新消息")

print(messages)
print(old_messages)
```

输出：

```text
['旧消息', '新消息']
['旧消息']
```

`copy()` 创建了一个新的外层列表。向 `messages` 追加元素，不会改变 `old_messages` 的长度。

### 2. 浅拷贝的局限

```python
messages = [
    {"role": "user", "content": "你好"}
]

old_messages = messages.copy()

messages[0]["content"] = "修改后的内容"

print(old_messages[0]["content"])
```

输出：

```text
修改后的内容
```

原因是：浅拷贝只复制外层列表，内层字典仍然是共享的。

| 操作 | 备份是否受到影响 |
|---|---|
| `messages.append(new_message)` | 不影响备份列表的长度 |
| `messages[0]["content"] = "新内容"` | 会影响备份中的同一个字典 |
| `messages = old_messages` | 让 `messages` 重新指向备份列表，但不能撤销字典内部已经发生的修改 |

如果需要独立备份嵌套字典，可以考虑深拷贝：

```python
import copy

old_messages = copy.deepcopy(messages)
```

`deepcopy()` 会递归复制嵌套对象，适用于需要隔离内部修改的情况。

## 六、异常处理在 AI API 项目中的应用

`ask_ai()` 将异常处理与消息状态管理结合：**请求前备份，只在完整成功后保存回答，最终失败恢复历史。**

| 情况 | 本地状态与返回值 |
|---|---|
| 收到协议结束标记 `[DONE]` | 保存完整助手回复，返回 `answer` 字符串 |
| 流关闭但未收到 `[DONE]` | 提示响应不完整，恢复历史，返回 `None` |
| 不再重试的 HTTP、网络或数据格式错误 | 按错误类型提示，恢复历史，返回 `None` |
| 429 仍有重试机会且等待未超限 | 等待后重试，保留本轮问题，避免重复添加 |

当前实现已分类捕获 HTTP 错误、具体超时、其他请求异常及解析错误，并在访问响应字段前逐层校验类型。

`None` 是该函数约定的失败信号，`""` 则是空字符串。调用者应使用 `answer is None` 判断失败；`if not answer` 会把空字符串也算进去。

消息回滚仅恢复本地历史，不清除已经打印的半段文本，也不撤销服务端处理。

## 七、异常捕获的基本原则

### 1. 捕获你知道如何处理的异常

例如：

```python
try:
    data = json.loads(content)
except json.JSONDecodeError as e:
    print(f"JSON 解析失败：{e}")
```

这种写法明确地处理了 JSON 解析失败的情况。

如果直接使用：

```python
try:
    data = json.loads(content)
except Exception:
    print("发生错误")
```

虽然能够捕获许多异常，但可能隐藏代码本身的问题，不利于调试。

这并不意味着绝不能使用 `except Exception`。在程序最外层，它可以用于记录意外错误，但应该保留必要的错误信息，并谨慎决定是否继续运行。

### 2. 先校验已知的数据约束

例如：

```python
delta = None
text = delta.get("content", "")
```

这会抛出 `AttributeError`，因为 `None` 没有 `.get()` 方法。对于已知可能变化的响应字段，应先检查其类型，再访问内容；不符合约定时可主动抛出 `ValueError`，交给数据格式错误分支处理。配套代码已经采用了这种逐层校验方式。

校验和异常捕获各有作用：前者拒绝不符合约定的数据，后者处理运行中发生的失败。是否恢复、终止或继续传播，应由具体错误决定，不能为让程序看起来正常而一律吞掉异常。
