# 站点乱码问题排查与修复全记录

> **问题**：前端页面“我的站点”列表中，站点名称显示为乱码。  
> **涉及环境**：阿里云 ECS `39.102.213.11`，Spring Boot 3.2.5，MySQL 8.0，Jackson 序列化，Docker 部署。  
> **最终结论**：问题根源有三层——Jackson 非 ASCII 转义、JAR 包内配置文件编码损坏、MySQL 连接字符集为 latin1。  

---

## 一、初始现象

1. 前端站点列表有两个站点：`ST-001`（示例换热站）和 `ST-LAB-001`（实验室测试站点）。
2. 前者显示正常中文，后者显示乱码。
3. 数据库直接查询 `station` 表，`ST-LAB-001` 的 `name` 字段已经是乱码（`å®žéªŒå®¤æµ‹è¯•ç«™ç‚¹`），`ST-001` 正常。

**初步判断**：`ST-LAB-001` 这条历史数据本身存错了，直接修复数据库即可。

---

## 二、第一轮尝试：手动修复数据库 + 排查 Jackson 转义

### 1.1 手动 UPDATE 数据库

```sql
UPDATE station SET name='实验室测试站点' WHERE station_id='ST-LAB-001';
```

执行后数据库显示正确中文。但**前端仍然乱码**。

### 1.2 检查后端接口返回

用 `curl` 直接访问后端 8080 端口：

```bash
curl -s http://localhost:8080/api/stations -H "Authorization: Bearer <token>"
```

返回的 JSON 中 `name` 字段是 `\u00e5\u00ae\u017e...` 这种 **Unicode 转义序列**，而不是直接的中文。

**思考**：数据库已经正确，但接口返回转义序列，说明问题出在后端的 JSON 序列化环节。

### 1.3 排查 Jackson 配置

- 检查 `application.properties`，没有 Jackson 相关配置。
- 检查 JAR 包，发现已有 `JacksonConfig.class`（后端之前添加过），但**启动日志中没有加载记录**。
- 怀疑 `@Bean @Primary ObjectMapper` 没有生效。

### 1.4 尝试外部配置文件关闭转义

在 `/opt/iot-backend/application.properties` 中添加：

```properties
spring.jackson.serialization.write-non-ascii-characters-as-unicode=false
```

重启后端 → **后端启动失败**（8080 端口无监听）。  
**原因**：Spring Boot 3.2.5 不支持该属性，导致 Jackson 启动报错，进而拖垮整个应用。  
**教训**：不是所有 Spring 官方文档中的属性在当前版本都能用，需要验证。

### 1.5 换用 `Jackson2ObjectMapperBuilderCustomizer`

让后端修改代码，使用 Customizer 方式：
```java
@Bean
public Jackson2ObjectMapperBuilderCustomizer jsonCustomizer() {
    return builder -> builder.featuresToDisable(
            JsonWriteFeature.ESCAPE_NON_ASCII.mappedFeature()
    );
}
```
重新打包部署后，**启动日志仍无加载记录，转义依旧**。

**结论**：Jackson 转义问题暂时无法通过外部配置解决，但这不是唯一的问题——后面发现即使 Jackson 不转义，数据库里的数据本身就是坏的。

## 三、第二轮排查：数据库数据为何反复变成乱码

### 2.1 发现数据被“神秘覆盖”

我们多次执行 `UPDATE` 把数据库改成正确中文，但只要重启后端，数据又变回乱码。  
**思考**：肯定有某个初始化代码在启动时往数据库写入了错误的值。

### 2.2 定位到 `LabBootstrapConfig`

在后端源码中找到 `LabBootstrapConfig.java`，其 `@PostConstruct` 方法会在启动时执行：

```java
Station station = stationRepository.findByStationId(stationCode)
    .orElseGet(() -> stationRepository.save(Station.builder()
            .stationId(stationCode)
            .name(stationName)  // 从配置文件读取
            .build()));
```

- `stationCode` = `ST-LAB-001`
- `stationName` = `${app.lab-bootstrap.station-name}`（默认 `实验室测试站点`）

**关键**：如果数据库已有 `ST-LAB-001`，不会覆盖；但如果数据库没有这条记录（比如被删了），就会用配置文件中的值重新创建。  
**但我们的情况是**：数据库明明有记录，重启后 `name` 却变了。这说明**配置文件中的 `station-name` 本身就是乱码**，JAR 包内的 `application-dev.properties` 中的中文在打包时被错误编码了。

### 2.3 验证：检查 JAR 包内的配置文件

```bash
jar tf /opt/iot-backend/app.jar | grep "application-dev"
cd /tmp
jar xf /opt/iot-backend/app.jar BOOT-INF/classes/application-dev.properties
cat BOOT-INF/classes/application-dev.properties | head -50
```

发现文件内容正常（中文未损坏？）——但实际上是**终端显示问题**，实际字节已经损坏。

### 2.4 尝试禁用自动初始化

在外部配置文件中添加：

```properties
app.lab-bootstrap.enabled=false
```

重启后端 → **数据仍被覆盖**。

**排查原因**：

- `systemctl cat iot-api` 确认启动命令中有 `--spring.config.additional-location=file:/opt/iot-backend/application.properties`，说明外部配置会被加载。
- 但 `application-dev.properties` 中**没有** `app.lab-bootstrap.enabled` 字段，代码中默认值是 `true`。
- 外部配置的 `false` 虽然被加载，但 profile 配置文件优先级更高，且 dev 文件中没有覆盖该字段，导致默认值 `true` 生效？  

**实际原因**：Spring Boot 加载配置的顺序问题，外部配置的 `false` 可能没有覆盖默认值。

### 2.5 用环境变量强制禁用
在 systemd 服务文件中添加：
```
Environment="APP_LAB_BOOTSTRAP_ENABLED=false"
```

重启后端 → **数据仍被覆盖**。  

**思考**：环境变量优先级最高，为什么还不行？因为**即使 `enabled=false` 跳过了 `LabBootstrapConfig`，`ST-001` 的乱码仍然存在**——这说明还有另一个初始化代码在操作 `ST-001`。

### 2.6 搜索 `ST-001` 的源头

`LabBootstrapConfig` 只处理 `ST-LAB-001`，不碰 `ST-001`。`ST-001` 的乱码一定来自另一个初始化类。  
在代码中搜索 `ST-001`、`示例换热站`，但未找到。  

**推测**：可能是早期版本直接通过 SQL 脚本导入的，或者另一个 `@PostConstruct` 没有被发现。

## 四、第三轮突破：发现 MySQL 连接字符集问题

### 4.1 检查 MySQL 字符集变量

```bash
docker exec -i mysql_8.0 mysql -u clouduser -pcloudpass123 -e "SHOW VARIABLES LIKE 'character_set%';"
```

输出：

| 变量 | 值 |
|------|-----|
| character_set_client | **latin1** |
| character_set_connection | **latin1** |
| character_set_results | **latin1** |
| character_set_database | utf8mb4 |
| character_set_server | utf8mb4 |

**震惊**：数据库和服务器都是 utf8mb4，但**客户端连接字符集是 latin1**！  
这意味着 JDBC 驱动在传输数据时，把 UTF-8 中文当作 Latin-1 处理，导致中文被错误解码。即使我们 `UPDATE` 成正确中文，后端读取时又被转成乱码。

### 4.2 尝试在 JDBC URL 中追加参数

修改 `application.properties`：

```properties
spring.datasource.url=jdbc:mysql://...?useUnicode=true&characterEncoding=utf-8&connectionCollation=utf8mb4_unicode_ci&characterSetResults=utf8
```
重启后端 → `character_set_results` 仍为 `latin1`。

### 4.3 用环境变量覆盖 JDBC URL
在 systemd 服务文件中设置 `SPRING_DATASOURCE_URL` 环境变量。  
重启后端 → 仍无效。

### 4.4 最终手段：修改 MySQL 容器全局配置
创建 `/tmp/my.cnf`：
```ini
[mysqld]
character-set-server=utf8mb4
collation-server=utf8mb4_unicode_ci
init_connect='SET NAMES utf8mb4'
skip-character-set-client-handshake
```

复制到容器并重启 MySQL：

```bash
docker cp /tmp/my.cnf mysql_8.0:/etc/mysql/conf.d/charset.cnf
docker restart mysql_8.0
```

再次检查字符集变量 → **全部变成 utf8mb4**。

## 五、最终修复：双管齐下

### 5.1 后端重新打包（修复 Maven 资源编码）
让后端在 `pom.xml` 中配置资源编码：
```xml
<properties>
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
</properties>
<build>
    <resources>
        <resource>
            <directory>src/main/resources</directory>
            <filtering>false</filtering>
        </resource>
    </resources>
</build>
```
重新打包部署，确保 JAR 包内的 `application-dev.properties` 中文正确。

### 5.2 清洗历史数据
数据库里已有的乱码记录需要手动修复。执行 Python 脚本，将 Latin-1 误存的 UTF-8 字节流转回正确编码：
```python
sql = f"UPDATE {table} SET {field} = CONVERT(CAST(CONVERT({field} USING latin1) AS BINARY) USING utf8mb4) WHERE ..."
```

### 5.3 验证
```bash
curl -s http://localhost:8080/api/stations
```
返回：
```json
{"name": "示例换热站", ...}
{"name": "实验室测试站点", ...}
```
前端页面刷新后，站点名称正常显示。

## 七、核心经验总结

1. **乱码问题要分层排查**：数据库存储 → JDBC 传输 → 后端序列化 → 前端渲染，逐层验证。
2. **不要轻信“配置文件已加载”**：用日志或环境变量验证，而不是猜测。
3. **Spring Boot 属性兼容性**：不是所有文档中的属性在当前版本都能用，需验证。
4. **Docker 容器的字符集陷阱**：即使数据库字符集正确，连接字符集也可能被客户端驱动或服务器端配置覆盖。
5. **初始化代码是双刃剑**：`@PostConstruct` 或 `CommandLineRunner` 在启动时自动执行，可能反复覆盖手动修复的数据。
6. **Maven 资源编码容易被忽略**：`<project.build.sourceEncoding>` 只影响 Java 源码，资源文件需要单独配置。
7. **终极武器：`skip-character-set-client-handshake`**：当 JDBC 参数无效时，直接在 MySQL 服务器端强制 UTF-8 通信。

---

**最终状态**：站点列表中文正常，Jackson 转义已关闭，MySQL 连接字符集全为 utf8mb4，自动初始化已禁用（环境变量），新部署的 JAR 包中配置文件编码正确。
