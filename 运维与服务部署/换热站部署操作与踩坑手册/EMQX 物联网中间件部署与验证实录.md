# EMQX 物联网中间件部署与验证实录

**项目背景**：在本地服务器（IP: `202.199.6.249`）上完成 EMQX 消息服务器的部署，并打通从配置到客户端验证的全链路，为后续 Jetson 边缘设备接入奠定基础。

---

## 第一阶段：安全基线搭建（认证配置）

**目标**：防止未授权设备接入，建立设备身份体系。

- **操作**：登录 EMQX Dashboard（`18083` 端口），在 `Access Control` -> `Authentication` 中启用内置数据库认证。
- **产出**：创建了设备专用账号 `jetson / jetson123456`。
- **技术决策**：选择内置数据库而非外部 Redis/MySQL，旨在减少初期外部依赖，快速验证业务逻辑。

---

## 第二阶段：协议选型与客户端的“踩坑”适配

**目标**：选择合适的 MQTT 客户端工具进行连接测试。

- **初步尝试（Web 端失败）**：最初选用 MQTTX Web 版，填写 `Host: mqtt://IP:1883` 连接失败
- **关键发现（协议限制）**：**浏览器环境（Web 端）无法直接使用 TCP 协议（1883端口）**，必须使用 WebSocket（WS/WSS）协议
- **配置调整**：转而配置 EMQX 的 WebSocket 监听器（8083/8084端口），并尝试通过 `ws://` 连接
- **再遇新规（平台限制）**：连接 `8083` 端口时，MQTTX Web 端提示 **“不再支持 ws 明文协议（安全警告）”**
- **最终决策**：放弃 Web 端，**切换至 MQTTX 桌面版**

> [!TIP]
> **面试话术提炼**：
> “在选型时，我意识到 Web 端 MQTT 客户端的局限性。由于浏览器沙箱环境无法直接发起 TCP 连接，必须通过 WebSocket 代理。同时，考虑到现代 Web 应用的安全策略强制要求加密（WSS），为了快速验证核心业务，我果断切换至桌面版客户端，避免了在自签名证书和代理配置上浪费时间。**这体现了我对 TCP/IP 协议栈和浏览器同源策略的深刻理解。**”

## 第三阶段：服务器端核心配置（监听器与网络打通）

**目标**：配置 EMQX 监听器并解决网络可达性问题。

- **排查与发现**：登录 Dashboard 检查 `Settings` -> `Listeners`，发现**监听器列表为空**。这是之前连接失败的**根本原因**。
- **解决方案**：手动创建监听器：
  - **TCP 监听器**：端口 `1883`，绑定 `0.0.0.0`（监听所有网卡）。
  - **WS/WSS 监听器**：端口 `8083/8084`，设置 MQTT Path 为 `/`。
- **网络连通性验证**：使用 Windows PowerShell 的 `Test-NetConnection` 命令，分别验证了 `1883` 和 `8084` 端口的连通性，均返回 `True`，**确认防火墙和网络路由正常**。

---

## 第四阶段：协议细节打磨（Path 路径纠错）

**目标**：解决 WebSocket 握手失败问题。

- **现象**：Web 端配置 `wss://IP:8084` 后依然报错 `400 BAD_REQUEST`。
- **根因分析**：EMQX 监听器配置的 `MQTT Path` 与客户端 `Path` 不匹配。EMQX 默认根路径为 `/`，而客户端填写了 `/mqtt`，导致路由寻址失败。
- **解决**：将 EMQX 监听器的 Path 明确设为 `/`，并同步将 MQTTX 客户端的 Path 字段**置空**（或填 `/`），握手成功。

## 面试/复盘核心收获总结

1.  **架构认知**：理解了不同 MQTT 协议（TCP vs WebSocket）的适用场景。设备端（Jetson）用 TCP（1883）性能最佳；浏览器端必须用 WebSocket。
2.  **排查方法论**：遇到连接问题，应遵循 **“自下而上”** 的排查顺序——先测网络连通性（`Test-NetConnection`），再查服务监听状态（Dashboard Listeners），最后看客户端协议匹配（Path/SSL）。
3.  **工具链思维**：懂得在“在线工具（Web）”与“本地工具（Desktop）”之间灵活切换，不钻牛角尖，以最快速度验证核心功能。
4.  **安全意识**：从一开始就引入认证机制（用户名/密码），拒绝匿名访问，符合物联网安全基线要求。
