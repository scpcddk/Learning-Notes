# 云平台部署与运维踩坑手册

> **服务器**：阿里云 ECS `39.102.213.11`，Ubuntu 22.04  
> **部署方式**：Docker + systemd  
> **维护人**：你（云平台/运维）

---

## 一、整体架构速查

| 组件 | 端口 | 部署方式 | 管理命令 |
|------|------|----------|----------|
| Nginx | 80 | Docker（`docker-nginx-1`） | `docker exec docker-nginx-1 nginx -s reload` |
| Spring Boot | 8080 | systemd（`iot-api`） | `systemctl restart iot-api` |
| MySQL | 3306 | Docker（`mysql_8.0`） | `docker restart mysql_8.0` |
| EMQX | 1883/18083 | Docker（`emqx`） | — |
| MinIO | 9000/9001 | Docker（`minio`） | — |
| SRS | 1935/8081 | Docker（`srs`） | `docker restart srs` |

### 按现象选择第一条排障证据

原手册记录的 502、403、页面旧版本和 WebSocket 失败曾出现在不同层。接手时先记出现时间、访问入口、失败路径、状态码和影响范围，再找对应的入口日志和上游日志。对登录请求只记录错误类型和请求编号，避免留下口令、Cookie 或 Token。只要还能读取证据，先做一轮对照，再决定是否需要重启。

| 首个现象 | 第一条证据 | 继续判断 |
|---|---|---|
| 所有请求都失败 | DNS、证书、入口端口和监听进程 | 确认请求到对的主机和服务 |
| 静态页正常，API 502 | Nginx error log 的 upstream 与错误 | 从代理所在网络查后端可达性、端口和协议 |
| 登录或部分接口 401/403 | 响应来自 Nginx 还是应用，应用安全日志是否匹配 | 区分认证失败、权限不足和路径被改写 |
| 静态文件 403 | Nginx 错误日志及进程身份 | 查路径遍历权限、文件可读性和安全上下文 |
| 页面仍旧 | 响应 HTML 引用的资源名、实际挂载 | 判断是缓存、旧目录、旧容器或另一入口 |
| WS 握手成功后断开 | 握手状态、客户端关闭原因、最后心跳 | 区分握手配置、业务认证、代理超时与客户端重连 |

## 二、最常踩的坑：502 Bad Gateway

### 问题描述

浏览器访问 `http://39.102.213.11/CloudPlatform/` 或 `/iot-api/` 时，页面返回 `502 Bad Gateway`，Nginx 无法连接后端。

### 底层原因

Nginx 容器通过 `proxy_pass` 转发请求到后端 `8080` 端口。如果**宿主机内网 IP 发生变化**（阿里云 ECS 重启或网络环境抖动），Nginx 配置中写死的旧 IP 就会失效，导致连接后端失败。

### 解决方案（按顺序尝试）

#### 1. 确认后端是否存活

```bash
# 确认监听端口或连通性，区分本机监听和远端可达。
ss -tlnp | grep 8080
```

有 `LISTEN` 只说明端口有进程监听，还需检查 HTTP 与业务健康状态，否则查看后端状态：

```bash
# 通过服务管理器操作目标进程，再核对它的状态和错误日志。
systemctl status iot-api
```

#### 2. 测试 Nginx 容器能否访问后端

```bash
# 在已运行容器内执行命令，命令使用容器里的路径和网络。
docker exec docker-nginx-1 curl -s -o /dev/null -w "%{http_code}" http://172.27.119.137:8080/
```

- 返回 **200**：该目标路径可达；核对实际失败路径与配置。修改后先 nginx -t，再重载：
  
  ```bash
  # 在已运行容器内执行命令，命令使用容器里的路径和网络。
  docker exec docker-nginx-1 nginx -s reload
  ```

- 返回 **000** 或超时：尚未取得 HTTP 响应；先查 curl 错误、端口、路由和防火墙，再核对 IP，不能据此断定 IP 改变。

**直连成功后的下一步**

最早的踩坑手册（`e0acef3`）记录了容器内直连成功后重载 Nginx 的排查分支。若直连响应正确而外部入口仍报 502，先比较入口请求命中的 upstream 与刚验证的地址和协议，确认配置语法和实际加载文件，再按手册重载并复测同一入口。


#### 3. 更新 Nginx 配置中的宿主机 IP

```bash
# 在已运行容器内执行命令，命令使用容器里的路径和网络。
NEW_IP=$(ip addr show eth0 | grep 'inet ' | awk '{print $2}' | cut -d/ -f1)
sed -i "s/172\.[0-9.]*:8080/$NEW_IP:8080/g" /opt/nginx/conf.d/default.conf
sed -i "s/172\.[0-9.]*:8081/$NEW_IP:8081/g" /opt/nginx/conf.d/default.conf
docker exec docker-nginx-1 nginx -s reload
```

### 预防措施

- 每次服务器重启后，先执行上述检查。
- 如果经常出现，考虑使用 `host.docker.internal` 替代固定 IP（需要 Docker 版本支持）。

### 从宿主和代理逐层确认后端状态

```bash
# 设置实际服务名。先读取状态和近期日志，留存用于比对的时间点。
: "${APP_SERVICE:?请设置 systemd 服务名}"
systemctl show "$APP_SERVICE" \
  -p ActiveState -p SubState -p MainPID -p WorkingDirectory
journalctl -u "$APP_SERVICE" --since "10 minutes ago" --no-pager -n 100
# 确认实际监听服务。需要完整进程信息时用有权限的账号查询。
ss -lntp
```

进程 `active` 仍可能没连上数据库或消息 Broker。只读业务接口应从宿主、代理网络和实际浏览器入口各验证一次。入口失败、宿主成功时优先查路由、代理上游和容器网络。宿主也失败时再看应用启动、端口和依赖。若服务确实通过 Docker 容器暴露，先用 `docker ps` 和 `docker inspect` 核对映射，不从容器列表的名字猜端口。

## 三、前端登录失败 / 页面空白 / 404

### 问题描述

登录接口返回 `404 Not Found`，或页面加载后白屏，控制台报错 `app.xxxx.js:404`。

### 底层原因

前端 `baseURL` 配置与 Nginx 代理路径不匹配。当前正确路径为 `/iot-api`，但前端代码中可能写死为 `/api` 或 `localhost`，导致请求直接发到前端静态服务器或错误路径，后端接口不可达。

### 解决方案

#### 1. 检查当前 JS 文件中的 baseURL

```bash
# 读取或筛选本地文件，按实际路径与输出核对关键字段。
grep -o 'baseURL:"[^"]*"' /opt/iot-frontend/CloudPlatform/js/app.*.js
```

#### 2. 如果输出包含 `/api`（错误），强制修改

```bash
# 找到最新 app 文件
NEW_APP=$(ls -t /opt/iot-frontend/CloudPlatform/js/app.*.js | head -1 | xargs basename)
sed -i 's|baseURL:"/api"|baseURL:"/iot-api"|g' /opt/iot-frontend/CloudPlatform/js/$NEW_APP
chattr +i /opt/iot-frontend/CloudPlatform/js/$NEW_APP
docker exec docker-nginx-1 nginx -s reload
```

#### 3. 确认 index.html 引用的 JS 文件与修改一致

```bash
# 读取或筛选本地文件，按实际路径与输出核对关键字段。
grep -oP 'src="/CloudPlatform/js/app\.[0-9a-f]+\.js"' /opt/iot-frontend/CloudPlatform/index.html
```

如果引用的不是刚才修改的文件，需要更新 index.html：

```bash
# 读取或筛选本地文件，按实际路径与输出核对关键字段。
sed -i "s|app\.[0-9a-f]*\.js|$NEW_APP|g" /opt/iot-frontend/CloudPlatform/index.html
```

### 永久解决

让前端同学在 **源码** `src/utils/request.js` 中直接写死：

```javascript
// 先看输入与依赖，再沿关键调用检查返回结果和异常分支。
baseURL: '/iot-api'
```

打包后必须验证：

```bash
# 读取或筛选本地文件，按实际路径与输出核对关键字段。
grep -o 'baseURL:"[^"]*"' dist/js/app.*.js
```

必须输出 `baseURL:"/iot-api"`，否则不要上传。

## 四、前端更新后页面不刷新

### 问题描述

前端重新打包上传后，浏览器访问仍然是旧页面，强制刷新、无痕模式均无效。

### 底层原因

浏览器缓存了旧版 `index.html`，而新上传的 `index.html` 中引用的 JS 文件名可能**没有变化**或**浏览器未重新获取**。只读目录挂载仍会反映宿主机修改，需检查挂载源、缓存及单文件 inode 替换。

### 解决方案

#### 1. 确认服务器返回的 index.html 是否为最新

```bash
# 从当前网络位置访问指定端点，结合状态码和响应内容判断结果。
curl -s http://localhost/CloudPlatform/ | grep -oP 'src="/CloudPlatform/js/app\.[0-9a-f]+\.js"'
```

对比本地 `dist/index.html` 中的引用，看文件名是否一致。

#### 2. 如果文件名一致但页面未更新，检查 JS 文件内容是否更新

```bash
# 从当前网络位置访问指定端点，结合状态码和响应内容判断结果。
curl -s http://localhost/CloudPlatform/js/app.xxxxx.js | grep -o 'baseURL:"[^"]*"'
```

#### 3. 如果内容也是新的，问题在浏览器缓存

- 使用**无痕模式**打开。
- `Ctrl+Shift+Del` 清除所有时间段的缓存和 Cookie。
- `Ctrl+F5` 强制刷新。
- 注销 Service Worker：`chrome://serviceworker-internals` → 找到站点 → Unregister。

#### 4. 如果容器内文件与宿主机不一致

先用 docker inspect 核对挂载源，再比较校验和。只读目录挂载可以保留；单文件挂载遇到原子替换时可能仍引用旧 inode，可改挂父目录。不要为排查缓存直接删除正在服务的 Nginx 容器。

**检查只读挂载和当前入口引用**

以前遇到过只读挂载导致容器里的修改无法同步。重建或拷贝文件前，用 inspect 查目标文件是镜像里的文件、可写层还是宿主绑定挂载。只读挂载应更新宿主端的正确来源，再按该服务的变更方式加载。镜像内置静态文件要更新镜像并确认新容器实际引用该镜像。若容器运行时被旧挂载覆盖，单独重建镜像不会让页面变新。

```bash
# 分辨是宿主文件、数据卷，还是镜像内路径在提供站点文件。
: "${NGINX_CONTAINER:?请设置实际 Nginx 容器名}"
docker inspect --format '{{range .Mounts}}{{println .Source "->" .Destination "RW=" .RW}}{{end}}' "$NGINX_CONTAINER"
# 从宿主上的实际发布目录核对入口与它引用的文件。
: "${SITE_DIR:?请设置实际前端发布目录}"
grep -oE '(src|href)="[^"]+\.(js|css)(\?[^"]*)?"' "$SITE_DIR/index.html"
```

旧版曾用 grep 核对 `/CloudPlatform/js/app.<哈希>.js`。现在仍可以用同样思路，但路径、文件名和后缀应从正在服务的入口 HTML 获取，不能沿用历史哈希。对照「宿主磁盘上的入口 → Nginx 读到的入口 → 浏览器收到的入口」。若旧页面只出现在一台电脑，检查本地缓存或 Service Worker；所有客户端都拿到旧入口时，先确认真实发布目录、反代节点和缓存层。


### 预防措施

- 前端上传文件后，立即执行服务器端验证。
- 确保 Nginx 配置中静态文件有 `Cache-Control: no-cache` 头（针对 HTML）。

## 五、数据库连接失败 / 启动报错

### 问题描述

后端启动日志出现 `Unknown database 'cloud_platform'` 或 `Access denied for user 'clouduser'`，服务反复重启。

### 底层原因

1. **数据库不存在**：云上 MySQL 可能丢失了业务库。
2. **权限不足**：`clouduser` 没有该库的访问权限。
3. **配置文件错误**：`application.properties` 中的数据库名或密码错误。

### 解决方案

#### 1. 检查数据库是否存在

```bash
# 在已运行容器内执行命令，命令使用容器里的路径和网络。
docker exec -i mysql_8.0 mysql -u root -p123456 -e "SHOW DATABASES;"
```

若没有 `cloud_platform`，需要从备份恢复。

#### 2. 恢复数据库（从本地上传 SQL 文件）

```powershell
# 核对远端账号、主机与目标路径。区分本机文件和远端文件。
scp cloud_platform.sql root@39.102.213.11:/root/
```

```bash
# 在已运行容器内执行命令，命令使用容器里的路径和网络。
docker exec -i mysql_8.0 mysql -u root -p123456 -e "CREATE DATABASE IF NOT EXISTS cloud_platform CHARACTER SET utf8mb4;"
docker exec -i mysql_8.0 mysql -u root -p123456 cloud_platform < /root/cloud_platform.sql
```

#### 3. 授权给 clouduser

```bash
# 在已运行容器内执行命令，命令使用容器里的路径和网络。
docker exec -i mysql_8.0 mysql -u root -p123456 -e "GRANT ALL PRIVILEGES ON cloud_platform.* TO 'clouduser'@'%'; FLUSH PRIVILEGES;"
```

#### 4. 检查外部配置文件

```bash
# 读取或筛选本地文件，按实际路径与输出核对关键字段。
grep "spring.datasource.url" /opt/iot-backend/application.properties
```

确保数据库名、用户名、密码与实际一致。

### 预防措施

- 定期备份数据库（`mysqldump`）。
- 将数据库初始化脚本纳入版本管理，并使用 Flyway 自动迁移。

## 六、后端 403 拦截登录 / WebSocket / API

### 问题描述

登录接口返回 `403 Forbidden`，WebSocket 连接被拒，或新接口无权限。

### 底层原因

Spring Security 配置中没有放行对应路径。常见于 Nginx 代理路径与后端真实路径不匹配时（如 `/iot-api/auth/login` 被转发为 `/auth/login` 但安全配置中放行的是 `/api/auth/login`）

### 解决方案

#### 1. 确认安全配置中已放行对应路径

在 `SecurityConfig.java` 的 `authorizeHttpRequests` 块中添加：

```java
.requestMatchers("/ws/**").permitAll()        // WebSocket
.requestMatchers("/stream/**").permitAll()    // 流媒体
.requestMatchers("/api/auth/login").permitAll()  // 登录
```

#### 2. 如果路径因 Nginx 重写而改变

检查 Nginx 配置：

```nginx
location /iot-api/ {
    proxy_pass http://172.27.119.137:8080/api/;  # 注意结尾的 /api/，会剥离 /iot-api 前缀
}
```

确保后端的 `SecurityConfig` 中放行的是重写后的路径（如 `/api/auth/login`）。

#### 3. 临时绕过（仅限测试）

仅在隔离的测试环境可临时调整授权规则；permitAll 不会自动关闭 CSRF、认证过滤器或 WebSocket Origin 校验，不能保证消除所有 403。示意：

```java
// 先看输入与依赖，再沿关键调用检查返回结果和异常分支。
.anyRequest().permitAll()
```

**看响应来自代理还是后端**

浏览器登录时收到 HTML 登录页、Nginx 403 页面和后端 JSON 401 是三种不同现象。先看 Content-Type、响应正文类型和请求是否命中上游。不要用放开全部权限、关闭认证或延长超时作为通用恢复手段。对历史账号恢复手顺，复现时使用批准的账户恢复流程，并核对服务配置是否需要同步新凭据。

## 七、WebSocket 连接报错

### 问题描述

前端控制台打印 `WebSocket connection to 'ws://.../ws/events' failed` 或 `403/502`。

### 底层原因

1. **Nginx 未配置 WebSocket 代理**：需要升级 HTTP 连接。
2. **Spring Security 拦截 WebSocket 握手**。
3. **后端没有实现 WebSocket 端点**。

### 解决方案

#### 1. Nginx 配置添加 WebSocket 支持

```nginx
# 根据 location 选择代理路径，核对 proxy_pass 的 URI、上游地址和转发头。
location /ws/ {
    proxy_pass http://172.27.119.137:8080/ws/;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
}
```

#### 2. 后端实现原生 WebSocket 端点

```java
// 先看输入与依赖，再沿关键调用检查返回结果和异常分支。
@Configuration
@EnableWebSocket
public class WebSocketConfig implements WebSocketConfigurer {
    @Override
    public void registerWebSocketHandlers(WebSocketHandlerRegistry registry) {
        registry.addHandler(new SimpleWebSocketHandler(), "/ws/events")
                .setAllowedOriginPatterns("*");
    }
}
```

#### 3. 安全配置放行 `/ws/**`

```java
// 先看输入与依赖，再沿关键调用检查返回结果和异常分支。
.requestMatchers("/ws/**").permitAll()
```

#### 4. 避免连接后发送纯文本消息

在后端 `SimpleWebSocketHandler` 中**不要发送 `"connected"` 等非 JSON 消息**，否则前端 `JSON.parse` 会报错。

## 八、MySQL 容器 root 密码遗忘

### 问题描述

执行 `docker exec -it mysql_8.0 mysql -u root -p` 时密码错误。

### 解决方案

#### 1. 查找启动时环境变量

```bash
# 在已运行容器内执行命令，命令使用容器里的路径和网络。
docker exec mysql_8.0 env | grep MYSQL_ROOT_PASSWORD
```

#### 2. 环境变量只反映首次初始化输入，不一定等于现有账号密码；先核对实例、账号 host 与秘密配置，再按恢复流程处理

```bash
# 在已运行容器内执行命令，命令使用容器里的路径和网络。
docker exec -it mysql_8.0 mysql -u root
```

#### 3. 如果仍失败，重置密码（需重启）

```bash
docker exec -it mysql_8.0 bash
# 在容器内
# --skip-grant-tables 属于 mysqld 服务端参数，不能传给 mysql 客户端。
# 先保存原容器镜像、配置和数据卷信息并备份；停止正常 MySQL 容器。
# 用相同版本、配置和数据卷启动隔离的临时 mysqld，启用
# --skip-grant-tables --skip-networking，通过 docker exec + 本地 socket 登录。
# 同一数据目录只能有一个 mysqld 进程，临时实例不能发布到公网。
# 登录后执行 SQL：
# FLUSH PRIVILEGES;
# ALTER USER 'root'@'localhost' IDENTIFIED BY '新密码';
# 停止临时实例后恢复原容器正常启动参数，再验证新密码。
```

然后重启容器。

## 九、文件权限问题导致 403 Forbidden

### 问题描述

访问静态资源（CSS/JS）返回 `403 Forbidden`，但文件存在。

### 底层原因

文件或目录权限不足（如 `700`），Nginx 进程无法读取。

### 解决方案

```bash
# 修改指定文件或目录的权限，核对实际运行服务的用户。
chmod -R 755 /opt/iot-frontend/CloudPlatform/
```

### 预防措施

每次上传文件后执行权限修复。

## 十、配置文件被锁定（Operation not permitted）

### 问题描述

写入 `/opt/nginx/conf.d/default.conf` 或 `application.properties` 时提示 `Operation not permitted`。

### 底层原因

之前为了防止误覆盖执行了 `chattr +i` 锁定文件。

### 解决方案

```bash
# 在对应终端执行，先替换示例路径或参数，再核对当前目录和退出状态。
chattr -i 文件路径
```

修改完成后可重新锁定。

## 十一、前端部署文件不一致导致混乱

### 问题描述

服务器上存在多个版本的 JS 文件，`index.html` 引用的文件不存在或 `baseURL` 错误。

### 底层原因

前端多次上传时未完整覆盖，导致新旧文件混杂。

### 解决方案

1. 在独立发布目录上传同一次构建生成的完整 dist，核对 index.html 引用的全部 JS/CSS 文件。
2. 验证后切换发布目录，保留上一版用于回滚；不能仅按文件时间保留一个 app.js 并手改引用，分包之间可能依赖不一致。
3. HTML 使用合理的缓存策略，带内容哈希的资源按发布生命周期保留，避免打开旧页面的客户端加载分包时 404。

### 预防措施

- 前端每次部署应**完整覆盖** `dist/` 目录，不要增量上传。
- 上传后立即验证。

## 十三、恢复配置的操作顺序

原速记脚本中的 `...` 不是有效 Nginx 语法，不能直接运行。恢复时使用完整的已验证备份：

1. 先保留当前文件，并确认备份包含现有其他业务（如 Dify）的全部路由。
2. 将选定备份恢复到 `/opt/nginx/conf.d/default.conf`。
3. 执行 `docker exec docker-nginx-1 nginx -t`，成功后才执行 reload；失败则还原文件。
4. 分别验证前端、实际后端接口和具体流媒体资源；静态 `/iot-api/` 200 不代表后端健康。
5. 仅在后端确有故障时检查日志并重启，避免把重启当作所有问题的通用修复。

### 先保留证据，再做最小变更与回退

原版中的「快速恢复脚本」适合拆成可复核的小步骤。生产或演示环境先保留已工作的组件，每次只改一个环节，并明确失败如何回退。可使用下面的顺序作为接手记录，检查项以本次实际部署为准。

1. **确认入口和版本。** 记录当前运行的镜像 ID、JAR 校验值、站点目录、配置来源和最近一次成功访问。
2. **检查依赖。** 在应用所在网络确认 MySQL、EMQX、MinIO 或 SRS 对应入口可达。用代表性业务读取证明权限和数据正确，避免只看端口通。
3. **检查代理配置。** 在实际 Nginx 实例执行 `nginx -t`。记录要改的 server 和 location、上游及回退文件。确认当前活动配置确实包含它。
4. **最小变更。** 比如只替换静态资源、只修一个上游端口，或只恢复外部应用配置。发现其他问题时先记录，再决定下一步，不同时改变三层。
5. **逐段复测。** 分别看首页、带哈希资源、只读 API、WebSocket 和需要的媒体入口。保留成功与失败各一条证据，避免只验证最容易通过的首页。
6. **条件回退。** 出现新一轮 5xx、登录大面积失败或数据指向错误库时，停下后续变更，恢复配套的旧产物和配置。涉及数据库写入与迁移时，先看兼容和数据状态，不能单靠换旧 JAR 完成回退。
7. **记录结果。** 写清恢复时间、版本、入口、受影响路径和留下的待办。下次交接可根据这条记录快速判断是故障重现还是新的问题。

### 故障记录模板

| 需要留下的内容 | 示例记录口径 |
|---|---|
| 原始现象 | 什么时间、在哪种网络、哪个 URL 或流失败 |
