# 打包备份操作手册

---

## 一、为什么要打包？打包的意义是什么？

### 1. 数据安全：防止服务器到期后数据永久丢失

云服务器到期后，虽然平台说会保留数据 15 天，但这 15 天不是绝对可靠的。如果忘记续费、或者平台清理数据，所有业务数据、配置、文件都会彻底消失。**打包备份是把数据掌握在自己手里**，即使服务器被销毁，本地还有完整的副本。

### 2. 可迁移性：未来能快速部署到新服务器

项目是持续开发的，以后可能会换云服务商、升级服务器配置、或者交付给公司自己部署。**有了完整的备份包，可以在任何一台新服务器上快速恢复整个环境**，不需要重新配置、重新调试，大幅节省时间。

### 3. 灾难恢复：应对意外故障

服务器可能因为误操作、系统崩溃、被攻击、磁盘损坏等原因导致数据不可用。**有了备份，可以随时回滚到之前的状态**，最大程度减少损失。

### 4. 版本管理：留存当前可用版本

在开发过程中，前后端代码不断更新，很多配置是反复调试后才正确的（比如 Nginx 反向代理、SRS 的 HLS 参数、EMQX 的用户认证）。**把这些“正确配置”打包保存下来，就是留住了当前可用的版本**，以后出现问题可以对照恢复。

### 5. 团队协作与交接

如果项目需要交付给其他人维护，或者新成员加入，**打包好的备份文件就是最清晰的交接文档**。对方拿到备份包，按照手册恢复，就能快速接手。

## 二、哪些东西需要打包？

| 类别 | 内容 | 备份文件 |
|------|------|----------|
| **数据库** | 站点信息、设备信息、告警记录、用户等 | `cloud_platform.sql` |
| **后端** | Java 应用 JAR 包 | `app.jar` |
| **后端配置** | 数据库连接、MinIO、流媒体地址等 | `application.properties` |
| **前端** | 部署的静态文件（HTML/JS/CSS） | `CloudPlatform/` |
| **Nginx 配置** | 反向代理规则 | `nginx/` 目录 |
| **服务管理** | 后端服务的 systemd 配置 | `iot-api.service` |
| **SRS 配置** | HLS 优化参数 | `srs.conf` |
| **Docker 启动记录** | 概览信息；完整参数另存 Compose/inspect（包含网络、卷、环境等） | `docker_ps.txt` |
| **EMQX 数据** | 设备认证用户、集群及配置状态（使用了认证就需要纳入备份） | `emqx_data.tar.gz` |

**为什么这些都要备份？**  
它们共同构成了项目的完整运行环境。缺少任何一个，新服务器上都无法恢复原来的功能。比如：
- 没有数据库，业务数据就没了；
- 没有 Nginx 配置，前端和后端就串不起来；
- 没有 SRS 配置，视频延迟就会回到默认的高延迟；
- 没有 systemd 服务文件，后端就无法开机自启。

### 备份清单应记录哪些恢复证据

交接时给每个备份项记录来源、导出时间、校验值、恢复目标和依赖版本。镜像、JAR、静态资源决定应用版本，数据库和对象存储决定业务状态，Compose、systemd 和 Nginx 配置决定它们如何连接。单独恢复一项时，先列出它需要的另外几项。

| 备份项 | 最小证据 | 复原时的检查 |
|---|---|---|
| MySQL | 导出退出码、归档大小、库表清单 | 在隔离库导入，抽查行数、中文和业务时间范围 |
| MinIO | Bucket 与对象数、代表性对象键及大小 | 按应用权限能访问，必要时核对版本及元数据 |
| 镜像与制品 | 镜像标签、ID、平台，JAR 和静态包校验值 | 目标平台可运行，入口实际提供的资源版本正确 |
| 部署配置 | 端口、卷、反代路径、应用配置来源 | 核对运行进程实际使用的文件，敏感值另行交付 |

## 三、打包操作步骤

### 在服务器上执行以下操作（假设已登录服务器）

#### 1. 创建备份目录

```bash
# 操作前区分源路径和目标路径，核对操作后的文件位置。
mkdir -p /root/backup
```

#### 2. 复制后端相关文件

```bash
# 操作前区分源路径和目标路径，核对操作后的文件位置。
cp /opt/iot-backend/app.jar /root/backup/
cp /opt/iot-backend/application.properties /root/backup/
```

#### 3. 复制前端静态文件

```bash
# 操作前区分源路径和目标路径，核对操作后的文件位置。
cp -r /opt/iot-frontend/CloudPlatform /root/backup/
```

#### 4. 复制 Nginx 配置

```bash
# 操作前区分源路径和目标路径，核对操作后的文件位置。
cp -r /opt/nginx /root/backup/
```

#### 5. 复制 systemd 服务文件

```bash
# 通过服务管理器操作目标进程，再核对它的状态和错误日志。
cp /etc/systemd/system/iot-api.service /root/backup/
```

#### 6. 导出数据库

```bash
# 在已运行容器内执行命令，命令使用容器里的路径和网络。
docker exec mysql_8.0 mysqldump --single-transaction --quick --routines --events --triggers -u root -p123456 cloud_platform > /root/backup/cloud_platform.sql
```

#### 7. 导出 SRS 配置

```bash
# 操作前区分源路径和目标路径，核对操作后的文件位置。
docker cp srs:/usr/local/srs/conf/srs.conf /root/backup/srs.conf
```

#### 8. 记录 Docker 容器启动信息

```bash
# 用容器状态和近期日志确认启动进度及失败位置。
docker ps -a --format "table {{.Names}}\t{{.Image}}\t{{.Ports}}\t{{.Command}}" > /root/backup/docker_ps.txt
```

#### 9. 导出 EMQX 数据 

```bash
# 冷备：安排停机窗口，停止 EMQX 后再复制，避免运行中数据文件不一致
docker stop emqx
docker cp emqx:/opt/emqx/data /root/backup/emqx_data
docker start emqx

# 打包
cd /root/backup
tar -czf emqx_data.tar.gz emqx_data
rm -rf emqx_data  # 删除临时目录，保留压缩包
```

还需按实际使用补充：MinIO 对象数据及 IAM/桶策略、EMQX 的 etc 配置、容器持久化卷、systemd drop-in/环境文件、确切镜像 ID 或离线镜像。docker save 不包含运行数据，docker ps 也不能重建全部启动参数。数据库一致性导出期间避免并发 DDL；备份范围内有非事务表时需另行安排一致性方案。

#### 10. 打包所有备份文件

```bash
# 核对归档输入和输出位置，完成后检查文件清单。
cd /root/backup
tar -czf /root/cloud_full_backup_$(date +%Y%m%d).tar.gz .
```

#### 11. 下载压缩包到本地

在本地 PowerShell 执行：

```powershell
# 核对远端账号、主机与目标路径。区分本机文件和远端文件。
scp root@服务器IP:/root/cloud_full_backup_*.tar.gz C:\Users\Lenovo\Desktop\
```

## 四、打包后如何验证？

下载完成后，在本地解压压缩包，确认里面有：

- `app.jar`
- `application.properties`
- `cloud_platform.sql`
- `CloudPlatform/`（前端文件）
- `nginx/`（Nginx 配置）
- `iot-api.service`
- `srs.conf`
- `docker_ps.txt`
- `emqx_data.tar.gz`（如果导出了）

文件齐全只是完整性初检。还需检查导出退出码、归档可解包、校验和及隔离环境恢复结果，确认业务数据与账号权限可恢复。

### 检查归档并做隔离试恢复

```bash
# 在归档目录按交接清单校验文件，列出压缩包中的内容。
: "${ARCHIVE_FILE:?请设置已存在的归档文件}"
sha256sum -c SHA256SUMS
tar -tzf "$ARCHIVE_FILE"
```

归档清单里应能看到约定的目录和必要文件。正式恢复前，在空的演练目录解包，使用独立容器、库名和卷做试恢复。能打开包只证明格式可读，应用能否运行要看数据库、对象和入口的实际复测。若数据库行引用 MinIO 对象，最好在同一停写窗口取两份备份，至少记录各自截止时间，避免在恢复后遇到有引用但无对象。

验收依次看进程、依赖、业务样本和外部入口，记录恢复耗时、缺失项和退回上一版所需的文件。机器仍可访问时优先做一次小范围试恢复，交接时把过程和结果一起交付。 [Docker 镜像归档](https://docs.docker.com/reference/cli/docker/image/save/) · [MySQL 导出选项](https://dev.mysql.com/doc/refman/8.0/en/mysqldump.html)

## 五、注意事项

1. **打包前确认数据库是最新状态**：如果期间有人在使用系统，先停止写入或选在低峰期导出。
2. **备份文件不要只存在服务器上**：一定要下载到本地或网盘，防止服务器故障导致备份也丢失。
3. **定期备份**：项目每次重大更新后，都应重新打包备份一次，保持备份版本与线上一致。
4. **记录当前服务器 IP 和安全组规则**：虽然无法打包，但要截图或记录，方便新服务器配置。
5. **测试恢复流程**：如果时间允许，建议在新服务器上做一次恢复演练，确保备份文件可用。

### 复核归档路径、权限与时间点

恢复前核对包内是相对路径还是原机器的绝对路径，是否含符号链接、敏感配置和需要保持权限的目录。备份归档不宜与唯一的生产数据放在同一块磁盘。交接副本应能独立校验，也应有明确保管人。每个样本写清备份最晚覆盖到什么时候、试恢复耗时多少、需要哪些凭据或镜像。若未能保存录像或对象版本，在清单列出缺口和影响范围，不把只恢复配置表述为完整恢复。

压缩包检查通过后可先恢复小范围样本，再做全量演练。数据库恢复用准确表查询验证，不用压缩文件体积推测行数；对象样本用名称、大小和内容核对，不用文件夹能打开代替回放验证。

## 六、总结

打包备份并不是简单的复制粘贴，它是对整个项目“运行状态”的存档。**有了这份存档，项目才能在任何时候、任何地点被完整地重新构建起来**。这也是一个合格项目必须拥有的基本保障措施。
