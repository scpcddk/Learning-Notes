# 站点乱码问题排查与修复全记录

> **问题**：前端页面“我的站点”列表中，站点名称显示为乱码。  
> **涉及环境**：阿里云 ECS `39.102.213.11`，Spring Boot 3.2.5，MySQL 8.0，Jackson 序列化，Docker 部署。  
> **勘误结论**：原记录描述站点列表最终恢复，但多项配置、构建产物和历史数据同时被修改，现有证据不足以将 Jackson、Maven 和 JDBC 同时认定为根因。JSON 转义本身不是乱码。

2. 前者显示正常中文，后者显示乱码。
3. 数据库直接查询 `station` 表，`ST-LAB-001` 的 `name` 字段已经是乱码（`å®žéªŒå®¤æµ‹è¯•ç«™ç‚¹`），`ST-001` 正常。

**初步判断**：`ST-LAB-001` 这条历史数据本身存错了，直接修复数据库即可。

**用同一站点样本逐层比较**

旧记录里的几轮尝试分别涉及数据库存量、接口序列化、应用启动初始化和资源文件打包。复查时选定同一个站点和字段，先保持样本不变，在源码、JAR、数据库、接口和页面逐层比对。避免一次同时改全局字符集、序列化、前端渲染和 SQL，否则即使显示恢复，也难说明实际原因。

## 二、第一轮尝试：手动修复数据库 + 排查 Jackson 转义

### 1.1 手动 UPDATE 数据库

```sql
-- 先确认 WHERE 命中范围，再根据影响行数判断更新是否符合预期。
UPDATE station SET name='实验室测试站点' WHERE station_id='ST-LAB-001';
```

执行后数据库显示正确中文。但**前端仍然乱码**。

### 1.2 检查后端接口返回

用 `curl` 直接访问后端 8080 端口：

```bash
# 从当前网络位置访问指定端点，结合状态码和响应内容判断结果。
curl -s http://localhost:8080/api/stations -H "Authorization: Bearer <token>"
```

返回的 JSON 中 `name` 字段是 `\u00e5\u00ae\u017e...` 这种 **Unicode 转义序列**，而不是直接的中文。

**正确区分**：`\u5b9e\u9a8c` 与“实验”是等价 JSON 表示；`\u00e5...` 解码后却是 `å...`，说明转义前字符串就已异常。应先核对数据库原始字节、应用读取值和 JSON 解析结果，不能仅凭出现转义就定位为序列化错误。

#### 区分 JSON 转义与已经损坏的字符

| 现象 | 看哪一处原始证据 | 判断 |
|---|---|---|
| 接口原文为 `\u4e2d\u6587` | JSON 解析后的字符串 | 合法转义可还原为中文，单凭转义不能判断数据损坏 |
| 数据库查询和接口都显示 `??` | 对同一行查看 `HEX(字段)` | 字节是 `3F` 时说明样本已经存成问号，改显示编码不会恢复原字符 |
| 浏览器显示 `�` | 对比原始响应字节、解码方式与数据库 | 若 UTF-8 字节已经是 `EF BF BD`，该层收到的是替换字符；若原字节正常，查解码或渲染 |
| 手工修完，应用重启后又乱码 | 重启前后同一行内容和更新时间，初始化日志 | 可能是启动写入覆盖，先找写入来源 |
| 后端接口正常，页面仍显示旧值 | 开发者工具里实际响应与页面渲染数据 | 查缓存、状态更新和字段映射 |

#### 保留响应并用独立 JSON 解析器核对

当时的 Jackson 转义尝试说明，浏览器展示、终端渲染和传输字节是不同证据。可把同一条只读请求的响应保存在自己的排障目录，先确认 HTTP 状态与 Content-Type，再让标准 JSON 解析器读原文。下面只显示字段的码点，便于比对，不打印具体业务值。

```python
import json
from pathlib import Path

# 把两个键改成已脱敏响应中实际存在的对象和字符串字段。
raw = Path("sample-response.json").read_bytes()
data = json.loads(raw.decode("utf-8-sig"))
text = data["data"]["displayName"]
print(" ".join(f"U+{ord(char):04X}" for char in text))
```

如果解析结果里的码点正确，而终端或浏览器面板显示异常，下一步查字体、页面渲染、字段选择或缓存。若解码报错，先保留响应头和字节样本，核对是否实际收到 HTML、压缩正文或其他编码。如果原始 JSON 值已经变成 `?`，继续沿后端取值和数据库字段找第一次出现的位置，不靠调整控制台编码掩盖错误。


### 1.3 排查 Jackson 配置

- 检查 `application.properties`，没有 Jackson 相关配置。
- 检查 JAR 包，发现已有 `JacksonConfig.class`（后端之前添加过），但**启动日志中没有加载记录**。
- 怀疑 `@Bean @Primary ObjectMapper` 没有生效。

### 1.4 尝试外部配置文件关闭转义

在 `/opt/iot-backend/application.properties` 中添加：

```properties
# 把键值放到读取该配置的文件或节中，核对覆盖顺序与重启后的生效值。
spring.jackson.serialization.write-non-ascii-characters-as-unicode=false
```

重启后端 → **后端启动失败**（8080 端口无监听）。  
**原因**：该名称不是合法的 Jackson serialization feature；应删除错误配置，并根据实际启动异常确认绑定失败原因。不能把它解释为仅当前版本不支持的官方属性。
**教训**：不是所有 Spring 官方文档中的属性在当前版本都能用，需要验证。

**旧稿中的配置优先级假设**

早期记录（`ab3d50a`）曾怀疑外部设置与 dev profile 的加载顺序。把这条写作当时的假设：profile 文件里没有对应属性，并不能单独证明已加载的值被覆盖。应核对运行实例的 profile、属性来源以及实际 ObjectMapper 行为，再结合存储字节判断。


### 1.5 换用 `Jackson2ObjectMapperBuilderCustomizer`

让后端修改代码，使用 Customizer 方式：
```java
// 先看输入与依赖，再沿关键调用检查返回结果和异常分支。
@Bean
public Jackson2ObjectMapperBuilderCustomizer jsonCustomizer() {
    return builder -> builder.featuresToDisable(
            JsonWriteFeature.ESCAPE_NON_ASCII.mappedFeature()
    );
}
```
重新打包部署后，**启动日志仍无加载记录，转义依旧**。

**勘误**：Jackson 的 ESCAPE_NON_ASCII 通常默认关闭，普通 Bean 也不一定有启动日志。没有日志不能证明 customizer 未生效。使用 Boot 自动配置的 ObjectMapper 时可检查 `spring.jackson.generator.escape-non-ascii=false`，但关闭转义不会修复已经错误解码的字符。

## 三、第二轮排查：数据库数据为何反复变成乱码

### 2.1 发现数据被“神秘覆盖”

我们多次执行 `UPDATE` 把数据库改成正确中文，但只要重启后端，数据又变回乱码。  
**思考**：肯定有某个初始化代码在启动时往数据库写入了错误的值。

### 2.2 定位到 `LabBootstrapConfig`

在后端源码中找到 `LabBootstrapConfig.java`，其 `@PostConstruct` 方法会在启动时执行：

```java
Station station = stationRepository.findByStationId(stationCode)
    .orElseGet(() -> stationRepository.save(Station.builder()
            .stationId(stationCode)
            .name(stationName)  // 从配置文件读取
            .build()));
```

- `stationCode` = `ST-LAB-001`
- `stationName` = `${app.lab-bootstrap.station-name}`（默认 `实验室测试站点`）

**关键**：如果数据库已有 `ST-LAB-001`，不会覆盖；但如果数据库没有这条记录（比如被删了），就会用配置文件中的值重新创建。  
**勘误**：上面 orElseGet 只在查不到记录时创建，不会覆盖已存在行。若重启后已有数据变化，需检查实际数据库、查询条件、其他初始化器、SQL 脚本或更新路径，不能仅由此证明 JAR 配置被错误编码。

### 2.3 验证：检查 JAR 包内的配置文件

```bash
# 读取或筛选本地文件，按实际路径与输出核对关键字段。
jar tf /opt/iot-backend/app.jar | grep "application-dev"
cd /tmp
jar xf /opt/iot-backend/app.jar BOOT-INF/classes/application-dev.properties
cat BOOT-INF/classes/application-dev.properties | head -50
```

终端显示本身不能证明实际字节是否损坏。应比较源码资源、target/classes、JAR 内同一文件的校验和与字节，并核对运行时读取值；原记录未保留这些证据。

#### 对照运行的 JAR、资源字节和初始化写入

旧记录里的 `LabBootstrapConfig` 和带固定站点编号的初始化值得优先排查。先查源码中对应字段和编号，再确认运行中的 JAR 是否包含相同文本或配置。源码编辑器显示正确只代表源码文件能读，Maven 资源过滤、编码配置和打包过程都可能改变产物。运行时还可能读取外部文件或另一份 profile。

```bash
# 对运行中的 JAR 核对实际文件和归档中是否有配置、初始化数据。
: "${APP_JAR:?请设置实际运行的 JAR 路径}"
sha256sum "$APP_JAR"
jar tf "$APP_JAR" | grep -E 'BOOT-INF/classes/.*(application|bootstrap|seed|\.sql)'
```

若要看某个归档条目，可先在本地复制到临时目录，只检查目标内容。不要把含数据库口令的配置整体贴进排障记录。核对 Maven 源码编码与资源处理配置。对确实使用 filtering 的文件，用同一构建参数比较源码字节、`target/classes` 文件与 JAR 内容，找出第一次改变的阶段。用 `systemctl show` 和新启动日志确认实际执行的 JAR 和 profile，排除「已上传新包，服务仍启动旧路径」的情况。

若启动初始化会补数据，先验证关闭开关是否真正被当前应用识别。重启前记录样本，重启后再次读同一行，确认是否有 INSERT/UPDATE 或定时同步任务。对于补数或修复脚本，先在复制出来的练习库验证。初始化是否可重复运行、是否会覆盖既有行，以及关停后是否仍有定时写入，应分别确认。


### 2.4 尝试禁用自动初始化

在外部配置文件中添加：

```properties
# 把键值放到读取该配置的文件或节中，核对覆盖顺序与重启后的生效值。
app.lab-bootstrap.enabled=false
```

重启后端 → **数据仍被覆盖**。

**排查原因**：

- `systemctl cat iot-api` 确认启动命令中有 `--spring.config.additional-location=file:/opt/iot-backend/application.properties`，说明外部配置会被加载。
- 但 `application-dev.properties` 中**没有** `app.lab-bootstrap.enabled` 字段，代码中默认值是 `true`。
- 另一个文件缺少该属性，不会把已明确提供的 false 还原成代码默认值 true。应核对属性来源、实际生效值及代码是否使用此开关。

**待验证**：不能由上述现象认定是配置加载顺序；需查看最终属性值、运行 JAR、激活 profile 和其他写入数据的路径。

### 2.5 用环境变量强制禁用
在 systemd 服务文件中添加：
**阅读提示**　把键值放到读取该配置的文件或节中，核对覆盖顺序与重启后的生效值。

```
Environment="APP_LAB_BOOTSTRAP_ENABLED=false"
```

重启后端 → **数据仍被覆盖**。  

**思考**：环境变量通常高于配置文件，但命令行参数、Java 系统属性等还可能覆盖它。仍有乱码也不代表该开关未生效。因为**即使 `enabled=false` 跳过了 `LabBootstrapConfig`，`ST-001` 的乱码仍然存在**——这说明还有另一个初始化代码在操作 `ST-001`。

### 2.6 搜索 `ST-001` 的源头

`LabBootstrapConfig` 只处理 `ST-LAB-001`，不碰 `ST-001`。`ST-001` 的乱码一定来自另一个初始化类。  
在代码中搜索 `ST-001`、`示例换热站`，但未找到。  

**推测**：可能是早期版本直接通过 SQL 脚本导入的，或者另一个 `@PostConstruct` 没有被发现。

## 四、第三轮突破：发现 MySQL 连接字符集问题

### 4.1 检查 MySQL 字符集变量

```bash
# 在已运行容器内执行命令，命令使用容器里的路径和网络。
docker exec -i mysql_8.0 mysql -u clouduser -pcloudpass123 -e "SHOW VARIABLES LIKE 'character_set%';"
```

输出：

| 变量 | 值 |
|------|-----|
| character_set_client | **latin1** |
| character_set_connection | **latin1** |
| character_set_results | **latin1** |
| character_set_database | utf8mb4 |
| character_set_server | utf8mb4 |

**勘误**：这里 SHOW VARIABLES 来自新开的 mysql CLI 会话，默认显示当前会话值，不能代表 JDBC 连接。应通过应用实际连接池取得的连接查询 `@@session.character_set_client`、`@@session.character_set_connection`、`@@session.character_set_results`，并同时确认 DATABASE() 与 CONNECTION_ID()。

#### 分别查看会话与存储字段的字符集

建议先在原数据库连接用只读命令看编码变量，再用原记录中的目标行查询字段的 `HEX`、`LENGTH` 和 `CHAR_LENGTH`。普通客户端连接的会话变量与应用数据源未必相同。需要确认应用连接时，从受控的应用诊断路径或对应连接获取实际会话信息，比较 JDBC 配置、账号、库和服务器地址。

```sql
-- 在需要排查的会话执行。分别核对客户端、连接与结果字符集。
SELECT @@session.character_set_client,
       @@session.character_set_connection,
       @@session.character_set_results,
       @@session.collation_connection;
-- 继续对照目标库与默认字符集。字段本身的字符集另用 SHOW FULL COLUMNS 核对。
SELECT DATABASE(), @@character_set_server, @@collation_server;
```

若命令行客户端的输入本身已经被错误编码，用手工输入的中文作为测试可能误判。优先比对已知正确的文件样本、数据库字节和标准 JSON 解析结果。只改变终端显示后出现中文，说明至少需要进一步检查渲染差异；不能据此认为数据库写入路径也已恢复。


### 4.2 尝试在 JDBC URL 中追加参数

修改 `application.properties`：

```properties
# 数据库地址从应用所在网络选择，连接信息与驱动、字符集配置一起核对。
spring.datasource.url=jdbc:mysql://...?useUnicode=true&characterEncoding=utf-8&connectionCollation=utf8mb4_unicode_ci&characterSetResults=utf8
```
重启后端 → `character_set_results` 仍为 `latin1`。

### 4.3 用环境变量覆盖 JDBC URL
在 systemd 服务文件中设置 `SPRING_DATASOURCE_URL` 环境变量。  
重启后端 → 仍无效。

### 4.4 最终手段：修改 MySQL 容器全局配置
创建 `/tmp/my.cnf`：
```ini
# 核对配置属于 MySQL 服务端还是客户端，重启或重新连接后检查生效值。
[mysqld]
character-set-server=utf8mb4
collation-server=utf8mb4_unicode_ci
init_connect='SET NAMES utf8mb4'
skip-character-set-client-handshake
```

复制到容器并重启 MySQL：

```bash
# 从指定客户端连接 MySQL，先核对主机、端口、账号和目标库。
docker cp /tmp/my.cnf mysql_8.0:/etc/mysql/conf.d/charset.cnf
docker restart mysql_8.0
```

原记录描述再次检查时变量变为 utf8mb4；若仍由 CLI 查询，只能验证该 CLI 会话，不能替代 JDBC 会话检查。

## 五、最终修复：双管齐下

### 5.2 清洗历史数据
历史乱码需先备份，确认错误编码链路，再选明确的记录修复。以下只是针对特定可逆误编码的 SQL 生成示意，必须先用 SELECT 检查转换结果；不能批量用于正常中文、含替换字符或多次误编码的数据：

#### 先修写入，再清理旧数据

1. 备份受影响的行，记录主键、旧值字节、最后更新时间与可信的数据来源。
2. 用正确编码的测试值从实际应用写入，在隔离环境复现一次完整的「提交 → 查库 → 查 API → 浏览器」。
3. 测试重启后同一条记录仍保持正确，确认初始化、采集端和定时任务不会再次覆盖。
4. 确认错误行的筛选范围后再修旧数据。若原值已经变成 `?` 或替换字符，从备份、原始采集数据或可靠配置重建。
5. 修复后抽查普通站点名、显示名及带特殊字符的样本，保留脚本版本和对照结果。数据库、API 与页面分别记录。

一次复盘可用「站点或行号、文件或版本、时间、原始字节、解码结果、是否重启、下一次校验」串起证据。原手册列出的配置修改是当时的尝试与解决过程。再次迁移时优先核对应用数据源和具体表字段，再评估改数据库服务端默认值的影响范围。 [MySQL 连接字符集](https://dev.mysql.com/doc/refman/8.0/en/charset-connection.html)

登录接口返回的 `displayName` 仍然是乱码（`ç³»ç»Ÿç®¡çå'˜`），但数据库 `sys_user` 表中 `display_name` 字段是正常中文。

## 七、核心经验总结

1. **乱码问题要分层排查**：数据库存储 → JDBC 传输 → 后端序列化 → 前端渲染，逐层验证。
2. **不要轻信“配置文件已加载”**：用日志或环境变量验证，而不是猜测。
3. **Spring Boot 属性兼容性**：不是所有文档中的属性在当前版本都能用，需验证。
4. **Docker 容器的字符集陷阱**：即使数据库字符集正确，连接字符集也可能被客户端驱动或服务器端配置覆盖。
5. **初始化代码是双刃剑**：`@PostConstruct` 或 `CommandLineRunner` 在启动时自动执行，可能反复覆盖手动修复的数据。
6. **Maven 资源编码容易被忽略**：`project.build.sourceEncoding` 也可作为 Maven Resources Plugin 过滤资源的默认编码；properties 过滤另与插件版本及 propertiesEncoding 有关。filtering=false 通常按字节复制，不会自动修复源文件或运行时读取方式。
7. **服务端全局设置不能当通用修复**：init_connect 和握手覆盖可能影响共享实例的其他连接；先在应用实际 JDBC 会话验证，再决定是否调整。

# 排查证据速览

| 观察 | 能说明什么 | 尚需验证什么 |
|---|---|---|
| JSON 中有 Unicode 转义 | 存在 JSON 转义表示 | 解码后的字符是否正确，转义前 Java 字符串是否异常 |
| 重启后数据变化 | 可能有写入或读到了不同数据源 | 实际 SQL、数据库、初始化路径；orElseGet 不会覆盖已有行 |
| CLI 会话字符集为 latin1 | 该 CLI 会话的编码配置 | 应用实际 JDBC 会话的协商结果 |
| 终端显示 JAR 配置内容 | 某一终端的解码显示结果 | 原文件、构建文件和 JAR 字节及运行时读取值 |
| 多项修改后页面恢复 | 组合调整后的现象改善 | 各项改动的必要性及独立根因 |

参考：[Spring Boot 外部配置](https://docs.spring.io/spring-boot/reference/features/external-config.html)、[MySQL 连接字符集](https://dev.mysql.com/doc/refman/8.0/en/charset-connection.html)、[Maven properties 过滤](https://maven.apache.org/plugins/maven-resources-plugin/examples/filtering-properties-files.html)、[Jackson 转义特性](https://fasterxml.github.io/jackson-core/javadoc/2.14/com/fasterxml/jackson/core/JsonGenerator.Feature.html)。
