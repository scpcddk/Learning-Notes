# 外键

现在进入实际企业数据库设计。

很多初学者会觉得：

> “外键这么好，可以保证数据不乱，为什么大厂不用？”

原因是：

**外键解决的是“小规模数据正确性”，但大型系统更关注“高并发、扩展性、服务拆分”。**

我们详细分析。

---

## 一、先看传统设计：使用外键

例如：

用户表：

```text
user

id
name
```

订单表：

```text
order

id
user_id
price
```

建立：

```sql
FOREIGN KEY(user_id)
REFERENCES user(id)
```

关系：

```
user
 |
 |
order
```

优点：

数据库保证：

订单的 user_id 一定存在。

例如：

禁止：

```sql
INSERT INTO order
(user_id)
VALUES
(999);
```

因为用户999不存在。

---

## 二、为什么大厂不喜欢？

### 原因1：性能问题

假设：

订单系统：

每天：

```text
1亿订单
```

用户表：

```text
5000万用户
```

现在：

订单插入：

```sql
INSERT INTO order
(user_id)
VALUES(10001);
```

数据库必须检查：

```text
user表有没有 id=10001
```

也就是说：

**每次写订单**：

**多一次检查**。

---

小规模：

没有问题。

但是高并发：

例如：

每秒：

```text
10万订单
```

数据库压力增加。

---

## 三、原因2：分库分表以后外键失效

这是最重要原因。

小项目：

一个数据库：

```
MySQL

 user
 order
 product
```

外键很好用。

---

但是大厂：

数据量巨大。

可能：

用户库：

```
user_db

user_1
user_2
user_3
```

订单库：

```
order_db

order_1
order_2
order_3
```

现在：

user和order：

已经不在一个数据库。

问题：

外键怎么办？

比如：

```sql
order.user_id

REFERENCES

user.id
```

但是：

user 表在另外一个数据库。

MySQL 外键无法跨数据库。

所以：

大规模系统：

通常：

不用数据库外键。

---

## 四、原因3：微服务架构

现在互联网系统：

不是一个大数据库。

例如：

用户服务：

```
user-service
```

负责：

user表

订单服务：

```
order-service
```

负责：

order表

商品服务：

```
product-service
```

负责：

product表

结构：

```
          用户服务
             |
             |
订单服务 ---- 商品服务
```

---

订单表：

```text
order

id
user_id
product_id
```

这里：

user_id：

不是数据库外键。

只是一个普通字段。

为什么？

因为：

订单服务不知道用户数据库在哪里。

---

## 五、那数据一致性怎么办？

大厂不是不要约束。

而是：

从：

**数据库约束**

转移到：

**代码 + 业务流程**。

---

例如：

创建订单：

以前：

数据库：

```
外键检查
↓
插入订单
```

现在：

代码：

```
订单服务
 |
 | 查询用户服务
 ↓
用户存在？
 |
 ↓
创建订单
```

---

或者：

异步消息：

```
订单服务

创建订单

↓

消息队列

↓

库存服务
```

---

## 六、原因4：级联删除危险

外键：

```sql
ON DELETE CASCADE
```

看起来方便。

例如：

删除用户：

自动删除订单。

但是企业中：

非常危险。

比如：

管理员误操作：

```sql
DELETE FROM user
WHERE id=100;
```

可能：

用户删除

↓

订单删除

↓

支付记录删除

↓

退款记录删除

灾难。

所以企业更喜欢：

逻辑删除：

例如：

user：

| id  | name | deleted |
| --- | ---- | ------- |
| 100 | 张三   | 1       |

数据还在。

只是隐藏。

---

## 七、原因5：数据库职责变重

大型系统希望：

数据库主要负责：

* 存储
* 查询
* 索引

业务规则：

交给：

* Java代码
* 服务层

例如：

数据库：

```
user_id INT
```

只是保存。

Java：

判断：

```java
if(userExist){
    createOrder();
}
```

---

## 八、那是不是外键完全不用？

不是。

看场景。

---

### 小项目

例如：

学校管理系统：

```
student
class
teacher
```

非常适合外键。

优点：

* 数据安全
* 开发简单

---

### 中大型系统

例如：

电商：

```
用户
订单
支付
库存
物流
```

通常：

不用数据库外键。

使用：

* 业务代码保证
* 服务调用
* 消息队列
* 数据校验

---

## 九、你的 Spring Boot 项目应该怎么设计？

以你现在学习路线：

Spring Boot + MyBatis + MySQL

建议：

### 学习阶段

可以使用外键：

例如：

```text
class

id
name


student

id
name
class_id
```

帮助理解关系。

---

### 项目阶段

推荐：

保留关联字段：

```text
student

id
name
class_id
```

但是：

不一定创建：

```sql
FOREIGN KEY
```

---

## 十、总结一句话

> 小项目依靠数据库保证关系，大项目依靠业务代码保证关系。

外键：

```
优点：
✅ 数据安全
✅ 防止脏数据
✅ 设计清晰


缺点：
❌ 降低写入性能
❌ 难以分库分表
❌ 不适合微服务
❌ 级联风险
```
