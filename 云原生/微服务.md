# 第一篇　基础认知

## 1. 单体、模块化单体与微服务

微服务把业务能力划成可独立交付的服务。每个服务需要明确的接口、数据所有权和维护责任。订单系统可以有订单、库存、通知三个业务模块，先在同一个 Spring Boot 应用内运行，再根据实际瓶颈决定是否把通知处理单独部署。

| 形态 | 调用与部署 | 主要代价 | 适用信号 |
|---|---|---|---|
| 单体 | 一个进程和一次发布，常用本地事务 | 代码耦合会随规模增长 | 项目起步、需求变化快 |
| 模块化单体 | 一个部署单元，模块通过明确接口交互 | 需要约束依赖和数据访问边界 | 小团队维护多个业务域 |
| 微服务 | 各服务独立部署，跨边界使用 API 或消息 | 网络故障、跨服务一致性、可观测性和运维成本 | 发布或扩容需求出现明显分化，团队有能力独立维护 |

> [!tip]
> 先看可核实的拆分理由。订单通知因第三方接口限流需要独立排队、扩容和发布时，拆通知模块有实际收益。把 Controller、Service、Mapper 拆成三个远程进程，会让同一次业务操作依赖更多网络和发布步骤。

---

## 2. 服务边界与数据所有权

订单域维护订单与支付状态，库存域维护可用量与预留记录，通知域维护发送记录与重试进度。订单需要展示商品名称时，可保存下单时的商品快照。库存数量及其并发更新由库存域管理。

```text
客户下单 → 订单服务写入订单和待发布事件
                              ↓
                          订单事件
                              ↓
                       通知服务 → 第三方通知接口
```

| 拆分前要回答 | 订单场景 |
|---|---|
| 谁拥有写权限 | `orders` 归订单域，通知服务只维护 `notification` |
| 同步调用必须返回什么 | 查看详情需要当前订单状态和返回码 |
| 哪些动作允许延后 | 通知可异步发送，业务状态能显示待发送或失败 |
| 改接口会影响谁 | 记录 API 消费方、事件订阅者、兼容期和发布顺序 |

## 3. 基础设施各自管什么

| 组件 | 职责 | 按需使用 |
|---|---|---|
| API Gateway | 外部路由、认证入口、限流、请求转发 | 业务校验仍在业务服务内 |
| 服务发现 | 用服务名找到可用实例 | Kubernetes Service/DNS 可满足许多集群内调用。跨环境或已有体系可评估 Nacos |
| 配置中心 | 发布并管理共享运行配置 | 区分环境、权限、回滚，记录应用何时刷新 |
| 消息队列 | 缓冲流量、分发事件、支持异步处理 | 下游要定义重试、幂等和积压处理 |
| 可观测性 | 用指标、日志、Trace 找到故障层和证据 | 随第一个远程调用接入请求关联 |

# 第二篇　远程调用与数据一致性

## 4. 同步调用的超时、重试与熔断

同步调用适合当前响应依赖的结果。网络超时后，调用方只知道没收到结果，服务端可能已经执行成功。把重试限定在已知可重试的错误和幂等操作上。创建订单等写请求需要持久化幂等键，或先查询上一次请求结果。

| 手段 | 解决的问题 | 实践要点 |
|---|---|---|
| 超时 | 下游长时间不返回，占用线程和连接 | 同时考虑连接、读取和整个请求的截止时间 |
| 重试 | 短暂网络异常、少量可恢复失败 | 次数有限，退避加随机抖动，避免每层都重试 |
| 熔断 | 下游持续失败时减少重复调用 | 打开后快速失败，半开允许少量探测 |
| 舱壁隔离 | 一个依赖拖满所有执行资源 | 给慢依赖单独的并发上限或资源池 |
| 降级 | 可选功能不可用时保住核心流程 | 如推荐服务不可用，订单详情仍可正常查看 |

例子　详情接口总预算 800 ms，服务自身预留 200 ms。库存查询每次最多 200 ms，最多额外重试一次，退避 50 ms，合计上限 450 ms，剩余时间留给排队和序列化。请求只剩 150 ms 时，跳过重试并按业务规则返回结果或明确错误。

## 5. 异步消息与事务 Outbox

如果先提交 MySQL 再发送消息，进程可能在中间退出。反过来先发送消息再提交，消费者可能看到最后回滚的订单。Outbox 把订单和待发布事件写进同一个本地事务，后台发布器再投递事件。

```text
一个 MySQL 事务
  ① 更新 orders
  ② INSERT outbox(event_id, event_type, payload, ...)
  ③ COMMIT
       ↓
发布器扫描未发送事件 → Broker 确认 → 标记发送完成
       ↓
通知消费者按 event_id 去重，并持久化本地通知任务 → 提交消费进度
```

发布器可能在 Broker 确认之后、更新发送状态之前重启，因此会重复发送。通知服务用 `(consumer, event_id)` 唯一约束，在同一事务内完成去重与本地状态更新。调用外部通知接口时，还需要独立的发送状态和提供方支持的幂等键，处理「对方已发出，己方没收到响应」的情况。

> [!warning]
> **易混淆**　`@Transactional` 通常只覆盖本服务控制的本地资源。另一个服务的 HTTP 写入、第三方通知和 Broker 消息各有自己的提交边界。

多个步骤需要业务补偿时，可用 Saga 记录进度和补偿动作。例如订单创建后通知失败，可以重试或标记待人工处理。已经发出的短信无法靠数据库回滚撤回。

## 6. API 和事件演进

- HTTP 契约写清状态码、错误体、超时和幂等键语义。新增可选字段通常更容易兼容，删字段或改变旧值含义需要迁移。
- 事件至少有 `eventId`、`eventType`、`schemaVersion`、`occurredAt` 和业务标识。消费者应对未知可选字段有明确策略。
- 按「先加、再切、后删」做兼容迁移。滚动发布期间要考虑新消费者遇到旧消息、旧消费者遇到新消息两种情况。
- 按业务优先级区分错误。网络断开可短暂重试，非法字段应留证并人工修复，限流按退避策略等待。

# 第四篇　能验证的订单、库存和通知实战

## 9. 先规定接口与失败语义

考虑订单服务、库存服务和通知服务。选择下面的最小业务契约。核心写入要有可追踪的状态，错误响应要能决定重试还是人工处理。

| 操作 | 对外语义 | 幂等和失败处理 |
|---|---|---|
| `POST /orders` | 创建订单或返回该请求已创建的订单 | 保存 `Idempotency-Key` 与请求摘要，同键不同请求体返回冲突 |
| `GET /orders/{id}` | 返回当前状态，可轮询确认处理结果 | 只读，超时后可有限重试 |
| `PUT /reservations/{orderId}` | 预留指定 SKU 和数量 | 订单 ID 唯一。重复相同请求返回已有结果，不再扣减 |
| `DELETE /reservations/{orderId}` | 释放尚未完成的预留 | 以状态条件更新，重复释放不增加库存 |
| `OrderCreated` 事件 | 通知服务创建待发送任务 | 事件 ID 唯一，成功持久化后 ACK |

订单入库成功但库存仍在异步处理中，可返回订单 ID 与 `PENDING`，明确查询地址。若 API 采用 `202 Accepted`，响应表示已经接受处理。若资源已创建并返回 `201 Created`，资源状态仍可为待处理。客户端超时后以同一请求键重试或查结果，避免生成两个订单。幂等键要按账号和操作范围隔离，不同调用者的请求不能互相覆盖。

## 10. 在 MySQL 练习 Outbox 与消费者幂等

### 10.1 部署和表结构

把下面保存为 `schema.sql`，执行 `labmysql < schema.sql`。用于新卷里的独立练习。

```sql
CREATE DATABASE orders_lab;
CREATE DATABASE notify_lab;

CREATE TABLE orders_lab.orders (
    id VARCHAR(32) PRIMARY KEY,
    request_key VARCHAR(96) NOT NULL,
    request_hash CHAR(64) NOT NULL,
    status VARCHAR(20) NOT NULL,
    version INT NOT NULL DEFAULT 1,
    UNIQUE KEY uk_order_request (request_key)
);

CREATE TABLE orders_lab.outbox (
    id VARCHAR(96) PRIMARY KEY,
    order_id VARCHAR(32) NOT NULL,
    event_type VARCHAR(40) NOT NULL,
    payload JSON NOT NULL,
    state VARCHAR(16) NOT NULL DEFAULT 'PENDING',
    next_attempt_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
    -- 租约到期后可以回收事件，token 用于区分每次认领。
    lease_until DATETIME(6) NULL,
    lease_token VARCHAR(80) NULL,
    attempts INT NOT NULL DEFAULT 0,
    KEY ix_publish (state, next_attempt_at, id),
    KEY ix_lease (state, lease_until)
);

CREATE TABLE notify_lab.tasks (
    event_id VARCHAR(96) PRIMARY KEY,
    order_id VARCHAR(32) NOT NULL,
    state VARCHAR(16) NOT NULL DEFAULT 'PENDING',
    created_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6)
);
```

### 10.2 对照回滚与提交

以下语句在同一连接中执行。把 `ROLLBACK` 改为 `COMMIT` 再重做一次，观察订单行和 Outbox 行一起出现。

```sql
-- 在同一连接中观察事务内外的可见性，最后核对提交或回滚后的数据。
START TRANSACTION;

INSERT INTO orders_lab.orders (id, request_key, request_hash, status)
VALUES ('order-42', 'req-42', SHA2('sku=1001;qty=2', 256), 'PENDING');

INSERT INTO orders_lab.outbox (id, order_id, event_type, payload)
VALUES ('event-42-created', 'order-42', 'OrderCreated',
        JSON_OBJECT('eventId', 'event-42-created', 'orderId', 'order-42', 'version', 1));

ROLLBACK;

SELECT COUNT(*) AS order_count FROM orders_lab.orders WHERE id = 'order-42';
SELECT COUNT(*) AS event_count FROM orders_lab.outbox WHERE id = 'event-42-created';
```

回滚预期为 `0/0`，提交预期为 `1/1`。如果在一次已提交的实验上再运行插入，唯一约束会报重复。实际应用应捕获该冲突，按请求键查询已有结果并对比请求摘要，相同返回已有订单，不同返回 409。不能用直接忽略 SQL 错误代替这套判断。

### 10.3 两个 Worker 如何认领事件

实际轮询器在短事务中认领一小批到期事件，写入本次租约后提交。在数据库事务外调用 Broker，发送成功再用租约 token 标记完成。以下 SQL 用已知的单条事件演示，并发 worker 选择不同记录时可按同样模式做批量认领。

```sql
START TRANSACTION;

SELECT id, payload
FROM orders_lab.outbox
WHERE state = 'PENDING' AND next_attempt_at <= NOW(6)
ORDER BY next_attempt_at, id
LIMIT 1
FOR UPDATE SKIP LOCKED;

-- 应用只对 SELECT 选中的 id 执行，token 每次认领都应不同。
UPDATE orders_lab.outbox
SET state = 'PUBLISHING', lease_token = 'worker-a-attempt-1',
    lease_until = NOW(6) + INTERVAL 30 SECOND, attempts = attempts + 1
WHERE id = 'event-42-created' AND state = 'PENDING';

COMMIT;
```

Broker 确认后执行条件更新，避免旧 worker 在租约失效后覆盖新一轮的状态。

```sql
-- 先确认 WHERE 命中范围，再根据影响行数判断更新是否符合预期。
UPDATE orders_lab.outbox
SET state = 'SENT', lease_token = NULL, lease_until = NULL
WHERE id = 'event-42-created'
  AND state = 'PUBLISHING' AND lease_token = 'worker-a-attempt-1';

SELECT ROW_COUNT() AS updated;
```

如果发布失败，按当前 token 安排下一次尝试，更新 `next_attempt_at` 并清理租约。若 worker 意外退出，后台回收过期的 `PUBLISHING` 记录，限制重试并记录错误。只依赖一个永久的 `PUBLISHING` 状态会导致故障后卡住。监控待发送数、最老事件的年龄、过期租约和失败次数。

### 10.4 重复投递的可复现验收

让通知库执行以下事务两次。这个 SQL 用例模拟同一事件被送到消费者两次，实际消息确认顺序参照 Kafka 或 RocketMQ 笔记。

```sql
-- 在同一连接中观察事务内外的可见性，最后核对提交或回滚后的数据。
START TRANSACTION;
INSERT INTO notify_lab.tasks (event_id, order_id)
VALUES ('event-42-created', 'order-42')
ON DUPLICATE KEY UPDATE event_id = tasks.event_id;
COMMIT;

SELECT event_id, order_id, state FROM notify_lab.tasks
WHERE event_id = 'event-42-created';
```

两次处理预期只有一条任务，原状态不会被重新置为待发送。如果收到相同 eventId 但不同订单 ID，应当记录冲突。完整演练时，在消息已经进入 Broker、Outbox 尚未标记完成的位置停止发布器，恢复后确认重复事件仍只有一条任务。再在消费者提交之后、ACK 之前中断，重试后核对同样的结果。

## 11. 库存一致性与补偿

库存扣减需要在本地事务中防止并发超卖。一个常见写法是条件更新。仅当影响行数为 1 时创建或确认预留记录，两者在同一个库存服务事务提交。

```sql
-- 先确认 WHERE 命中范围，再根据影响行数判断更新是否符合预期。
UPDATE inventory
SET available = available - 2, version = version + 1
WHERE sku_id = 'sku-1001' AND available >= 2;
```

预留表对订单 ID 或“订单 + SKU”设置唯一约束。同一预留请求重试时应查询已有状态。释放库存时先把预留从 `RESERVED` 条件更新为 `RELEASED`，只有本次确实转换成功才恢复数量。两个动作在同一个本地事务中完成。

| 失败点 | 应保存的状态 | 下一次能做什么 |
|---|---|---|
| 订单保存成功，库存暂不可用 | 订单保持 PENDING，记录请求键和下一次尝试 | 限次重试并允许查询 |
| 预留成功，订单服务没收到响应 | 库存保留订单对应的预留记录 | 用原预留 ID 查询或幂等重试 |
| 付款超时关闭，库存已预留 | 记录取消与待释放状态 | 幂等释放，并比对实际库存 |
| 已发货后收到旧取消事件 | 记录版本与状态冲突 | 阻止回退，进入人工或售后流程 |
| 通知失败 | 通知任务进入重试或失败状态 | 修复通知后单独补发，订单状态独立处理 |

Saga 适合确有多步业务动作、并接受一段时间状态不一致的场景。写清每步重试和补偿前提。补偿本身也可能失败，需要单独状态、重试和观测。先验证状态机和人工恢复流程，再评估是否引入专门的编排工具。

## 12. 从测试到发布演练

### 12.1 按层测试

| 测试 | 要复现 | 验收 |
|---|---|---|
| 业务状态机 | 合法迁移、同一事件重复、旧版本晚到 | 状态与版本符合规则 |
| 真实持久化 | 本地事务回滚、唯一键冲突、并发扣减 | 行数、库存和 Outbox 证据可查 |
| HTTP 契约 | 200、冲突、下游超时、网络断开 | 状态码和错误体可指导客户端 |
| 消息恢复 | 写库后未 ACK，或发消息后未更新 Outbox | 最终恢复进度，业务结果不重复 |
| 混合版本 | 旧消费者读新增可选字段，新消费者读旧事件 | 两边仍正常处理，禁止不兼容字段抢先删除 |

同步故障可直接用 [OpenTelemetry 的双进程练习](可观测性/OpenTelemetry.md) 观察 200、504 和 502，再给客户端设置预算与降级。异步故障用 [Kafka](数据库与中间件/Kafka.md) 或 [RocketMQ](数据库与中间件/RocketMQ.md) 的本地环境验证。只引入一个能验证当前目标的 Broker。

### 12.2 一次变更从部署到回滚

1. 先发布兼容的数据库和事件字段，旧应用仍可运行。
2. 部署一小批新版本，检查错误率、p95、消费 Lag、Outbox 最老年龄和重复处理数。
3. 流量与积压稳定后再扩大，保留旧版本回切条件。
4. 若失败，先确认数据库和消息契约允许回退，再回到上一版。需要时暂停特定消费组，保留进度，恢复后按组观察追平。
5. 故障复盘记录影响、首次证据、失败边界、恢复时间和下一步修正。

### 12.3 网关认证、服务授权和资源归属

外部流量可由网关执行入口认证、限流和路由。服务仍要判断调用者是否拥有当前操作和目标资源的访问权。跨服务时传递授权所需的身份和上下文，内部服务调用使用独立身份或有明确定义的用户委托令牌。不要相信外部可任意设置的 `X-User-Id`、`X-Tenant-Id` 等头。

| 层次 | 负责的判断 | 练习 |
|---|---|---|
| 身份校验 | token 签名、签发方、有效期与目标服务 | 错签发方或错受众 token 请求订单服务，预期拒绝 |
| 操作授权 | scope 或角色是否允许读取、更新 | 只读身份可 GET，缺少读取 scope 被拒绝 |
| 资源授权 | 当前用户或租户是否拥有该订单 | 用同一个有效 token 访问另一个租户的订单，预期拒绝 |
| 服务间身份 | 下游知道由哪个服务、为谁发起 | 检查服务凭据与用户身份是否区分，并且不会写进日志 |

Spring Boot 3.5 资源服务器可通过 `spring-boot-starter-oauth2-resource-server` 依赖接入 JWT。以下是订单服务的配置片段，`IDP_ISSUER_URI` 填练习身份提供方地址。

```yaml
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: "${IDP_ISSUER_URI}" # 绑定可信签发方
          audiences: [orders-api]       # 只接受供订单服务使用的 token
```

配置只建立 token 验证条件。再用 `SecurityFilterChain` 或方法级授权为接口检查 `SCOPE_orders.read` 等权限，数据访问按可信身份限定订单归属。在本地分别测无 token、错受众、缺 scope、越租户与合法请求，确认审计日志能区分原因，并遮盖 token 原文。 [Spring Security JWT 资源服务器](https://docs.spring.io/spring-security/reference/6.5/servlet/oauth2/resource-server/jwt.html)

**实战验收**　从本地数据库做出 Outbox 与通知去重，演练至少一个进程退出窗口和一次重复消息，能解释请求幂等、消息确认、资源补偿三者各自解决的问题。最后提交一份可照着执行的部署、故障和恢复记录。
