# 镜像仓库与版本管理

> **定位**：让本地、CI 和服务器获得同一个应用版本，能够追溯、更新和回退。
> **示例环境**：使用 Docker Hub 或 GHCR 管理应用镜像，构建与运行方法见关联 Docker 笔记。
> **命令环境**：下文 shell 命令在 Bash / WSL 执行；用户名、镜像路径和版本均为示例，执行前替换。

---

## 一、先分清几个名字

| 概念 | 含义 | 示例 |
|---|---|---|
| Registry | 存储和分发镜像的注册服务 | `ghcr.io`、Docker Hub |
| Repository | 同一镜像名称下的内容集合 | `ghcr.io/yourname/student-api` |
| Tag | 指向镜像或镜像索引的可读名字 | `v1.0.0`、`sha-具体提交` |
| Digest | 标识特定内容的摘要 | `sha256:...` |
| 本地镜像 ID | 本地镜像对象的标识 | `docker image ls` 中的 IMAGE ID |

完整引用示例：

```text
ghcr.io/yourname/student-api:v1.0.0
│       │        │           └─ tag
│       │        └─ 镜像名
│       └─ 命名空间（账号或组织）
└─ registry
```

Tag 可以被重新指向其他内容；名字叫 latest 也不能保证它是最新、稳定或已经测试的版本。Digest 适合确定具体内容，但不能单独证明来源可信或没有漏洞。

## 二、结合后端与 AI 项目的版本约定

| 镜像 | 建议记录 | 理由 |
|---|---|---|
| Java 后端 | 源码提交、JDK、镜像 tag/digest | 追溯业务代码与运行环境 |
| FastAPI AI 服务 | 源码提交、Python 依赖、镜像 tag/digest | 排查客户端、框架和依赖差异 |
| AI 使用的数据与模型 | 模型名称/版本、提示词、知识库或索引版本 | 回退程序镜像不会自动回退这些外部状态 |

可以同时为同一发布保留人类易读的版本号和关联提交的标签。即使采用提交标签，也应约定不覆盖已发布的标签；真正需要精确固定内容时使用 digest。

## 三、GHCR 基本操作：构建、登录、推送、拉取

以下使用 GHCR，假定已在应用项目目录中准备好 Dockerfile，并拥有目标命名空间的发布权限。路径使用小写。

### 1. 构建镜像

```bash
docker build -t ghcr.io/yourname/student-api:v0.1.0 .
```

构建方式、构建上下文和 `.dockerignore` 见 [Docker 笔记](Docker.md)。若 Dockerfile 从宿主机复制 JAR，应先生成其要求的产物；多阶段构建则按该 Dockerfile 执行。

### 2. 登录 GHCR

命令行访问按官方说明使用具备所需权限的个人访问令牌（classic），发布通常需要 `write:packages`；组织还可能有 SSO 等访问要求。

```bash
read -r -s -p 'GHCR token: ' CR_PAT
printf '\n'
printf '%s' "$CR_PAT" | docker login ghcr.io -u yourname --password-stdin
unset CR_PAT
```

令牌用完清除 shell 变量，不写进 Dockerfile、镜像标签或 Git 仓库。Docker 登录凭据的保存方式取决于客户端的 credential store 配置，不能认为登录后令牌自动消失。

### 3. 推送与拉取

```bash
docker push ghcr.io/yourname/student-api:v0.1.0
docker pull ghcr.io/yourname/student-api:v0.1.0
docker image inspect ghcr.io/yourname/student-api:v0.1.0 --format '{{json .RepoDigests}}'
```

推送后记录仓库返回的 digest。也可将**实际返回的摘要**写成 `ghcr.io/yourname/student-api@sha256:实际摘要`，用于后续精确拉取。

公开源码仓库不代表关联的 Package 自动公开；在 Package 设置中核对可见性和访问权限。私有镜像需要给服务器或 CI 相应读取权限。

参考：[GHCR 的认证、发布与访问规则](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry)。

## 四、CI 中如何处理凭证

| 使用位置 | 基本做法 | 要注意什么 |
|---|---|---|
| Actions 发布同仓库关联的 GHCR 镜像 | 优先使用工作流的 `GITHUB_TOKEN`，授予必要的 `packages: write` | 还需匹配 Package 的访问策略；权限不是仅靠一行 YAML 就一定具备 |
| Actions 发布 Docker Hub 镜像 | 使用仓库 Secrets 保存账号与访问令牌 | 凭证名称要与 workflow 对应 |
| 部署服务器拉私有镜像 | 使用只读范围的凭证 | 构建机登录不会自动让服务器也登录 |

把构建与镜像发布接入 CI 时参考 [CI/CD 笔记](../DevOps/CI-CD.md)。镜像发布流程只维护一份，Docker Hub 完整示例位于 [Docker 笔记第 5 节](Docker.md#5-cicd-流水线示例github-actions)。

## 五、部署时怎样记录和切换版本

可以在 Compose 中将应用镜像引用作为显式配置：

```yaml
# compose.yaml：仅演示应用镜像引用，数据库等依赖按项目另行配置
services:
  backend:
    image: ${APP_IMAGE:?请先设置完整镜像引用}
    ports:
      - "127.0.0.1:8080:8080"
    restart: unless-stopped
```

服务须在容器中监听可达的接口和 8080 端口。回环端口发布适合本机检查或宿主机代理访问；其他网络拓扑按实际情况调整。

```bash
export APP_IMAGE=ghcr.io/yourname/student-api:v0.1.0
docker compose config --quiet
docker compose pull backend
docker compose up -d backend
docker compose ps
docker compose logs --tail 50 backend
```

日志和容器状态只是部分证据，还要检查项目实际的健康端点和业务接口。升级时把 APP_IMAGE 改为新版本；需要回退时改回旧版本，再拉取、重建和验收。

不要在刚发布后立即删除旧镜像。保留至少一个已经验证且配置兼容的回滚版本；数据库迁移、上传文件和外部 AI 配置需另行考虑恢复方式。

## 六、常见误区

| 误区 | 正确理解 |
|---|---|
| 改 tag 就重新构建了镜像 | `docker tag` 增加本地引用，不会修改镜像内容 |
| latest 一定是最新版本 | 它只是标签，含义取决于维护者约定 |
| 相同 tag 必然相同内容 | 标签可能被覆盖，重要发布应记录 digest |
| 镜像包含所有运行数据 | 数据库和对象存储的持久化数据需要单独备份 |
| 本地登录后，部署机自动有权限 | 凭证和权限需要分别配置 |
| image ID 就等于仓库 digest | 二者可能指向不同层次的对象，不应直接等同 |
| 镜像回滚会恢复整个系统 | 镜像只能回退程序及其镜像内环境，不能自动回退外部状态 |

## 七、发布版本记录

| 记录项 | 用途 |
|---|---|
| 源码提交 SHA | 确认对应的代码 |
| 完整镜像引用与 digest | 确认实际交付的内容 |
| 配置与数据迁移版本 | 判断环境差异及回滚兼容性 |
| 发布时间与运行结果 | 关联故障出现时间和部署变化 |
| 上一个可用版本 | 提供明确的回滚目标 |
