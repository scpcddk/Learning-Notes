## 第一章：项目背景与我的切入点（Why & How I started）

**项目名称**：换热站无人值守AI试点平台（CloudPlatform）  
**我的职责**：不是写代码，而是以开发视角完成**设备接入层**（心跳）与**事件告警层**（事件）两大核心模块的端到端测试。

**关键背景**：这是一个多人协作项目，其他成员已提交了基础代码，但未经过系统性测试。我的任务是 **“在POC阶段把底座夯实，确保边缘端（Jetson）和云端通信链路是可靠的”**。

**我面临的第一个难题不是测试，而是启动项目。**

接手代码后，我发现 `application.yml` 默认激活的是 `prod` 环境，指向 `localhost:3306` 的 MySQL。我的电脑没有装MySQL，启动直接报 `Communications link failure`。我没有直接改公共配置文件（因为会影响别人），而是采用了以下操作：

1. 创建 `application-local.yml`，配置使用 H2 内存数据库。
2. 在 IDEA 的 `Run/Debug Configurations` 中添加 `VM options: -Dspring.profiles.active=local`。
3. 利用项目自带的 `DataInitializer` 让 Hibernate 自动建表，并初始化了 `admin` 用户。

**面试价值点**：我掌握 Spring Boot 多环境隔离，不破坏团队配置，体现了工程化思维。

## 第二章：测试准备（工具与环境定义）

**测试工具**：Swagger UI (`http://localhost:8080/swagger-ui.html`)

**理由**：相比 Postman，Swagger 能实时看到 DTO 字段约束，修改请求体速度快，适合测试阶段的快速迭代

**前置数据准备（手工在Swagger里执行）**：

1. 登录：`POST /api/auth/login`，输入 `admin / Admin123456`，复制返回的 `accessToken`
2. 鉴权：点击 Swagger 右上角 `Authorize`，粘贴 Token，确保后续请求带着身份
3. 造数：检查 `GET /api/stations`、`GET /api/devices`、`GET /api/cameras` 是否存在 `ST-LAB-001`、`EDGE-LAB-001`、`RGB-A-LAB`。如果不存在，分别调 POST 接口创建。（这一步确保了后续测试不会因“404 设备不存在”而中断）

## 第三章：A系列——心跳接口完整测试实录（共9项，8 Pass，1 Fail）

### A1：正常心跳（正向链路）

**操作**：

- 接口：`POST /api/heartbeats`
- Body：

```json
{
  "deviceId": "EDGE-LAB-001",
  "stationCode": "ST-LAB-001",
  "timestamp": "2026-07-25T16:30:00+08:00"
}
```

**观察**：返回200，`"status": "ONLINE"`，且 `serverTime` 是服务器当前时间。  
**结论**：基础写入链路通。

---

### A2：设备不存在（异常校验）

**操作**：把 `deviceId` 改成 `FAKE-DEVICE`。
**观察**：返回 `404` + `"设备未登记"`。  
**结论**：后端做了设备存在性校验，未乱写数据。

---

### A3：设备与站点不匹配（关联校验）

**操作**：`deviceId` 用 `EDGE-LAB-001`，`stationCode` 改成 `ST-WRONG`。
**观察**：返回 `404` + `"站点不存在"`。  
**思考**：这里后端是先校验站点是否存在，逻辑合理。

---

### A4：无Token访问（安全拦截）

**操作**：在 Swagger 中点击 `Authorize` -> `Logout` 清空 Token，再执行 A1 请求。
**观察**：返回 `403`（Forbidden）。  
**结论**：认证拦截器生效，接口不暴露给未授权客户端。

---

### A5：无效Token访问（Token校验）

**操作**：在 `Authorize` 中填入乱码字符串 `eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.123`。
**观察**：返回 `403`。  
**结论**：JWT 解析失败会抛出异常并被全局处理器捕获。

---

### A6：心跳更新 `lastSeenAt`（数据一致性）

**操作**：

1. 先查询设备详情：`GET /api/devices/1`，记录 `lastSeenAt` = `16:06:57`。
2. 发送一次心跳。
3. 再次查询设备详情。

**观察**：`lastSeenAt` 变为 `16:15:12`，且 `status` 从 `OFFLINE` 变为 `ONLINE`。  
**验证方法**：在 H2 控制台执行 `SELECT * FROM DEVICE WHERE ID=1;` 交叉验证，确认数据库字段已更新。  
**结论**：Service 层事务正常提交，数据持久化成功。

---

### A7：超过阈值标记离线（定时任务联动）

**操作**：

1. 确保设备在线。
2. 调用手动触发接口：`POST /api/heartbeats/offline-alarm`，Body传入 `{"deviceId":"EDGE-LAB-001","stationCode":"ST-LAB-001"}`。

**观察**：返回 `"offline alarm created"`。
**验证**：再次查询 `GET /api/devices/1`，`status` 变为 `OFFLINE`。  
**思考**：这里利用手动触发代替了等待5分钟定时任务，提高了测试效率。

---

### A8：恢复在线（链路闭环）

**操作**：设备处于 `OFFLINE` 状态时，再次发送正常心跳（同 A1 请求）。
**观察**：

1. 心跳返回 200。
2. 查询设备详情，`status` 变回 `ONLINE`。
3. 查询告警列表，出现了一条 `RECOVERY`（恢复在线）类型的记录，`status` 为 `CLOSED`。  

**结论**：心跳模块具备状态自动恢复能力。

---

### A9：离线告警幂等性（这是关键 FAIL）

**背景知识**：幂等性指“一次请求和多次请求产生的副作用相同”。

**操作步骤（还原现场）**：

1. 调用离线扫描接口，生成第一条告警。
2. 查询告警列表：`GET /api/alarms`，此时 `totalElements = 1`。
3. **再次**调用离线扫描接口（模拟定时任务重复执行）。
4. 再次查询告警列表。

**观察到的异常**：

- 第二次调用返回的 `message` 依然是 `"offline alarm created"`（而不是“已存在”）。
- 告警列表 `totalElements` 变成了 **2**。
- 我为了确认，重复点了 4 次 Execute，最终 `totalElements` 变成了 **8**，其中 7 条是 `ACTIVE` 的离线告警。

**根因分析（面试重点）**：

- 代码在 `OfflineAlarmScheduler` 中，只判断了“时间是否超时”，**没有判断“是否已有 ACTIVE 状态的离线告警”**。
- 导致每一次触发都执行 `INSERT`，而非 `UPDATE` 或 `SKIP`。
- 这是一个典型的**并发幂等性缺失**问题，在定时任务场景下会被无限放大。

**修复建议（我写在报告里提交给了学姐）**：

```java
// 伪代码逻辑
Alarm exist = alarmRepo.findByDeviceAndStatus(deviceId, "ACTIVE");
if (exist == null) {
    createOfflineAlarm();
} else {
    log.info("已存在离线告警，跳过创建");
}
```


## 第四章：B系列——事件接口完整测试实录（共10项，9 Pass，1 Fail）

### B1：正常事件（正向链路）

**操作**：`POST /api/events`，使用 `eventType: BOUNDARY_BREACH`，`createAlarm: true`。
**观察**：返回200，`duplicate: false`，且 `alarmId` 有值。  
**结论**：事件 -> 告警联动链路通。

---

### B2 & B3：重复事件幂等性

**操作**：将 **完全相同的请求体**（同一个 `eventId`）再发一次。
**观察**：返回 `"duplicate": true`。  
**验证**：查询数据库 `EVENT_RECORD` 表，只有一条记录；`ALARM` 表也只有一条关联告警。  
**结论**：事件模块已实现幂等，不重复落库，不重复生成告警。

---

### B4 ~ B6：异常参数（站点/设备校验）

**操作**：分别传入不存在的站点、不存在的设备、以及站点和设备不匹配的组合。
**观察**：全部返回 `404` 或 `400`，错误信息提示准确。  
**结论**：参数校验层拦截有效。

---

### B7：非法时间格式（反序列化校验）

**操作**：把 `occurredAt` 格式写错，例如 `"2026-07-25 16:00"`（缺少 `T` 和时区）。
**观察**：返回 `400 Bad Request`，`"Failed to read request"`。  
**分析**：因为 DTO 中 `occurredAt` 是 `OffsetDateTime` 类型，Jackson 解析失败抛异常，被全局异常捕获。虽然错误提示不友好，但**功能上正确拒绝了非法数据**，未入库。

---

### B8：非法事件类型（业务枚举校验）

**操作**：`eventType` 填 `UNKNOWN`。
**观察**：返回 `400` + `"事件类型未启用或未配置规则"`。  
**结论**：事件类型受 `AlarmRule` 表控制，未配置的无法上报。

---

### B10：`createAlarm` 参数被忽略（关键 FAIL）

**测试期望**：设置 `"createAlarm": false` 时，系统应**只存事件，不生成告警**。

**操作**：

```json
{
  "eventId": "EVENT-B10-RETEST-002",
  "eventType": "BOUNDARY_BREACH",
  ...
  "createAlarm": false
}
```

**观察到的异常**：

- 返回了 `200`，但 `"alarmId": "EVENT-B10-RETEST-002"`。
- 查询 `ALARM` 表，确实生成了告警记录。

**根因分析**：

- 在 `AlarmRulePolicy` 或 `EventService` 中，系统根据 `eventType` 查到了规则表，发现 `autoCreateAlarm = true`，**直接覆盖了请求体中的 `false`**。
- 缺少“请求参数优先级高于规则配置”的逻辑。
- **修复建议**：在生成告警前加判断 `if (request.getCreateAlarm() != null && !request.getCreateAlarm()) return;`

## 第六章：深度经验总结（面试必备谈资）

1. **关于测试策略**：我采用了“广度优先”而非“深度优先”。先确保正向链路通，再测异常。A1和B1是基石，如果它们都500，后面测A2没有任何意义。
2. **关于Bug定位**：我不只看HTTP状态码，我会去**H2控制台执行SQL**，确认数据真实状态。比如A9，我必须亲眼看到 `totalElements` 从1变2才确认失败。
3. **关于环境隔离**：通过 `application-local.yml` 和 `-Dspring.profiles.active=local` 解决多环境配置冲突，避免了团队Git提交冲突。
4. **关于幂等性理解**：我学会了区分“重复事件幂等”（B2已实现）和“定时任务幂等”（A9未实现），这对设计高并发系统至关重要。
5. **关于沟通能力**：我提交的是“结构化缺陷报告”（现象->复现步骤->预期->实际->根因猜测），而不是只截图甩给学姐，这提高了协作效率。
