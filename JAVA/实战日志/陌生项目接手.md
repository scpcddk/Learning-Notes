# 📖 《陌生 Spring Boot 项目接手操作手册》


### 核心理念：不求瞬间全懂，但求先“跑起来”再“串起来”
接手别人的代码，如果一头扎进具体的业务类（如 `AlarmServiceImpl`）里逐行阅读，你会迷失在细节中。**我们的策略是：先看“说明书”（配置）→ 绕过“安检”（安全拦截）→ 利用“仪表盘”（Swagger）→ 最后追踪“一单到底”（全链路）。**


### 第一阶段：侦察与启动（让它先喘口气）

**目标：让项目在本地无报错地启动，哪怕连不上真实数据库。**

1.  **先看 `pom.xml` / `build.gradle`（依赖清单）**
    - **看ORM**：是 JPA/Hibernate 还是 MyBatis？（决定了你怎么看数据库操作）。
    - **看安全**：有没有 `spring-boot-starter-security` 和 `jjwt`？（预示着一定有拦截器）。
    - **看工具**：有没有 `springdoc-openapi` 或 `knife4j`？（如果存在，说明自带接口文档，可以省去 Postman 配参数的痛苦）。

2.  **再查 `application.yml` / `application-{profile}.yml`（环境总开关）**
    - **找数据库**：看 `spring.datasource.url`。如果是 `jdbc:h2:mem`（内存库），**恭喜你，零成本启动**；如果是 `mysql`/`postgresql`，且你本地没装，就临时在配置里把 `ddl-auto` 设为 `none`，并注释掉 `url`，临时改用 H2 覆盖（前提是你只是想看代码结构）。
    - **记端口**：确认 `server.port`（默认 8080），访问地址就靠它了。
    - **找上下文**：确认有没有 `server.servlet.context-path`（如果有，所有请求路径都得加前缀）。

3.  **直面报错（跳过坏代码）**
    - **现象**：启动时若报 `Bean` 创建失败（比如你遇到的 `HeartbeatController` 里既有 `@Configuration` 又有 `@Override` 这种语法错误）。
    - **操作**：别急着修复逻辑，**直接 `Refactor -> Rename` 把该文件加上 `_BACKUP`**。让 Spring 扫描不到它，项目先跑起来再说。**破车先上路，再修零件。**


### 第二阶段：冲破“安检门”（解决 401/403 权限拦截）

**目标：让 Swagger（接口文档）能打开，或者能用 Postman 调通登录接口。**

1.  **定位 `SecurityConfig`**
    - 找到 `SecurityFilterChain` 或 `configure(HttpSecurity http)` 方法。
    - **只看白名单**：搜索 `permitAll()` 或 `antMatchers("/**").permitAll()`。查看哪些路径是不需要 Token 就能访问的（通常是 `/auth/login`, `/swagger-ui/**`, `/v3/api-docs/**`）。

2.  **修复自定义过滤器的“越权拦截”（这一步极其关键，90%的坑在这里）**
    - 即使 `SecurityConfig` 放行了 `/swagger-ui/**`，但如果项目里有自定义的 `JwtAuthenticationFilter`（继承 `OncePerRequestFilter`），它依然会拦截所有请求。
    - **必杀技**：在 `JwtAuthenticationFilter` 的 `doFilterInternal` 方法**最顶部**，手动添加路径跳过逻辑：
      ```java
      String path = request.getRequestURI();
      if (path.contains("/swagger-ui") || path.contains("/v3/api-docs") || path.contains("/auth/login")) {
          filterChain.doFilter(request, response);
          return; // 直接放行，不解析 Token
      }
      // 原有的 Token 解析逻辑放在下面...
      ```
    - **原理**：`SecurityConfig` 管的是“需不需要登录”，`JwtFilter` 管的是“有没有 Token 给我解析”。两者必须同时放行，Swagger 才能打开。


### 第三阶段：利用“仪表盘”摸清家底（Swagger/Knife4j）

**目标：不读代码，先通过可视化界面摸清接口结构。**

1.  **调通登录接口，拿到 Token**
    - 访问 `http://localhost:端口/swagger-ui.html`。
    - 找到 `AuthController` 的登录接口。
    - **挖掘默认账号**：如果不知道账号密码，去 `config` 包下找 `DataInitializer` 或 `CommandLineRunner` 实现类，看启动时 `new SysUser()` 写入的是什么（通常硬编码了 `admin/123456`）。
    - 获取 Response 中的 `token` 值。

2.  **挂载全局 Token**
    - 点击 Swagger 右上角的 `Authorize` 按钮，粘贴刚才的 Token。这样你在网页上点“Execute”执行任何接口时，都会自动附带 Token，无需手动拼接 Header。

3.  **浏览“货架”**
    - 遍历所有 Controller（如 `DeviceController`、`StationController`）。
    - **只看两个东西**：`@RequestBody`（入参 DTO）和 `@Operation` 或返回值（出参 DTO/Response）。这让你对项目能做什么、数据结构长什么样一目了然。


### 第四阶段：执行“一单到底”链路追踪（核心读码技巧）

**目标：选定 1 个简单接口（如“新增设备”），从 HTTP 请求穿透到数据库，搞懂项目的代码分层风格。**

**操作步骤（以你刚刚做过的 `POST /api/devices` 为例）：**

1.  **Controller 层（入口）**：看接收的 DTO（`DeviceCreateRequest`），记住入参字段。
2.  **Service 层（业务）**：这里是核心。重点看三件事：
    - **校验**：有没有查重（`existsByDeviceId`）？
    - **外键关联**：有没有根据 `stationCode` 去查 `Station` 表（说明项目存在表关联）？
    - **补全字段**：有没有自动设置 `createdAt`、`lastSeenAt`、默认状态 `ONLINE`？
3.  **Repository 层（数据库）**：看接口继承的是 `JpaRepository` 还是 `PagingAndSortingRepository`，判断它用的是什么查询方式（方法名解析 or `@Query` 注解）。
4.  **Entity 层（表结构）**：看 `@Table` 和字段注解，对一下刚才 Swagger 返回的 JSON，理解数据库字段和业务字段的映射关系。
5.  **看 SQL 日志（验证）**：启动时配置了 `spring.jpa.show-sql=true`，当你点击 Swagger 执行时，盯着 IDEA 控制台打印的原生 SQL，**亲眼验证**代码生成的 SQL 是不是和你预想的一致。


### 第五阶段：安全的“第一次修改”（破冰行动）

**目标：修改一个废弃/错误的接口，让项目真正属于你的掌控之下。**

1.  **备份旧逻辑**：重命名或注释掉原有的错误类。
2.  **复用现有能力**：不要重复造轮子。比如写心跳接口时，直接用现成的 `DeviceRepository` 和 `Device` 实体，只写 `device.setLastSeenAt(now)` 和 `deviceRepository.save(device)`。
3.  **小步验证**：修改后重启，只在 Swagger 上调通这一个接口，确认 `lastSeenAt` 时间确实变了。
4.  **提交记录**：在 Git 上切一个新的 `feature/fix-heartbeat` 分支，提交这次修改。**不要在主分支上改**。


### 💡 核心心法总结（挂在工位上）

1.  **先跑后读**：代码跑不起来，读再多都是“静态分析”。
2.  **放过 Swagger**：只要能通过 Swagger 调接口，你就拥有了项目的“上帝视角”。
3.  **不走迷宫**：读代码时，遇到 A 调 B，B 调 C，C 又返回 A 的复杂嵌套逻辑，**立刻停止**。只跟踪一条 `Controller -> Service -> Repository` 的主线，旁枝末节（如工具类、拦截器、监听器）暂时跳过。
4.  **搜索关键词**：如果你想找某张表的数据在哪个类里处理，直接在 IDEA 中按 `Ctrl+Shift+F`（全局搜索）搜索 `Entity` 的类名（如 `Device`），看看哪些 `Service` 引入了它。
5.  **日志是最好老师**：`DEBUG` 级别的 SQL 日志和控制台报错堆栈，往往比代码本身更能说清楚数据流向。
