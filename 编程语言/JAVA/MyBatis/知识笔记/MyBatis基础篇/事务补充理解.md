# MyBatis 事务实战笔记：完整流程与核心部件

> **学习范围：** Spring Boot + MyBatis-Spring + MySQL  
> **核心目标：** 理解事务从开启、Mapper 执行、提交/回滚到资源清理的完整过程。
>
> **记忆主线：Spring 管事务，MyBatis-Spring 协调会话，Connection 承载数据库事务，事务结束后再清理资源。**
>
> 本笔记以实际实验和常见易错点为主，不展开讲解完整源码实现。

---

# 一、事务全流程总览

以一个 Service 调用两个 Mapper 为例：

```java
@Service
public class TransferService {

    @Autowired
    private AccountMapper accountMapper;

    @Transactional
    public void transfer() {
        accountMapper.deduct(1, 100);
        accountMapper.add(2, 100);
    }
}
```

完整流程：

```text
外部调用 Service
        ↓
Spring 事务代理
        ↓
检查事务传播行为
        ↓
开启事务 T1（或加入已有事务）
        ↓
获取并管理 JDBC Connection C1
        ↓
事务资源与当前线程关联
        ↓
Mapper A 执行 SQL A
        ↓
Mapper B 执行 SQL B
        ↓
Service 方法结束
        ↓
Spring 根据事务状态决定提交或回滚
        ↓
事务同步与资源清理
        ↓
处理 SqlSession 生命周期
        ↓
Connection 解除事务关联并关闭/归还连接池
```

**核心理解：** 事务不是 MyBatis 单独完成的，而是 Spring 事务管理、MyBatis-Spring、JDBC 和数据库共同协作的结果。

以上是概念流程。实际源码中的事务同步回调、会话处理和连接清理可能交错发生，并非所有场景都严格按照图中的顺序执行。

# 二、第一阶段：Service 调用与事务开启

## 1. 调用经过 Spring 事务代理

```text
外部调用
    ↓
Spring 代理
    ↓
事务拦截逻辑
    ↓
Service 方法
```

部件作用：

- `@Transactional`：声明事务规则与边界。
- Spring 事务代理：拦截符合条件的方法调用，协调事务的开启、提交或回滚。
- 事务管理器：实际协调事务操作。

在常见的 `REQUIRED` 传播行为下：

```text
当前没有事务
→ 通常创建新事务

当前已有事务
→ 通常加入现有事务
```

### `@Transactional` 生效检查

```text
① 对象是否由 Spring 管理？
② 调用是否经过 Spring 事务代理？
③ 方法是否符合当前代理方式的要求？
④ 是否使用正确的事务管理器？
⑤ 事务管理器与 Mapper 是否使用匹配的数据源？
```

例如：

```java
public void outer() {
    inner();
}

@Transactional
public void inner() {
    // 数据库操作
}
```

如果 `outer()` 和 `inner()` 在同一个对象中，上面的 `inner()` 通常属于同类内部调用，不会经过 Spring 代理。因此，`inner()` 上的事务注解通常不会独立触发事务拦截。

**易错点：**

- 自调用可能绕过事务代理。
- 手动 `new` 出来的对象通常不受 Spring 容器管理。
- `@Transactional` 不是无条件生效的开关。
- 使用错误的事务管理器或不匹配的数据源，也可能导致事务行为不符合预期。

## 2. 获取并关联 Connection

```text
Spring 事务管理器
        ↓
DataSource 获取 Connection C1
        ↓
准备事务连接
        ↓
关联到当前线程的事务资源
```

部件作用：

| 部件 | 作用 |
|---|---|
| `DataSource` | 提供 JDBC 连接 |
| `Connection` | 执行 JDBC 操作，承载数据库事务 |
| `TransactionSynchronizationManager`（TSM） | 管理当前线程关联的事务资源与同步信息 |
| `ConnectionHolder` | 持有与数据源关联的连接资源 |
| `ThreadLocal` | 提供线程局部存储机制，是实现线程资源关联的一种基础手段 |

概念上：

```text
当前线程
    ↓
TSM 管理的事务资源
    ↓
ConnectionHolder
    ↓
Connection C1
```

**易错点：**

- TSM 不是数据库事务本身。
- TSM 不是连接工厂。
- `ThreadLocal` 本身不负责创建、提交或回滚数据库事务。
- `ConnectionHolder` 是 Spring 关联事务资源的机制之一，不是 JDBC 连接本身。

# 三、第二阶段：Mapper A 执行 SQL

Service 调用：

```java
accountMapper.deduct(1, 100);
```

常见调用链：

```text
Mapper 代理
    ↓
SqlSessionTemplate
    ↓
SqlSessionUtils
    ↓
获取/复用 SqlSession
    ↓
Executor 执行 SQL
    ↓
SpringManagedTransaction
    ↓
Connection C1
    ↓
数据库执行 SQL A
```

各部件在这条链路中的作用：

| 部件 | 在当前流程中的作用 |
|---|---|
| Mapper 代理 | 将 Java 方法调用交给 MyBatis 执行 |
| `SqlSessionTemplate` | 协调 Mapper 调用时的 SqlSession 使用 |
| `SqlSessionUtils` | 检查、获取或复用事务关联的 SqlSession，并协调生命周期 |
| `SqlSessionHolder` | 持有并关联当前事务使用的 SqlSession |
| `Executor` | 组织 SQL 执行、缓存等工作 |
| `SpringManagedTransaction` | 让 MyBatis 配合 Spring 管理的 JDBC 连接与事务 |
| `Connection` | 实际执行 JDBC 操作，承载数据库事务 |

SQL A 执行后：

```text
SQL 已执行
    ↓
修改可能尚未提交
    ↓
事务继续进行
```

**易错点：SQL 执行成功不等于事务已经提交。**

例如，第一条 SQL 已经更新了账户余额，但第二条 SQL 发生异常时，第一条 SQL 的未提交修改仍然可能被回滚。

# 四、第三阶段：Mapper B 复用事务资源

Service 接着调用：

```java
accountMapper.add(2, 100);
```

在同一有效 Spring 事务、同一数据源及正确事务配置下，第二次 Mapper 调用通常会复用当前事务关联的会话和连接。

```text
Mapper B
    ↓
SqlSessionTemplate
    ↓
检查事务关联的 SqlSession
    ↓
复用相关资源
    ↓
Connection C1
    ↓
数据库执行 SQL B
```

概念上：

```text
SQL A → Connection C1
SQL B → Connection C1
```

这样两个 SQL 才能作为同一个数据库事务中的操作统一提交或回滚。

## 容易混淆的部件

- **`SqlSession`**：MyBatis 的会话层，负责组织数据库访问。
- **`Connection`**：JDBC 连接层，承载数据库事务。
- **`SqlSessionTemplate`**：协调会话使用，不等于底层连接。
- **`SpringManagedTransaction`**：连接 MyBatis 与 Spring 管理的连接，不是独立的 Spring 事务管理器。

**易错点：**

两个 Mapper 都由 Spring 注入，并不自动保证它们属于同一个事务。还要确认：

- 调用是否处于同一个有效事务中；
- 事务传播行为是否符合预期；
- 是否使用匹配的数据源和事务管理器；
- 是否存在 `REQUIRES_NEW` 等会改变事务边界的情况。

不要仅凭两个 Mapper 都被注入，就认定它们一定复用了同一个连接。

# 五、第四阶段：事务结束——提交还是回滚

## 1. 正常返回

```java
@Transactional
public void transfer() {
    accountMapper.deduct(1, 100);
    accountMapper.add(2, 100);
}
```

流程：

```text
SQL A 执行
    ↓
SQL B 执行
    ↓
方法正常返回
    ↓
Spring 检查事务状态
    ↓
事务可以提交
    ↓
COMMIT
```

在没有其他回滚标记、事务状态正常且提交成功的情况下，两个操作一起提交。

## 2. 抛出运行时异常

```java
@Transactional
public void transfer() {
    accountMapper.deduct(1, 100);
    accountMapper.add(2, 100);

    throw new RuntimeException("测试回滚");
}
```

流程：

```text
SQL A 执行
    ↓
SQL B 执行
    ↓
RuntimeException 向外传播
    ↓
Spring 事务代理命中默认回滚规则
    ↓
ROLLBACK
```

两个 SQL 的未提交修改都会被回滚。

## 3. 事务规则速记

| 情况 | 默认行为 |
|---|---|
| 方法正常返回，事务可以提交 | 提交 |
| `RuntimeException` 向事务拦截器传播 | 回滚 |
| `Error` 向事务拦截器传播 | 回滚 |
| 受检异常 `Exception` | 默认通常不回滚 |
| 异常被捕获且未触发其他回滚机制 | 可能提交 |
| 事务已被标记为 `rollback-only` | 不能正常提交，最终需要回滚 |

需要受检异常也触发回滚时，可以使用：

```java
@Transactional(rollbackFor = Exception.class)
```

### 这里有一个关键限定

默认回滚规则并不是“代码中只要出现异常就必然回滚”。

实际结果还取决于：

- 异常类型；
- 异常是否到达事务拦截器；
- 是否经过 Spring 事务代理；
- 是否配置了 `rollbackFor` 等规则；
- 当前事务是否已经被标记为 `rollback-only`；
- 数据库提交是否成功。

**易错点：** 判断回滚不能只看代码中有没有异常，还要看异常传播方式、事务边界和事务状态。

# 六、第五阶段：捕获异常与 rollback-only

## 1. 异常被捕获，不代表事务一定回滚

例如：

```java
@Transactional
public void testCommit() {
    studentMapper.updateScore(1, 70);
    studentMapper.updateScore(2, 60);

    try {
        throw new RuntimeException("模拟业务异常");
    } catch (RuntimeException e) {
        System.out.println("异常已被捕获");
    }
}
```

执行流程：

```text
执行 SQL A
    ↓
执行 SQL B
    ↓
产生 RuntimeException
    ↓
异常被方法内部捕获
    ↓
方法正常返回
    ↓
没有其他回滚标记
    ↓
事务可能提交
```

在实际实验中，如果异常只是在方法内部被捕获，且没有触发其他回滚机制，数据库修改就可能被提交。

## 2. 什么是 rollback-only？

`rollback-only` 表示当前事务已经被标记为只能回滚。

假设外层事务调用内层 `REQUIRED` Service：

```text
外层事务 T1
    ↓
执行 SQL A
    ↓
调用内层 Service
    ↓
内层加入共享事务 T1
    ↓
内层抛出运行时异常
    ↓
异常经过内层事务拦截器
    ↓
共享事务被标记为 rollback-only
    ↓
外层捕获异常并继续执行
    ↓
外层方法正常返回
    ↓
事务仍不能正常提交
    ↓
最终回滚
```

**易错点：** 捕获异常不等于清除 `rollback-only`。在常见配置下，外层最终可能抛出：

```text
UnexpectedRollbackException
```

原因是外层方法虽然正常返回，但共享事务已经被标记为只能回滚。

## 3. `REQUIRED` 与 `REQUIRES_NEW`

| 对比项 | `REQUIRED` | `REQUIRES_NEW` |
|---|---|---|
| 已有事务时 | 通常加入现有事务 | 暂停外层事务并创建独立事务 |
| 内外层是否共享事务结果 | 通常共享 | 不共享 |
| 内层提交后外层回滚 | 共享事务整体回滚 | 内层已提交的结果通常保留 |
| 资源开销 | 通常复用已有事务资源 | 通常需要额外的事务连接资源 |

### `REQUIRES_NEW` 实验流程

```text
外层事务 T1，使用 C1
    ↓
外层执行 SQL A
    ↓
暂停 T1
    ↓
内层创建独立事务 T2
    ↓
T2 通常使用另一条连接 C2
    ↓
内层执行 SQL B
    ↓
T2 提交成功
    ↓
恢复 T1
    ↓
外层抛出 RuntimeException
    ↓
T1 回滚
```

最终可能出现：

```text
外层 SQL A → 回滚
内层 SQL B → 保留
```

**易错点：**

- `REQUIRES_NEW` 不是“必然提交”，而是独立事务；内层自身失败时也可以回滚。
- 独立事务通常需要额外连接，可能增加连接池压力。
- 如果外层事务持有连接并等待内层事务，而连接池容量不足，可能出现等待或资源耗尽。

因此，只有确实需要独立事务结果时，才应该考虑 `REQUIRES_NEW`。

# 七、第六阶段：事务结束后的资源清理

事务提交或回滚后，还需要处理会话和连接资源。

```text
Spring 完成提交/回滚
        ↓
事务同步及相关回调
        ↓
解除事务资源关联
        ↓
处理 SqlSession 生命周期
        ↓
清理 Connection 事务关联
        ↓
关闭/归还 Connection
```

这是概念流程。真实执行时，事务同步回调、会话处理与连接清理可能交错发生，具体顺序取决于框架实现及配置。

## 1. 各部分的职责区分

| 工作 | 主要负责方 |
|---|---|
| 数据库提交/回滚 | Spring 事务管理机制与 JDBC |
| SqlSession 使用与生命周期协调 | MyBatis-Spring |
| 当前线程事务资源绑定与解绑 | Spring 事务资源管理机制 |
| 连接关闭/归还连接池 | Spring 资源管理与 DataSource / 连接池机制 |

## 2. 连接关闭不等于销毁物理连接

在使用连接池时：

```text
调用 Connection.close()
        ↓
通常归还连接池
        ↓
连接池决定何时复用或销毁物理连接
```

因此：

- 提交/回滚决定数据库事务结果；
- SqlSession 清理处理会话生命周期；
- Connection 清理释放当前使用的连接资源；
- 连接池中的 `Connection.close()` 通常是归还连接，而不是销毁物理数据库连接。

**易错点：** 不能把“连接被关闭”当作“事务回滚”的原因。事务提交/回滚与资源清理是两个不同的概念。

# 八、第七阶段：事务与缓存的关系

```text
数据库事务
→ 决定数据库修改是否提交

MyBatis 缓存
→ 维护查询结果缓存
```

## 1. 一级缓存

一级缓存与 `SqlSession` 相关。

写操作通常会清理相关缓存，但数据库回滚不会自动把一级缓存完整恢复到写操作之前的状态。

因此，不能仅凭数据库已经回滚，就假定当前会话中所有缓存状态都恢复了。

## 2. 二级缓存

标准 MyBatis 二级缓存通过事务协调机制处理缓存变更，相关变更通常会延迟到事务提交阶段。

回滚时，待提交的缓存变更通常会被丢弃。

**易错点：数据库回滚不等于所有缓存都恢复原状。**

---

# 九、第八阶段：数据库事务与外部副作用

数据库事务只能回滚其事务管理范围内、且数据库支持事务回滚的操作。

例如：

```text
扣减账户余额
    ↓
发送通知
    ↓
后续 SQL 失败
    ↓
数据库事务回滚
```

此时，余额修改可能被回滚，但已经发送出去的通知不会自动撤销。

类似情况还有：

- 已发送的 HTTP 请求；
- 已发出的消息；
- 已写入的外部文件；
- 已执行的其他系统操作。

因此，在数据库与外部系统协作时，不能认为一个 `@Transactional` 就能让所有外部操作一起回滚。

根据业务要求，可以进一步考虑：

- 事务提交后执行的操作；
- 消息事务或 Outbox 模式；
- 补偿机制；
- 幂等设计。

**易错点：** 数据库事务不等于整个业务流程的全局事务。

# 十一、常见错误的快速定位

| 现象 | 优先检查 |
|---|---|
| `@Transactional` 看起来不生效 | Spring 代理、自调用、对象是否受 Spring 管理 |
| 方法抛出异常但数据库仍然修改 | 异常是否被捕获、异常类型、回滚规则 |
| 外层捕获异常但最终回滚 | 内层事务是否标记了 `rollback-only` |
| 出现 `UnexpectedRollbackException` | 共享事务是否已被标记为只能回滚 |
| 内层提交但外层回滚后仍保留数据 | 是否使用 `REQUIRES_NEW` |
| 两次 Mapper 调用没有按预期共享事务 | 事务边界、传播行为、数据源、事务管理器 |
| 测试结束后修改消失 | 测试方法是否有事务，以及测试结束时的回滚行为 |
| 数据库已回滚但缓存结果异常 | 一级缓存与二级缓存的状态 |
| 数据库回滚但消息已经发出 | 外部副作用是否位于数据库事务范围之外 |
| 连接被关闭后仍然可复用 | 是否使用连接池，`close()` 是否只是归还连接 |

# 十二、最后记住这条主线

```text
外部调用 Service
        ↓
Spring 事务代理
        ↓
Spring 事务管理器开启/加入事务
        ↓
Connection 与当前事务关联
        ↓
Mapper A、Mapper B 执行 SQL
        ↓
Spring 根据异常规则和事务状态决定提交或回滚
        ↓
MyBatis-Spring 协调 SqlSession 生命周期
        ↓
Spring / DataSource 机制清理连接资源
```

## 核心结论

1. **Spring 决定事务边界和提交/回滚规则。**
2. **MyBatis-Spring 协调 Mapper、SqlSession 与 Spring 事务。**
3. **JDBC Connection 承载数据库事务。**
4. **同一有效事务中的多个 Mapper 通常复用事务关联的 Connection。**
5. **SQL 执行成功不等于事务提交成功。**
6. **异常被捕获不代表事务一定提交，也不代表事务一定回滚。**
7. **`REQUIRED` 通常加入已有事务；`REQUIRES_NEW` 建立独立事务。**
8. **事务结果与资源清理是两件不同的事情。**
9. **数据库回滚不能自动撤销所有缓存变化和外部副作用。**
10. **实战验证必须检查最终数据库状态，并结合日志或调试器验证资源复用。**

# 第一轮事务学习的复习标准

如果以后时间有限，优先确保自己能够独立回答：

- [ ] `@Transactional` 是如何通过 Spring 代理生效的？
- [ ] 为什么两个 Mapper 调用可以参与同一个事务？
- [ ] `SqlSession` 和 `Connection` 有什么区别？
- [ ] 为什么 SQL 执行成功后仍然可能回滚？
- [ ] 为什么异常被捕获后事务可能提交？
- [ ] 为什么内层 `REQUIRED` 出错后，外层捕获异常仍可能回滚？
- [ ] `REQUIRES_NEW` 为什么可能让内层修改在外层回滚后继续保留？
- [ ] 为什么提交/回滚与资源清理不是同一件事？
- [ ] 为什么测试结束后数据可能被测试框架回滚？
- [ ] 为什么数据库事务不能自动撤销已经发送的外部消息？

**学习策略：** 这份笔记作为事务主笔记保留即可。后续优先通过实验和排错巩固，不必继续无止境地增加概念；达到以上复习标准后，再进入原定学习路线的下一阶段。
