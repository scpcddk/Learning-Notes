# MyBatis 事务实战笔记：完整流程与核心部件

> 学习范围：Spring Boot + MyBatis-Spring + MySQL  
> 核心目标：理解事务从开启、Mapper 执行、提交/回滚到资源清理的完整过程。
>
> 记忆主线：**Spring 管事务，MyBatis-Spring 协调会话，Connection 执行数据库操作，事务结束后再清理资源。**

---

# 一、事务全流程总览

以一个 Service 调用两个 Mapper 为例：

```java
@Service
public class TransferService {

    @Autowired
    private AccountMapper accountMapper;

    @Transactional
    public void transfer() {
        accountMapper.deduct(1, 100);
        accountMapper.add(2, 100);
    }
}
```

完整流程：

```text
外部调用 Service
        ↓
Spring 事务代理
        ↓
开启事务 T1
        ↓
获取并管理 JDBC Connection C1
        ↓
事务资源与当前线程关联
        ↓
Mapper A 执行 SQL A
        ↓
Mapper B 执行 SQL B
        ↓
Service 方法结束
        ↓
Spring 决定提交或回滚
        ↓
事务同步与资源清理
        ↓
SqlSession 生命周期处理
        ↓
Connection 解除关联并关闭 / 归还连接池
```

**核心理解：** 这不是 MyBatis 单独完成的，而是 Spring 事务管理、MyBatis-Spring、JDBC 和数据库共同协作的结果。

# 二、第一阶段：Service 调用与事务开启

## 1. 调用经过 Spring 事务代理

```text
外部调用
    ↓
Spring 代理
    ↓
事务拦截逻辑
    ↓
Service 方法
```

- `@Transactional`：声明事务规则与边界。
- Spring 事务代理：拦截符合条件的方法调用，协调开启、提交或回滚。
- 事务管理器：实际协调事务操作。

在常见 `REQUIRED` 传播行为下，如果当前没有事务，Spring 通常会开启新事务；如果已有事务，则加入现有事务。

**易错点：** 自调用绕过代理、手动 `new` 对象等情况，可能导致事务注解不生效。

## 2. 获取并关联 Connection

```text
Spring 事务管理器
        ↓
DataSource 获取 Connection C1
        ↓
准备事务连接
        ↓
关联到当前线程的事务资源
```

部件作用：

- `DataSource`：提供 JDBC 连接。
- `Connection`：执行 JDBC 操作，并承载数据库事务。
- `TransactionSynchronizationManager`（TSM）：管理当前线程关联的事务资源与同步信息。
- `ConnectionHolder`：持有与数据源关联的连接资源。

概念上：

```text
当前线程
    ↓
TSM 管理的事务资源
    ↓
ConnectionHolder
    ↓
Connection C1
```

**易错点：** TSM 不是数据库事务本身，也不是连接工厂；`ThreadLocal` 只是线程局部存储机制。

# 三、第二阶段：Mapper A 执行 SQL

Service 调用：

```java
accountMapper.deduct(1, 100);
```

常见调用链：

```text
Mapper 代理
    ↓
SqlSessionTemplate
    ↓
SqlSessionUtils
    ↓
获取 / 复用 SqlSession
    ↓
Executor 执行 SQL
    ↓
SpringManagedTransaction
    ↓
Connection C1
    ↓
数据库执行 SQL A
```

各部件在这条链路中的作用：

| 部件 | 在当前流程中的作用 |
|---|---|
| Mapper 代理 | 将 Java 方法调用交给 MyBatis 执行 |
| `SqlSessionTemplate` | 协调 Mapper 调用时的 SqlSession 使用 |
| `SqlSessionUtils` | 检查、获取或复用事务关联的 SqlSession，并协调生命周期 |
| `SqlSessionHolder` | 持有并关联当前事务使用的 SqlSession |
| `Executor` | 组织 SQL 执行、缓存等工作 |
| `SpringManagedTransaction` | 让 MyBatis 使用 Spring 管理的 JDBC 连接 |
| `Connection` | 实际执行 JDBC 操作 |

SQL A 执行后：

```text
SQL 已执行
    ↓
修改可能尚未提交
    ↓
事务继续进行
```

**易错点：** SQL 执行成功不等于事务已经提交。

# 四、第三阶段：Mapper B 复用事务资源

Service 接着调用：

```java
accountMapper.add(2, 100);
```

在同一有效 Spring 事务、同一数据源及正确事务配置下，第二次 Mapper 调用通常会复用当前事务关联的会话和连接。

```text
Mapper B
    ↓
SqlSessionTemplate
    ↓
检查事务关联的 SqlSession
    ↓
复用相关资源
    ↓
Connection C1
    ↓
数据库执行 SQL B
```

概念上：

```text
SQL A → Connection C1
SQL B → Connection C1
```

这样两个 SQL 才能作为同一个数据库事务中的操作统一提交或回滚。

### 容易混淆的部件

- **`SqlSession`**：MyBatis 的会话层，负责组织数据库访问。
- **`Connection`**：JDBC 连接层，承载数据库事务。
- **`SqlSessionTemplate`**：协调会话使用，不等于底层连接。
- **`SpringManagedTransaction`**：连接 MyBatis 与 Spring 管理的连接，不是独立的 Spring 事务管理器。

**易错点：** 两个 Mapper 都由 Spring 注入，并不自动保证它们属于同一个事务；还要确认事务传播、数据源和事务管理器配置。

# 五、第四阶段：事务结束——提交还是回滚

## 1. 正常返回

```java
@Transactional
public void transfer() {
    accountMapper.deduct(1, 100);
    accountMapper.add(2, 100);
}
```

**流程**：

```text
SQL A 执行
    ↓
SQL B 执行
    ↓
方法正常返回
    ↓
Spring 检查事务状态
    ↓
事务可以提交
    ↓
COMMIT
```

两个操作一起提交。

## 2. 抛出运行时异常

```java
@Transactional
public void transfer() {
    accountMapper.deduct(1, 100);
    accountMapper.add(2, 100);

    throw new RuntimeException("测试回滚");
}
```

流程：

```text
SQL A 执行
    ↓
SQL B 执行
    ↓
RuntimeException 向外传播
    ↓
Spring 事务代理命中默认回滚规则
    ↓
ROLLBACK
```

两个 SQL 的未提交修改都被回滚。

### 事务规则速记

| 情况 | 默认行为 |
|---|---|
| 方法正常返回，事务可提交 | 提交 |
| `RuntimeException` 向事务代理传播 | 回滚 |
| `Error` 向事务代理传播 | 回滚 |
| 受检异常 `Exception` | 默认通常不回滚 |
| 异常被捕获且未触发其他回滚机制 | 可能提交 |

需要受检异常也触发回滚时，可以使用：

```java
@Transactional(rollbackFor = Exception.class)
```

**易错点：** 是否回滚取决于异常类型、传播方式、回滚规则和事务状态，而不是只看代码中有没有异常。

# 六、第五阶段：捕获异常与 rollback-only

假设外层事务调用内层 `REQUIRED` Service：

```text
外层事务 T1
    ↓
执行 SQL A
    ↓
调用内层 Service
    ↓
内层抛出运行时异常
    ↓
共享事务被标记为 rollback-only
    ↓
外层捕获异常并继续执行
    ↓
外层方法正常返回
    ↓
事务仍不能正常提交
    ↓
最终回滚
```

`rollback-only` 表示当前事务已被标记为只能回滚。

**易错点：** 捕获异常不等于清除 `rollback-only`。在常见配置下，外层最终可能抛出 `UnexpectedRollbackException`。

### `REQUIRED` 与 `REQUIRES_NEW`

```text
REQUIRED
→ 通常加入现有事务，共享事务结果

REQUIRES_NEW
→ 暂停外层事务，创建独立事务
```

如果 T2 是 `REQUIRES_NEW`，并且 T2 已经成功提交，那么外层 T1 后续回滚通常不会撤销 T2 的提交结果。

# 七、第六阶段：事务结束后的资源清理

事务提交或回滚后，还需要处理会话和连接资源。

```text
Spring 完成提交 / 回滚
        ↓
事务同步及相关回调
        ↓
解除事务资源关联
        ↓
处理 SqlSession 生命周期
        ↓
清理 Connection 事务关联
        ↓
关闭 / 归还 Connection
```

这是概念流程。真实执行时，事务同步回调、会话处理与连接清理可能交错发生，具体顺序取决于框架实现及配置。

### 这里的职责区分

| 工作 | 主要负责方 |
|---|---|
| 数据库提交 / 回滚 | Spring 事务管理机制 |
| SqlSession 使用与生命周期协调 | MyBatis-Spring |
| 当前线程事务资源绑定与解绑 | Spring 事务资源管理机制 |
| 连接关闭 / 归还连接池 | Spring 资源管理与 DataSource / 连接池机制 |

**易错点：**

- 提交 / 回滚决定数据库事务结果。
- SqlSession 清理处理会话生命周期。
- Connection 清理释放当前使用的连接资源。
- 连接池中的 `Connection.close()` 通常是归还连接，而不是销毁物理数据库连接。

因此，不能把“连接被关闭”当作“事务回滚”的原因。

# 八、事务与缓存的关系

```text
数据库事务
→ 决定数据库修改是否提交

MyBatis 缓存
→ 维护查询结果缓存
```

- 一级缓存与 `SqlSession` 相关，写操作通常会清理相关缓存；回滚不会自动把缓存完整恢复到写操作之前。
- 标准 MyBatis 二级缓存会通过事务协调机制延迟处理相关缓存变更；回滚时通常会丢弃待提交的缓存变更。

**易错点：** 数据库回滚不等于所有缓存都恢复原状。

# 十、最后记住这条主线

```text
Spring 代理
    ↓
Spring 事务管理器开启 / 加入事务
    ↓
Connection 与当前事务关联
    ↓
Mapper A、Mapper B 执行 SQL
    ↓
Spring 根据执行结果提交或回滚
    ↓
MyBatis-Spring 协调 SqlSession 生命周期
    ↓
Spring / DataSource 机制清理连接资源
```

**核心结论：**

1. Spring 决定事务边界和提交 / 回滚。
2. MyBatis-Spring 协调 Mapper、SqlSession 与 Spring 事务。
3. JDBC Connection 承载数据库事务。
4. 同一有效事务中的多个 Mapper 通常复用事务关联的 Connection。
5. 事务结果与资源清理是不同的事情。
6. 实战验证必须检查最终数据库状态，并结合日志或调试器验证资源复用。
