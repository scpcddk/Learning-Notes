# MyBatis 常见性能问题笔记

> 记录常见性能瓶颈、排查方法与优化思路，方便实际项目中快速定位问题。

## 一、N+1 查询

**问题表现：**

查询一次主数据后，遍历结果，为每条记录再次执行关联查询。

例如：查询 80 名学生，执行 1 次学生查询和 80 次班级查询，共 81 次 SQL。

**排查方法：**
- 查看 SQL 日志和参数，确认是否存在重复查询。
- 比较 SQL 执行次数与返回记录数。

**优化思路：**
- 优先考虑 JOIN。
- 也可以收集关联 ID，通过 `IN` 批量查询，再在 Java 中组装结果。

**易错点：** SQL 次数多不一定就是 N+1，必须结合日志确认。

## 二、慢 SQL 与索引

**问题表现：**

SQL 本身执行耗时较长。

**排查方法：**
- 使用 `EXPLAIN` 分析执行计划。
- 关注 `type`、`key`、`rows` 等字段。
- 检查过滤条件、JOIN 条件、排序及索引是否合理。

**优化思路：**
- 根据查询条件和执行计划评估索引。
- 避免不必要的全表扫描、排序和数据读取。
- 只查询业务需要的字段。

**易错点：**
- `key = NULL` 不代表表没有索引。
- `rows` 是估算值，不是实际扫描行数的绝对证明。
- 不能看到 `type = ALL` 就盲目加索引。

## 三、大结果集与分页

**问题表现：**

一次返回大量记录，增加数据库读取、网络传输、结果映射和 JSON 序列化开销。

**优化思路：**
- 使用分页。
- 只查询必要字段。
- 对深分页场景评估游标分页（Keyset Pagination）。

**分页公式：**

`offset = (pageNum - 1) × pageSize`

```sql
SELECT id, name
FROM student
ORDER BY id
LIMIT 100, 20;
```

**易错点：**
- `offset` 表示跳过的记录数，不是页码。
- 深分页可能需要扫描并跳过大量记录。
- 随机跳页通常更适合 OFFSET；连续向后加载通常可以考虑游标分页。
- 分页查询应使用稳定排序，必要时增加唯一字段作为排序条件。

## 四、批量操作

**问题表现：**

循环执行大量单条 INSERT、UPDATE 或 DELETE，产生过多数据库交互。

**优化思路：**
- 批量删除：评估 `WHERE id IN (...)`。
- 批量插入：使用多行 INSERT 或 JDBC/MyBatis 批处理。
- 大批量数据：合理分批，测试合适的批次大小。

**重要区别：**

- 多行 INSERT：一条 SQL 包含多个 `VALUES`。
- `ExecutorType.BATCH`：批处理多次 JDBC 更新操作，不等于自动合并成一条多行 INSERT。

**易错点：**
- 批次过大可能增加内存、锁持有时间和失败处理成本。
- `flushStatements()` 不等于事务提交。
- 批量操作必须考虑事务、异常及部分失败的处理策略。

## 五、MyBatis 缓存

**一级缓存：**
- 默认与 `SqlSession` 的本地缓存机制有关。
- 同一会话内满足缓存条件的重复查询可能复用结果。

**二级缓存：**
- 需要相应配置，通常以 Mapper namespace 为范围。
- 是否适用取决于数据更新频率、缓存一致性和业务需求。

**优化思路：**
- 先确认是否存在重复读取，再决定是否使用缓存。
- 评估数据更新后的失效与一致性问题。

**易错点：**
- 缓存命中不能替代 SQL 和接口性能分析。
- 不要对频繁变化、强一致性要求高的数据盲目启用缓存。

## 六、连接池与连接等待

**问题表现：**

接口很慢，但 SQL 本身执行时间不长。

**排查方法：**
- 查看获取连接的等待时间。
- 查看连接池 active、idle、pending 等指标。
- 检查长事务、连接占用和连接归还情况。

**判断方向：**

- 连接等待长、SQL 执行短：优先检查连接池使用和连接占用。
- 连接等待短、SQL 执行长：优先检查 SQL、执行计划、锁等待和数据量。

**易错点：** 不要因为连接等待就直接无限增大连接池；连接数过多也可能压垮数据库。

## 七、结果映射与 JSON 序列化

**问题表现：**

SQL 已经很快，但接口总耗时仍然很高。

**可能原因：**
- 查询结果过大。
- MyBatis 结果映射耗时较高。
- Java 业务处理复杂。
- JSON 序列化耗时较长。
- 返回对象包含大量不必要的嵌套数据。

**优化思路：**
- 使用合适的 DTO / VO。
- SQL 只查询需要的字段。
- 返回对象只保留前端需要的数据。
- 使用计时埋点或性能分析工具定位具体耗时。

**易错点：** SQL 优化不等于接口整体优化；只删除返回字段，也不一定能减少数据库读取和结果映射成本。

## 八、通用性能排查流程

```text
① 确认接口总耗时与复现条件
        ↓
② 检查 SQL 执行次数，排查 N+1
        ↓
③ 检查单条 SQL 耗时与执行计划
        ↓
④ 检查连接等待、锁等待和事务
        ↓
⑤ 检查结果集大小、映射与业务处理
        ↓
⑥ 检查 JSON 序列化与响应体积
        ↓
⑦ 实施针对性优化
        ↓
⑧ 对比优化前后性能并验证功能正确性
```

## 九、性能优化的核心原则

1. **先测量，再定位，再优化。**
2. SQL 次数多，优先检查重复查询；单条 SQL 慢，再分析执行计划。
3. 区分连接等待、SQL 执行、结果映射和 JSON 序列化。
4. 不盲目添加索引、缓存或扩大连接池。
5. 优化后必须重新测试，并确认业务结果正确。
6. 性能测试应尽量保持数据量、请求参数和测试环境一致。
