# MyBatis 错题与易错点补充：八、常见设计问题

> 本节记录 MyBatis 工程设计中容易忽略的风险、设计取舍和安全边界。
>
> 重点不是重复基础语法，而是理解：**代码能运行，不代表设计安全、可维护、符合业务要求。**

---

# 一、Controller → Service → Mapper 职责

## 1. 三层职责不同，不是 Spring Boot 的强制语法要求

```text
Controller
    ↓
Service
    ↓
Mapper
    ↓
MyBatis / JDBC / MySQL
```

- Controller：接收请求、处理请求参数、组织 HTTP 响应。
- Service：执行业务规则、参数校验、事务管理、协调多个数据访问操作。
- Mapper：执行数据库操作，将 Java 方法与 SQL 映射起来。

**易错点：**

技术上可以在 Controller 中直接调用 Mapper，但不代表这是合理的工程设计。

当业务逻辑、事务或多个数据库操作逐渐增加时，直接在 Controller 中操作 Mapper 会增加耦合。

---

# 二、事务边界设计

## 2. 事务边界由业务原子性决定

假设一个业务需要：

```text
① 更新学生成绩
② 插入成绩修改记录
```

如果业务要求两项操作必须同时成功或失败，就应该将它们放在同一个有效事务中。

```java
@Transactional
public void updateScore(...) {
    studentMapper.updateScore(...);
    scoreLogMapper.insert(...);
}
```

**易错点：**

- `@Transactional` 不意味着所有异常都会自动回滚。
- Spring 默认通常对 `RuntimeException` 和 `Error` 回滚；受检异常通常需要通过 `rollbackFor` 等配置纳入回滚规则。
- 捕获异常后直接吞掉，可能使事务正常结束并提交。
- `REQUIRES_NEW` 会创建独立事务，不适合用来保证两个操作同成同败。
- 远程 API 调用可能延长事务时间；如果不要求与数据库操作原子完成，应评估能否在数据库事务提交后执行。

# 三、Mapper / XML 可维护性

## 3. Mapper 方法名应体现操作意图

推荐：

```java
selectById(...)
selectByClassName(...)
updateScore(...)
deleteById(...)
```

避免：

```java
query1(...)
handleData(...)
process(...)
```

方法名应让开发者能够快速判断其用途。

## 4. Mapper 接口与 XML 通过 namespace + id 绑定

```xml
<mapper namespace="org.example.mapper.StudentMapper">
    <select id="selectById">
        ...
    </select>
</mapper>
```

对应：

```text
org.example.mapper.StudentMapper.selectById
```

**易错点：**

真正决定绑定关系的是 `namespace + id`，而不是 XML 文件名。

## 5. SQL 片段可以复用，但不要为了复用而复用

```xml
<sql id="studentColumns">
    id, name, age, gender, score, class_name
</sql>
```

使用：

```xml
SELECT <include refid="studentColumns"/>
FROM student
```

适合多个查询真正共享相同字段集合的情况。

如果列表查询只需要 `id, name`，详情查询需要更多字段，就不应该为了复用而强行让列表查询读取全部字段。

## 6. 固定结构的搜索条件通常适合 DTO

```java
public class StudentSearchDTO {
    private String className;
    private String gender;
    private Integer minScore;
    private Integer maxScore;
    private String nameKeyword;
}
```

```java
List<Student> searchStudents(StudentSearchDTO query);
```

**易错点：**

`Map<String, Object>` 并非不能用于 MyBatis，但固定的参数结构通常更适合 DTO，因为字段、类型和语义更清楚。

# 四、动态 SQL 设计

## 7. `<if>` 负责条件是否加入，不负责业务校验

```xml
<if test="minScore != null">
    AND score >= #{minScore}
</if>
```

当 `minScore` 不为空时，才加入对应条件。

但动态 SQL 不负责判断：

- 最低成绩是否大于最高成绩。
- 是否允许所有查询条件为空。
- 是否允许没有更新字段。
- 是否允许没有删除条件。

这些都需要根据业务规则设计校验。

## 8. 动态查询可能意外退化成全表查询

```xml
<where>
    <if test="name != null and name != ''">
        AND name = #{name}
    </if>
</where>
```

如果 `name` 为空，可能生成：

```sql
SELECT * FROM student;
```

如果业务不允许无条件查询，应在 Service 层拒绝请求。

## 9. 动态 UPDATE 需要考虑没有更新字段的情况

```xml
<set>
    <if test="name != null">
        name = #{name},
    </if>
    <if test="score != null">
        score = #{score},
    </if>
</set>
```

当两个字段都没有提供时，SQL 可能没有实际更新内容。

**设计原则：**

- 先明确哪些字段允许更新。
- 根据业务规则检查是否至少提供一个有效更新字段。
- 不要将“未提供字段”和“明确设置为 NULL”混为一谈。

## 10. 动态 DELETE 必须防止无条件删除

如果所有 `<if>` 都不成立，可能生成：

```sql
DELETE FROM student;
```

不能依赖 `<where>` 自动保证删除安全。

推荐：

- 优先使用职责明确的删除方法，例如 `deleteById`。
- 如果业务允许条件删除，在 Service 层校验必要条件。
- 不要用 `AND id > 0` 之类没有实际限制效果的条件假装安全。

## 11. 动态 UPDATE / DELETE 的保护原则

```text
Service
→ 校验业务输入和操作范围

Mapper / XML
→ 使用明确的 SQL 条件

Database
→ 通过约束、事务等机制提供额外保护
```

Service 校验不能替代 SQL 本身的正确性，也不能替代数据库约束。

---

# 五、resultType / resultMap 选择

## 12. 两者不是“整体映射”和“一对一映射”的区别

```text
resultType
→ 指定结果 Java 类型，通常依赖自动映射

resultMap
→ 显式定义列与属性的映射关系
```

`resultMap` 不仅用于一对一，还可以处理：

- 普通字段的显式映射。
- 一对一关联：`association`。
- 一对多关联：`collection`。
- 复杂嵌套结果。

## 13. property 与 column 不要弄反

```xml
<result property="className" column="class_name"/>
```

```text
property → Java 属性
column   → SQL 查询结果中的列
```

## 14. 驼峰映射不能解决所有字段名称差异

```yaml
mybatis:
  configuration:
    map-underscore-to-camel-case: true
```

可以帮助将：

```text
class_name → className
```

但不能自动将：

```text
student_id → id
```

这种不是简单命名风格转换的字段对应关系。

# 六、批量操作设计

## 15. 批量操作的目标是减少数据库交互，但批次并非越大越好

例如插入 1000 条记录，可以考虑多行 INSERT：

```sql
INSERT INTO score_record (student_id, score)
VALUES
    (1, 90),
    (2, 85),
    (3, 92);
```

MyBatis 可以使用 `<foreach>` 生成多行 VALUES。

相比循环执行大量单条 INSERT，多行 INSERT 通常能减少数据库交互次数。

## 16. 大批量操作需要控制批次大小

一次插入 10 万条记录可能带来：

- SQL 过长或参数数量超出限制。
- 内存与数据库资源占用增加。
- 单次操作耗时过长。
- 失败后的处理成本增加。

应根据数据规模、驱动、数据库限制和实际测试决定批次大小。

## 17. 分批执行不等于分批提交事务

如果业务要求所有记录必须同时成功或失败，可以分批执行 SQL，但仍在一个有效事务中提交。

如果业务允许部分成功，才考虑按业务规则分批提交。

# 七、缓存设计

## 18. 一级缓存与二级缓存的作用范围不同

| 缓存 | 作用范围 | 默认情况 |
|---|---|---|
| 一级缓存 | `SqlSession` 内 | 默认开启 |
| 二级缓存 | 同一 Mapper namespace 范围内 | 默认不开启 |

一级缓存不能在不同 `SqlSession` 之间直接共享。

二级缓存通常需要配置，并应根据数据更新频率、一致性要求和实际收益决定是否启用。

## 19. 读多写少不代表一定适合二级缓存

使用缓存前需要评估：

- 数据是否频繁修改。
- 业务是否允许一定延迟。
- 写操作是否能正确影响缓存。
- 是否存在其他应用或系统修改数据。
- 缓存是否真的减少了瓶颈。

库存等需要准确处理并发修改的数据，不能仅依靠普通缓存保证正确性。

例如：

```sql
UPDATE product
SET stock = stock - 1
WHERE id = #{productId}
  AND stock > 0;
```

再根据受影响行数判断扣减是否成功，可以将库存不足的判断放在数据库原子操作中处理。

# 八、`#{}` / `${}` 安全问题

## 20. `#{}` 与 `${}` 的本质区别

```text
#{}
→ 参数绑定，通常转换为 JDBC 的 ? 占位符

${}
→ SQL 文本直接替换
```

例如：

```xml
WHERE name = #{name}
```

适合普通参数值。

而：

```xml
ORDER BY ${sortField}
```

是直接将 SQL 片段拼入语句，必须严格控制输入来源。

## 21. 为什么 `ORDER BY #{sortField}` 通常不能实现动态列名？

假设传入：

```text
sortField = "score"
```

使用：

```sql
ORDER BY #{sortField}
```

MyBatis 通常会将其转换为：

```sql
ORDER BY ?
```

此时 `score` 是参数值，不是列标识符。

它不能实现预期的动态排序，某些数据库中甚至可能退化成对常量排序。

**核心原则：**

普通值使用 `#{}`；SQL 结构不能直接靠普通参数绑定来改变。

# 九、动态排序：深入设计

## 22. 动态排序为什么需要特殊处理？

排序字段和排序方向属于 SQL 结构：

```sql
ORDER BY score DESC
```

其中：

```text
score → 排序字段
DESC  → 排序方向
```

用户可能提交：

```text
sortField = score
sortOrder = DESC
```

但也可能提交任意字符串。

如果将用户输入直接拼进 `${}`，就会产生 SQL 注入风险。

因此，动态排序的正确设计不是“把 `#{}` 换成 `${}`”，而是：

> **将用户输入转换为预先允许的 SQL 结构，再进行拼接。**

## 23. 推荐方案：白名单映射

假设接口只允许按照成绩、姓名或年龄排序。

不要将原始用户输入直接传给 Mapper，而是先将外部字段名映射为固定的 SQL 列名。

```java
private String resolveSortColumn(String sortField) {
    return switch (sortField) {
        case "score" -> "score";
        case "name"  -> "name";
        case "age"   -> "age";
        default -> throw new IllegalArgumentException(
            "不支持的排序字段"
        );
    };
}
```

排序方向也需要单独校验：

```java
private String resolveSortOrder(String sortOrder) {
    return switch (sortOrder) {
        case "ASC"  -> "ASC";
        case "DESC" -> "DESC";
        default -> throw new IllegalArgumentException(
            "不支持的排序方向"
        );
    };
}
```

然后将校验后的结果传给 Mapper。

XML 可以写成：

```xml
<select id="selectStudents" resultType="Student">
    SELECT id, name, age, gender, score, class_name
    FROM student
    ORDER BY ${sortColumn} ${sortOrder}
</select>
```

这里的 `${}` 只有在以下前提下才是可接受的：

1. `sortColumn` 来自固定白名单映射。
2. `sortOrder` 只能是 `ASC` 或 `DESC`。
3. 原始用户输入绝不直接传入 `${}`。
4. 传入 Mapper 的值在所有调用路径中都受到相同约束。

**不要因为某个 Controller 已经校验，就假定其他调用 Mapper 的路径也一定安全。**

## 24. 更容易维护的方式：枚举或固定映射

当排序选项比较固定时，可以用枚举表达业务允许的排序选项。

例如：

```java
public enum StudentSortField {
    SCORE("score"),
    NAME("name"),
    AGE("age");

    private final String column;

    StudentSortField(String column) {
        this.column = column;
    }

    public String getColumn() {
        return column;
    }
}
```

请求中的 `"score"` 应先转换成允许的枚举值，再取出固定列名。

注意：如果排序选项是外部请求传入的字符串，不能直接使用未经校验的字符串构造枚举或传入 SQL。

枚举的优势是将允许的选项集中定义，降低拼写错误和随意扩展 SQL 结构的风险。

## 25. 排序字段与数据库列名应分开

推荐让 API 使用稳定的业务名称：

```text
score → score
name  → name
age   → age
```

如果数据库以后将 `score` 改名为 `student_score`，只需要调整白名单映射，不必要求客户端同步修改请求字段。

这也是白名单映射比直接拼接请求参数更容易维护的原因。

## 26. 动态排序还要考虑分页稳定性

例如：

```sql
SELECT id, name, score
FROM student
ORDER BY score DESC
LIMIT #{offset}, #{pageSize};
```

如果多个学生的成绩相同，仅按 `score DESC` 排序时，分页顺序可能不够稳定。

可以追加唯一字段作为次级排序：

```sql
ORDER BY score DESC, id ASC
```

这样在成绩相同的情况下，会进一步按照 `id` 排序。

**易错点：**

- 排序字段安全，不代表分页顺序一定稳定。
- `LIMIT` 的参数仍然适合使用 `#{}`。
- 排序字段和方向属于 SQL 结构，必须经过白名单控制。

## 27. 动态排序与 SQL 注入的核心记忆

```text
普通查询值
→ #{value}

动态列名
→ 不能直接用 #{column} 实现

动态排序字段
→ 白名单映射
→ ${trustedColumn}

动态排序方向
→ 白名单映射
→ ${trustedDirection}
```

如果排序选项很少，也可以完全不使用 `${}`，而是在 XML 中使用 `<choose>` / `<when>`，为每个允许的排序选项写出固定的 ORDER BY 片段。这种方式可以进一步减少动态 SQL 文本拼接。

例如：

```xml
<choose>
    <when test="sortField == 'score'">
        ORDER BY score
    </when>
    <when test="sortField == 'name'">
        ORDER BY name
    </when>
    <otherwise>
        ORDER BY id
    </otherwise>
</choose>
```

如果还要支持排序方向，也应对方向做显式分支或白名单映射。

# 十、本节综合排查顺序

遇到 Mapper 设计问题时，可以按下面的顺序检查：

```text
① Controller 参数是否合理？
        ↓
② Service 是否完成业务校验？
        ↓
③ Mapper 方法职责是否清晰？
        ↓
④ namespace + id 是否正确绑定？
        ↓
⑤ 动态 SQL 是否可能生成危险语句？
        ↓
⑥ #{xxx} 是否对应正确的参数？
        ↓
⑦ ${xxx} 是否来自可信的固定内容？
        ↓
⑧ UPDATE / DELETE 是否有正确限制条件？
        ↓
⑨ 批量操作的事务与批次大小是否合理？
        ↓
⑩ 缓存是否满足一致性要求？
        ↓
⑪ 最终 SQL、执行结果和性能是否符合预期？
```

---

# 本节核心记忆

1. Controller → Service → Mapper 是职责划分，不是强制语法。
2. 事务边界由业务原子性决定。
3. Mapper 方法与 XML 依赖 `namespace + id` 绑定。
4. DTO 通常适合结构固定、条件较多的查询请求。
5. 动态 SQL 不负责保证业务输入合理。
6. 动态查询、更新和删除都必须考虑条件缺失的情况。
7. 批量执行不代表越大越好；分批执行也不代表必须分批提交。
8. 一级缓存属于 `SqlSession`，二级缓存通常属于 Mapper namespace。
9. 缓存不能替代事务、原子更新和并发控制。
10. `#{}` 绑定参数值，`${}` 替换 SQL 文本。
11. 动态排序字段与方向都必须经过白名单控制。
12. 动态排序的安全性与分页的稳定性是两个不同问题。
13. 遇到性能问题，应先测量和定位，再决定是否需要优化。
