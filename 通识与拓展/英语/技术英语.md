## 01 技术文档怎么读

[01.1 阅读步骤与配置示例](#011-阅读步骤与配置示例) · [01.2 版本说明与迁移指南](#012-版本说明与迁移指南) · [01.3 从 API 参考提取可验证条件](#013-从-api-参考提取可验证条件)

### 01.1 阅读步骤与配置示例

打开文档后先确定要解决的问题。安装跑不起来、参数不知道怎么填、接口结果和预期不一致，分别对应不同的阅读入口。

#### 按文档类型找信息

| 材料 | 先看 | 读完要能说清 |
| --- | --- | --- |
| Quickstart、安装指南 | 支持版本、前置条件、最小运行示例 | 在什么环境运行哪一步，看到什么才算成功 |
| 概念说明 | 术语定义、组成部分、输入和输出 | 每个部件负责什么，信息如何在部件之间流动 |
| 配置参考 | 配置项的类型、默认值、适用范围 | 不设置会怎样，显式设置会改变什么 |
| API 参考 | 请求格式、必填字段、成功和错误响应 | 发什么、收什么、哪条分支需要额外处理 |
| 版本说明、迁移指南 | 目标版本、破坏性变更、替代方式 | 哪些旧写法要改，在哪个版本开始受影响 |
| 排错说明 | 适用症状、诊断条件、可观察结果 | 这段说明是否匹配当前症状，下一步核对哪一处 |

同一页可能混有操作指南、概念和参考表。卡在某个选项时，可以直接查该选项的默认值和适用范围，再回到操作步骤。

#### 把一段文档读成几个可以核对的事实

1. **标适用范围**。先圈版本、环境、运行模式和对象。遇到同名参数，核对它属于客户端、服务端还是某个插件。
2. **找动作和执行者**。圈出谁 `reads`、`loads`、`returns` 或 `rejects` 什么。被动句省略执行者时，用上下文定位是哪个组件在做。
3. **拆分支**。把 `if`、`unless`、`only if` 和后面的动作抄在一起。把默认行为、显式配置和错误分支分行写。
4. **找可观察结果**。记下能核对的响应状态、输出、日志或生成文件。文档只说 `is supported` 时，继续找支持的前提和用法。
5. **保留原文中的搜索词**。中文旁边保留参数名、英文错误片段和章节链接。回查时优先用准确拼写。

#### 容易读漏的语气

| 信号 | 读法 |
| --- | --- |
| `requires`、`must` | 找到具体的必要条件，以及条件对哪一步生效。 |
| `recommended`、`should` | 识别建议的场景。遇到协议规范时，查看文档对规范用语的定义。 |
| `may`、`can` | 标出能力或可能性。用上下文判断是不是在保证结果。 |
| `by default`、`unless overridden` | 同时记录默认值和覆盖它的方式。 |
| `only applies to`、`ignored when` | 圈定生效范围，遇到无效配置时优先对照这一行。 |
| `deprecated`、`removed` | 前者通常表示已不推荐继续使用，后者表示指定版本已经移除。核对各自对应的版本。 |

#### 示例：拆一段配置参考

> In development mode, the service reads `app.local.yaml` if the file exists. Otherwise, it reads `app.yaml`. The `APP_PORT` environment variable overrides the port in the selected file. If neither source specifies a port, the service listens on port 8080.

**简译**：开发模式下，服务优先读取存在的 `app.local.yaml`，否则读取 `app.yaml`。环境变量 `APP_PORT` 会覆盖所选文件里的端口。两处都没指定端口时，服务监听 8080。

| 读出的信息 | 对应原文 |
| --- | --- |
| 这里讨论开发模式 | `In development mode` |
| 本地配置文件存在时优先读取它，否则读取基础配置文件 | `if the file exists`、`Otherwise` |
| 环境变量会覆盖已选配置文件里的端口 | `overrides the port in the selected file` |
| 环境变量和已选配置文件都没提供端口时，才使用 8080 | `If neither source specifies a port` |

把它写成便于排查的一行：先确认是否是开发模式，再确认选中了哪个文件。端口从高到低依次查看 `APP_PORT`、已选文件中的端口、默认值 8080。看到 8080 时，若想知道它来自哪里，还要看实际配置，因为显式配置也可能恰好填了 8080。

### 01.2 版本说明与迁移指南

> The old option is deprecated in this release and scheduled for removal in the next major version. Existing configurations continue to work for now. Before upgrading, replace the option, then verify that the effective configuration has the same value.

**简译**：旧选项在本版本中已弃用，并计划在下个主版本移除。已有配置暂时仍能工作。升级前先换用新选项，再核对实际生效值是否一致。

| 关键词与搭配 | 在这段里的含义 |
| --- | --- |
| `deprecated` | 仍可存在但不推荐继续使用 |
| `scheduled for removal` | 计划在未来移除 |
| `effective configuration` | 运行时实际采用的配置 |

**阅读辨析** 读到 deprecated 时，同时圈出替代名称、移除版本、验证行为三项。

### 01.3 从 API 参考提取可验证条件

> The response includes a continuation token only when more results are available. Clients should treat the token as opaque and send it unchanged with the next request. A missing token marks the end of the result set.

**简译**：只有还有结果时，响应才包含续页令牌。客户端应把令牌视为不透明值，下一次请求原样传回。没有令牌表示结果已到末尾。

| 关键词与搭配 | 在这段里的含义 |
| --- | --- |
| `only when` | 指出出现令牌的必要条件 |
| `opaque token` | 调用方无需解析内部结构的令牌 |
| `unchanged` | 原样传递 |

**阅读辨析** 从一段话分别提取触发条件、客户端动作和结束标志。

## 02 MyBatis 参数绑定与结果映射

[02.1 参数绑定与语句定位](#021-参数绑定与语句定位) · [02.2 动态 SQL 与参数列表](#022-动态-sql-与参数列表) · [02.3 显式映射与关联集合](#023-显式映射与关联集合) · [02.4 会话与事务边界](#024-会话与事务边界)

### 02.1 参数绑定与语句定位

> To retrieve a student by ID, call `StudentMapper.selectById(id)`. MyBatis uses the mapper namespace and the statement ID to locate the mapped SQL statement. In the default prepared-statement mode, `#{id}` acts as a parameter placeholder. MyBatis binds the supplied value to the corresponding parameter before executing the query. If a row matches, MyBatis maps the returned columns to properties of a `Student` object.

**简译**：按 ID 查学生时，调用 `StudentMapper.selectById(id)`。MyBatis 用 Mapper 的命名空间和语句 ID 定位 SQL。在默认的预编译语句模式下，`#{id}` 是参数占位符。MyBatis 先绑定传入值，再执行查询。查到匹配的行后，它把返回的列映射到 `Student` 对象的属性。

这段英文按仓库里的学生查询示例编写。 [MyBatis 实践记录](../../编程语言/JAVA/MyBatis/MyBatis实践记录/MyBatis%20实践记录.md)

#### 关键词与搭配

| 原文词块 | 在这里具体指什么 | 常用搭配 |
| --- | --- | --- |
| **retrieve a student by ID** | 以 ID 为条件取回一条学生记录。`by ID` 给出查找依据。 | `retrieve a record by its key`、`retrieve data from a database` |
| **namespace / statement ID** | 命名空间对应 Mapper 接口，语句 ID 指向其中的一条映射语句。两者一起用于定位 SQL。 | `the mapper namespace`、`a mapped statement` |
| **parameter placeholder** | SQL 里给参数值预留的位置。MyBatis 的 `#{id}` 在这种模式下会对应 JDBC 的 `?` 参数位置。 | `a placeholder for the ID`、`a positional parameter` |
| **bind the supplied value to ...** | 将调用方给出的值交给对应参数。`bind A to B` 的 A 是值，B 是参数位置。 | `bind a value to a parameter`、`a bound parameter` |
| **execute the query** | 执行查询。`query` 作名词时指查询，作动词可以说 `query the database`。 | `execute a statement`、`run a query` |
| **map the returned columns to properties** | 将数据库列与 Java 对象属性对应起来。`map A to B` 的方向由 A 指向 B。 | `map a column to a property`、`result mapping` |

参数与结果的行为可对照官方参考。 [MyBatis Mapper XML 文档](https://mybatis.org/mybatis-3/sqlmap-xml.html)

#### 一条查询里的三种动词

| 表达 | 从哪个角度描述 |
| --- | --- |
| `The application retrieves a student record.` | 调用方想取到什么。 |
| `MyBatis binds the student ID to a query parameter.` | 执行前，框架怎样处理输入。 |
| `The mapper method returns a Student object.` | 调用方拿到的返回值是什么。 |

`parameter` 往往指声明里等待接收值的位置，`argument` 指调用时传入的值。以 `selectById(Integer id)` 和 `selectById(42)` 为例，`id` 是方法参数，`42` 是实参。文档若写 `bind 42 to the SQL parameter`，此处的 `parameter` 则在 SQL 这一层。

#### 在实际文档中跟踪方向

`supplied value` 属于输入，`returned columns` 属于查询输出。读到 `map A to B` 时先保留 A、B 的原顺序，再翻译成「把 A 映射到 B」。这个习惯也适用于 JSON 字段与对象属性、表单字段与请求参数之间的映射。

### 02.2 动态 SQL 与参数列表

> The mapper adds a status predicate only when the caller provides a status. A foreach element builds the list of placeholders for the selected IDs. The application handles an empty ID list before calling the mapper so that the intended query semantics remain clear.

**简译**：只有调用者传入状态时，映射器才添加状态筛选。foreach 为选中的 ID 生成占位符列表。应用在调用前处理空列表，明确这种输入应该查询什么。

| 关键词与搭配 | 在这段里的含义 |
| --- | --- |
| `predicate` | 用于筛选的条件表达式 |
| `placeholder` | 给绑定值预留的位置 |
| `query semantics` | 查询应当表达的行为 |

**阅读辨析** 区分拼出 SQL 结构和绑定参数值。阅读动态条件时先查空值、空集合会进入哪一条分支。 [MyBatis Dynamic SQL](https://mybatis.org/mybatis-3/dynamic-sql.html)

### 02.3 显式映射与关联集合

> A join returns one row for each matching parent and child pair. An explicit result map groups the rows into parent objects and populates a collection of children. Column aliases distinguish identifiers whose original names are the same.

**简译**：连接查询会为每对匹配的父子记录返回一行。显式结果映射把这些行组装成父对象，并填充子对象集合。列别名区分原名相同的标识列。

| 关键词与搭配 | 在这段里的含义 |
| --- | --- |
| `explicit result map` | 显式声明列到对象的映射 |
| `populate a collection` | 把元素填入集合 |
| `column alias` | 查询结果中的列别名 |

**阅读辨析** 区分结果集的行数和最终对象的个数。 [MyBatis Result Maps](https://mybatis.org/mybatis-3/sqlmap-xml.html)

### 02.4 会话与事务边界

> The service updates two records in one transaction. Both mapper calls participate in the same unit of work. If the second update fails and the transaction is rolled back, the first update is rolled back with it.

**简译**：服务在一个事务中更新两条记录。两次 Mapper 调用属于同一工作单元。若第二次更新失败并导致事务回滚，第一次更新也会一起回滚。

| 关键词与搭配 | 在这段里的含义 |
| --- | --- |
| `transaction boundary` | 事务何时开始和结束 |
| `unit of work` | 作为整体处理的一组操作 |
| `roll back an update` | 撤销尚未提交的更新 |

**阅读辨析** 看到 session、connection 和 transaction 时，分别查对象范围、连接获取方式和提交者。 [MyBatis-Spring Transactions](https://mybatis.org/spring/transactions.html)

## 03 HTTP 请求响应与异步处理

[03.1 请求响应与异步状态](#031-请求响应与异步状态) · [03.2 幂等语义与超时重试](#032-幂等语义与超时重试) · [03.3 分页与参数传递](#033-分页与参数传递) · [03.4 条件请求与缓存校验](#034-条件请求与缓存校验)

### 03.1 请求响应与异步状态

> Send a `POST` request to `/exports` with the export options in the request body. If the server accepts the request, it responds with `202 Accepted` and returns a job ID. Poll `GET /exports/{id}` until the response indicates that the job has finished. In this API, deleting a completed export returns `204 No Content` on success.

**简译**：向 `/exports` 发送 POST 请求，把导出选项放在请求正文中。服务端接受请求后会返回 202 和作业 ID。重复查询 `GET /exports/{id}`，直到响应显示作业已经结束。删除已完成的导出结果时，这个接口成功返回 204，响应没有正文。

这是虚构的报表导出接口。作业 ID 和查询路径是该接口的设计。 [RFC 9110 · HTTP 状态码](https://datatracker.ietf.org/doc/html/rfc9110#section-15)

#### 关键词与搭配

| 原文词块 | 在这里具体指什么 | 常用搭配 |
| --- | --- | --- |
| **send a request to an endpoint** | 向某个接口发请求。读 API 表格时把方法和路径一起看，`POST /exports` 和 `GET /exports/{id}` 是两个操作。 | `make a request to`、`call the endpoint` |
| **request body** | 请求正文。例子把导出选项放在这里。查询参数写在 URL 的查询部分，请求头另有字段。 | `include X in the request body`、`parse the response body` |
| **accept the request / respond with 202** | 服务端接收请求并用 202 表示已受理，任务可能还在队列中。此处接口另外返回作业 ID。 | `accept a request for processing`、`respond with a status code` |
| **poll the endpoint** | 客户端定期发查询请求，查看同一个作业的进展。 | `poll for status updates`、`poll until completion` |
| **indicate that the job has finished** | 状态响应里有能判断任务已经结束的信息。实际文档还需查明哪些状态表示成功，哪些表示失败。 | `indicate completion`、`report a failed status` |
| **return 204 No Content on success** | 删除成功时返回 204，响应没有正文。 | `on success`、`a response with no content` |

#### 近似表达放在同一场景比较

| 写法 | 应当读出的动作 |
| --- | --- |
| `The job was accepted.` | 服务端接收了这项工作。若接口是异步的，继续查作业状态。 |
| `The job completed successfully.` | 已有结果表明工作执行成功。 |
| `Poll the status endpoint.` | 反复查询同一作业的状态。 |
| `Retry the original request.` | 再发原始请求。原始请求会创建作业时，先查接口的重试约定，确定重复发送会发生什么。 |

看到 `returns` 时留意它后面接什么。`returns 202` 说状态码，`returns a job ID` 说返回的数据，`returns no content` 说响应正文。一个响应可以同时有状态码和响应头，即使没有正文。

### 03.2 幂等语义与超时重试

> The connection timed out before the client received a response. The client cannot infer whether the server applied the operation. It may retry an idempotent request when the retry policy permits it. For a create operation, it follows the API's documented idempotency mechanism.

**简译**：客户端尚未收到响应，连接就超时了。这时无法判断服务端是否已经执行操作。若策略允许，可以重试具备幂等语义的请求。创建操作则要遵循该接口说明的幂等机制。

| 关键词与搭配 | 在这段里的含义 |
| --- | --- |
| `time out` | 在规定时间内未完成 |
| `idempotent` | 重复请求的预期效果与执行一次相同 |
| `retry policy` | 规定何时与怎样重试的策略 |

**阅读辨析** 应用支持幂等键时，再查它覆盖的请求、保留时间及参数不一致时的行为。 [RFC 9110 · 幂等方法](https://datatracker.ietf.org/doc/html/rfc9110#section-9.2.2)

### 03.3 分页与参数传递

> The list endpoint returns a page of results and a next-page cursor. The client sends that cursor with the same filters to continue the listing. It stops when the response no longer contains a cursor.

**简译**：列表接口返回一页结果及下一页游标。客户端保留原筛选条件，并附上游标继续获取。响应不再包含游标时结束。

| 关键词与搭配 | 在这段里的含义 |
| --- | --- |
| `page of results` | 一批分页结果 |
| `next-page cursor` | 服务器给出的续页位置 |
| `filter` | 用于限制结果范围的筛选条件 |

**阅读辨析** cursor 不是 page number。游标是否过期、修改排序是否有效由接口文档说明。

### 03.4 条件请求与缓存校验

> The server returns an ETag with the representation. On a later GET, the client sends that value in If-None-Match. If the selected representation still matches the validator, the server can respond with 304 and the client can reuse its stored copy.

**简译**：服务端随资源表示返回 ETag。后续 GET 把它放入 If-None-Match。若当前表示仍与验证标识匹配，服务端可返回 304，客户端复用原来的副本。

| 关键词与搭配 | 在这段里的含义 |
| --- | --- |
| `representation` | 资源的一种可传输表示 |
| `validator` | 用于判断表示是否变化的标识 |
| `reuse a stored copy` | 复用缓存副本 |

**阅读辨析** 收到 304 时，客户端可按缓存规则复用之前保存的响应内容。收到 204 时，操作成功且这次响应没有内容。 [RFC 9110 · 304 Not Modified](https://datatracker.ietf.org/doc/html/rfc9110#section-15.4.5)

### 04.1 启动日志与依赖排查

> The service loaded its configuration from `app.yaml` and started listening on port 8080. The readiness check failed because the database refused the connection. The service will retry the connection in five seconds. If the problem persists, verify the database host and port in the active configuration.

**简译**：服务已从 `app.yaml` 加载配置，并开始监听 8080 端口。数据库拒绝了连接，因此就绪检查失败。服务将在五秒后重试连接。若问题仍然存在，请核实当前生效配置中的数据库主机和端口。

这段虚构日志摘要同时写了已成功的步骤和仍失败的步骤。先按时间读动作，再看最后一句建议对应哪一层。

#### 关键词与搭配

| 原文词块 | 在这里具体指什么 | 常用搭配 |
| --- | --- | --- |
| **load configuration from** | 从指定来源加载配置。先确认程序实际读取的路径，再对照自己修改的文件。 | `load settings from a file`、`read an environment variable` |
| **listen on port 8080** | 服务已在 8080 端口等待连接。该动作只说明监听已经启动。 | `listen on a port`、`listen for incoming connections` |
| **readiness check** | 判断服务当前是否准备好接流量的检查。本例把数据库连接纳入了判断。 | `pass a readiness check`、`report the service as unready` |
| **refuse the connection** | 连接尝试遭拒。记录出错的主机、端口和时间，再看数据库是否正在该地址接收连接。 | `connection refused`、`a connection attempt` |
| **retry the connection** | 再尝试建立连接。后面的 `in five seconds` 表示五秒之后执行。 | `retry after a delay`、`retry a failed operation` |
| **verify ... in the active configuration** | 核实运行时采用的配置。需要同时留意文件内容和可能的覆盖来源。 | `verify the effective settings`、`override a setting` |

#### 相似日志词如何指向下一步

| 日志表达 | 核对的信息 |
| --- | --- |
| `Configuration loaded` | 核对实际采用的配置来源和生效值。 |
| `Server listening` | 核对监听的地址和端口。 |
| `Connection refused` | 核对目的地址、端口和对端是否接受连接。 |
| `Connection timed out` | 核对哪一步等待超时、等待多久、目标地址是否可达。 |
| `Authentication failed` | 核对失败的是哪次身份验证，以及程序用了哪套凭据或认证方式。 |

### 14.1 指令与存储层次

> The processor fetches an instruction, decodes it and executes the operation. A cache hit allows the processor to obtain the data from the cache. A cache miss may require access to a lower level of the memory hierarchy. An instruction may store its result in a register.

#### 关键词与搭配

| 关键词 | 在这里的意思 | 可复用搭配 |

| **fetch an instruction** | 从相应位置取出指令 | `instruction fetch` |
| **decode** | 解释指令编码 | `decode an instruction` |
| **register** | 处理器内部用于保存值的存储位置 | `store a value in a register` |
| **cache hit / miss** | 目标数据能否从当前缓存层取得 | `handle a cache miss` |
| **memory hierarchy** | 由不同速度、容量的存储层组成的层次 | `access main memory` |

`latency` 是完成一次访问的等待时间，`throughput` 是单位时间完成的工作量。读流水线说明时，先确认文档在讨论哪项指标。

仓库笔记 · [计算机组成原理阅读指南](../../软件工程/计算机组成原理/笔记/章节笔记/阅读指南.md)

### 14.2 流水线和停顿

> The processor overlaps several instruction stages. When an instruction needs a value that is not yet available, the pipeline may stall. The stall affects throughput even if the instruction sequence is short.

**简译**：处理器让多条指令的不同阶段重叠执行。某条指令需要尚未可用的值时，流水线可能停顿。即使指令序列很短，停顿也会影响吞吐量。

| 关键词与搭配 | 在这段里的含义 |
| --- | --- |
| `overlap stages` | 让执行阶段重叠 |
| `stall` | 暂时停住推进 |
| `throughput` | 单位时间内完成的工作量 |

**阅读辨析** 吞吐量描述整体处理速度，latency 描述单条指令或单次操作的完成时间。

### 14.3 局部性与缓存缺失

> The loop reads adjacent elements in sequence. Fetching one cache line can bring nearby elements into the cache. A different access pattern can cause more misses even when it performs the same number of reads.

**简译**：循环依次读取相邻元素。取入一个缓存行时可能把附近元素一起带入缓存。即使读取次数相同，访问模式不同也可能引起更多未命中。

| 关键词与搭配 | 在这段里的含义 |
| --- | --- |
| `adjacent elements` | 位置相邻的元素 |
| `cache line` | 缓存传输和管理的一块数据 |
| `access pattern` | 访问地址的规律 |

**阅读辨析** 把 reads、cache misses 和 time 分开，三者不一定同比变化。

| 关键词 | 在这里的意思 | 可复用搭配 |
| --- | --- | --- |
| **register an instance** | 把服务实例信息登记到注册中心 | `register with the service registry` |
| **service discovery** | 按服务名等信息找到服务实例 | `discover an available instance` |
| **configuration service** | 集中提供配置的服务 | `fetch configuration` |
| **at runtime** | 在应用运行期间 | `apply a change at runtime` |
| **refresh configuration** | 决定是否以及怎样刷新配置的设置 | `refresh application settings` |

`service name` 是逻辑名称，`instance` 是运行中的一个具体节点。看到 `configuration published` 时，可继续查应用是否拉到新值、是否刷新，以及新值是否覆盖了本地值。

仓库笔记 · [Nacos](../../云原生/数据库与中间件/Nacos.md)

### 20.2 服务发现与调用失败

> The consumer discovers a registered instance through the registry. A successful lookup returns an address, but a subsequent request can still fail. The caller records which instance it selected and whether the error occurred before or after connection.

**简译**：消费方通过注册中心发现实例。查询成功得到地址，但随后发出的请求仍可能失败。调用方记录选中哪个实例以及错误发生在连接前还是连接后。

| 关键词与搭配 | 在这段里的含义 |
| --- | --- |
| `registered instance` | 已登记的服务实例 |
| `service lookup` | 查询可调用实例 |
| `subsequent request` | 随后发出的请求 |

**阅读辨析** 把登记可见、发现成功和真实请求成功分别验证。

### 20.3 配置标识与刷新

> The application subscribes to a configuration entry in its intended environment. After a change is published, the client receives a notification. Whether existing components see the new value depends on how the application refreshes its configuration.

**简译**：应用在目标环境订阅一个配置项。发布改动后，客户端收到通知。已有组件能否读到新值取决于应用刷新配置的方式。

| 关键词与搭配 | 在这段里的含义 |
| --- | --- |
| `configuration entry` | 通过标识定位的配置条目 |
| `publish a change` | 发布配置变更 |
| `refresh configuration` | 将更新带入运行中的应用 |

**阅读辨析** 先核对环境与条目标识，再区分变更已发布、客户端已接收和业务已生效。

## 21 Redis 与缓存

[21.1 键值操作与缓存模式](#211-键值操作与缓存模式) · [21.2 TTL 过期与内存淘汰](#212-ttl-过期与内存淘汰) · [21.3 缓存回填与并发未命中](#213-缓存回填与并发未命中) · [21.4 持久化与恢复](#214-持久化与恢复)

### 21.1 键值操作与缓存模式

> The application looks up the key in Redis. On a cache miss, it loads the record from the database and stores it with a time to live. When the record changes, the application invalidates the cached value so that a later request can load fresh data.

**简译**：应用先在 Redis 里查键。缓存未命中时，从数据库读取记录并按设定的存活时间缓存。记录改变后，应用让缓存失效，后续请求就能重新读到新数据。

#### 关键词与搭配

| 关键词 | 在这里的意思 | 可复用搭配 |
| --- | --- | --- |
| **look up a key** | 按键查找存储的值 | `a key lookup` |
| **cache miss** | 缓存中没有可用数据 | `handle a cache miss` |
| **time to live** | 键保留多久，简称 TTL | `set a TTL on a key` |
| **invalidate** | 让旧缓存值失效 | `invalidate a cache entry` |
| **fresh data** | 重新读取到的数据 | `serve fresh data` |

`expiration` 通常由时间到期引起，`eviction` 通常表示系统因资源约束等策略移除数据，`invalidation` 描述主动让旧值不再用于后续读取。

仓库笔记 · [Redis](../../云原生/数据库与中间件/Redis.md)

### 21.2 TTL 过期与内存淘汰

> A key can disappear because its time to live expired. Under memory pressure, an eviction policy can remove eligible keys earlier. Metrics for expiration and eviction help explain which mechanism removed data.

**简译**：键可能因为存活时间到期而消失。内存不足时，淘汰策略也可提前移除符合条件的键。分别查看过期和淘汰指标，有助于判断数据为何消失。

| 关键词与搭配 | 在这段里的含义 |
| --- | --- |
| `time to live` | 键的存活时限 |
| `memory pressure` | 内存资源紧张 |
| `eviction policy` | 选择移除哪些键的规则 |

**阅读辨析** TTL 是数据何时过期的设置，eviction policy 是达到内存限制后怎样选键。 [Redis Key Eviction](https://redis.io/docs/latest/develop/reference/eviction/)

### 21.3 缓存回填与并发未命中

> Several requests miss the same cached item at once. If each request fetches it from the database, the extra traffic can overload the database. The service can allow one request to refill the entry while others wait briefly.

**简译**：多个请求同时没命中同一个缓存项。如果每个请求都查库，额外流量可能使数据库过载。服务可让一个请求回填，其余短暂等待。

| 关键词与搭配 | 在这段里的含义 |
| --- | --- |
| `cache miss` | 缓存中找不到所需内容 |
| `refill an entry` | 重新填充缓存项 |
| `concurrent requests` | 同时发生的多个请求 |

**阅读辨析** 描述这种问题时给出是同一个键、发生在什么时间窗口及回源量如何变化。

### 21.4 持久化与恢复

> A snapshot records the dataset at a point in time. An append-only log records changes for later replay. When discussing recovery, specify which persistence mode was enabled and what data the restored instance actually contains.

**简译**：快照记录某一时刻的数据集，只追加日志记录可在之后重放的变更。讨论恢复时，要写明启用了哪种持久化方式，以及恢复后的实例实际包含什么。

| 关键词与搭配 | 在这段里的含义 |
| --- | --- |
| `snapshot` | 某时点的数据快照 |
| `append-only log` | 以追加方式记录变更的日志 |
| `replay changes` | 重放已有变更 |

**阅读辨析** 备份文件存在、持久化开启和恢复结果正确是三个分别核对的事实。 [Redis Persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)

### 22.1 生产消费与确认

> The producer publishes an order event to a topic. A consumer processes the event and records progress according to the messaging system's acknowledgment rules. If delivery is repeated, the handler uses the event ID to avoid applying the same business change twice.

**简译**：生产者把订单事件发到主题。消费者处理事件，并按消息系统的确认机制记录进度。若事件重复投递，处理器用事件 ID 避免重复执行业务变更。

#### 关键词与搭配

| 关键词 | 在这里的意思 | 可复用搭配 |
| --- | --- | --- |
| **publish an event** | 发布业务事件 | `send a message to a topic` |
| **consumer** | 从消息系统接收或读取数据的消费端 | `a consumer group` |
| **acknowledgment** | 接收或处理过程中的确认 | `acknowledge a message` |
| **repeated delivery** | 同一逻辑消息再次投递 | `handle duplicate deliveries` |
| **event ID** | 用于识别事件的标识 | `deduplicate by event ID` |

Kafka 文档常用 `partition` 和 `offset` 描述日志分区与读取位置。RocketMQ 文档常围绕消息、队列和消费结果描述重试。看到 `acknowledged` 或 `offset committed` 时，查清确认发生在处理前还是处理后。

### 22.2 Kafka 分区与消费位置

> A topic is divided into partitions. An offset identifies a record's position within its partition. A consumer group can resume from its committed positions after a restart, subject to its configuration and the availability of those records.

**简译**：主题由多个分区组成。偏移量标识记录在本分区的位置。重启后，消费者组可以从已提交位置恢复，具体受配置和记录是否仍存在影响。

| 关键词与搭配 | 在这段里的含义 |
| --- | --- |
| `partition` | 主题内部独立的有序日志 |
| `offset` | 分区内的位置 |
| `committed position` | 消费者组已经记录的恢复位置 |

**阅读辨析** 比较 offset 时先核对主题和分区。消息已读、已处理、消费位置已提交是不同阶段。

### 22.3 RocketMQ 重试与死信

> A consumer reports a processing failure. RocketMQ can deliver the message again under the configured retry policy. If retries are exhausted, the message may move to a dead-letter queue for investigation.

**简译**：消费者报告处理失败。RocketMQ 可按重试策略再次投递。用尽重试次数后，消息可能进入死信队列，等待排查。

| 关键词与搭配 | 在这段里的含义 |
| --- | --- |
| `redelivery` | 再次投递 |
| `retry policy` | 规定重试时机与次数的策略 |
| `dead-letter queue` | 保存超过重试上限等异常消息的队列 |

**阅读辨析** 先看失败类型、消费模式和重试次数，再决定查重试还是死信。 [RocketMQ Consumption Retry](https://rocketmq.apache.org/docs/featureBehavior/10consumerretrypolicy/)

### 22.4 消费去重与确认时机

> The consumer updates the record and then acknowledges the message. A failure between those steps can lead to redelivery. The handler stores a business identifier so it can recognise a change that has already been applied.

**简译**：消费者更新记录后再确认消息。如果两步之间失败，消息可能被再次投递。处理器保存业务标识，以识别已经应用过的变更。

| 关键词与搭配 | 在这段里的含义 |
| --- | --- |
| `acknowledge` | 向消息系统确认处理结果 |
| `redelivery` | 把同一消息再次交给消费者 |
| `business identifier` | 识别同一业务动作的标识 |

**阅读辨析** 确认成功和业务处理成功要分别描述，读到 exactly once 时尤其要核对它涵盖哪一层。

**简译**：监控系统根据平时的基线发现异常，并归并相关告警。运维人员检查受影响服务，将异常时间与近期发布对照。调查记录可能的原因，以及确认它所需的证据。

**简译**：事件时间线记录最早症状、已经采取的动作和服务恢复时点。缓解措施先减少眼前影响。后续改动再处理使故障可能发生的条件。

| **steps to reproduce** | 别人可以照着操作的复现步骤 | `reproduce the issue with the same input` |
| **actual result** | 实测结果 | `compare the actual and expected results` |
| **affected behavior** | 改动涉及的行为范围 | `identify affected behavior` |
| **verify the fix** | 验证修复的效果 | `verify with an existing record` |
| **known limitation** | 已经知道且应交代的限制 | `document a known limitation` |

标题写可观察的现象，例如 `Student details page returns HTTP 500 for an unknown ID`。验证段写已做的事和结果，例如 `Confirmed that an unknown ID returns HTTP 404.`

### 31.2 Issue 的复现边界

> The report identifies the application version and lists the smallest set of steps that reproduces the issue. It states the expected and observed behaviour, then includes the relevant log excerpt.

**简译**：报告给出应用版本与能重现问题的最少步骤，说明预期和实际表现，并附相关日志片段。

| 关键词与搭配 | 在这段里的含义 |
| --- | --- |

| `expected behaviour` | 预期行为 |
| `log excerpt` | 和现象直接相关的一小段日志 |

**阅读辨析** 报告先写现象与条件，推测原因单独标为尚待确认。

### 31.3 PR 的改动与验证证据

> The change handles an empty response before parsing begins. The pull request describes the affected case and records the checks run against both empty and non-empty responses.

**简译**：改动在解析前处理空响应。PR 描述受影响的情况，并记录针对空响应与非空响应执行过的检查。

| 关键词与搭配 | 在这段里的含义 |

| `verification` | 核对行为是否符合预期 |

### 32.1 排版与仓库笔记

> A Markdown heading gives the section a clear title. A fenced code block preserves the formatting of a command or snippet. In a renderer that supports LaTeX math, use inline math for a symbol in a sentence and display math for a standalone equation. Define any notation before using it in a derivation.

**简译**：Markdown 标题给小节起名，围栏代码块保留命令或片段的排版。在支持 LaTeX 数学的渲染器里，用行内公式表示句中的符号，用独立公式排版单独一行的等式。推导前先定义所用记号。

#### 关键词与搭配

| 关键词 | 在这里的意思 | 可复用搭配 |
| --- | --- | --- |
| **heading** | 给章节或小节命名的标题 | `use a descriptive heading` |
| **fenced code block** | 由标记围起来的代码块 | `include a command in a fenced code block` |
| **snippet** | 从代码或文本中截出的一小段 | `a minimal code snippet` |
| **inline math / display math** | 嵌在句子里的数学内容与独立排版的公式 | `typeset an equation as display math` |
| **notation / derivation** | 记号与推导过程 | `define the notation before the derivation` |
